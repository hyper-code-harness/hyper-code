# Git как источник bundle: сценарий для проверки

> **Не текущая модель.** Сейчас реализовано «один плагин = один репозиторий, релиз = тег, установка = git clone в `USER_PLUGINS`» — см. [src/plugins/SKILL.md](../src/plugins/SKILL.md), разделы «Publishing», «Installing from the catalog», «Changing an installed plugin». Этот документ — более ранний эскиз bundle из нескольких плагинов.

**Статус: проектное описание для обсуждения, не реализованный API.** Зафиксированное в разговоре решение: **один Git-репозиторий = один bundle**; bundle содержит один или несколько независимо включаемых и настраиваемых плагинов. Корень репозитория — корень bundle, без выбора подкаталога bundle. Локальная папка и распакованный npm-пакет должны представлять *такое же дерево файлов*; источник различается способом поиска следующей ревизии, а не правилами установки. Точный синтаксис manifest ещё не утверждён.

## Как автор готовит репозиторий

Например, `https://github.com/acme/hyper-team-tools.git`:

```text
hyper-team-tools/                 ← корень Git-репозитория = корень bundle
├── package.json                  ← предлагаемый manifest bundle
├── plugins/
│   ├── status-board/
│   │   ├── package.json          ← собственные имя и procs.src
│   │   ├── SKILL.md
│   │   └── src/statusBoard/
│   │       ├── status.ts         ← ctx.fns.statusBoard.status({})
│   │       ├── $setting_project.ts
│   │       ├── $start.ts
│   │       └── $stop.ts
│   └── release-notes/
│       ├── package.json
│       ├── SKILL.md
│       └── src/releaseNotes/
│           └── latest.ts
└── README.md
```

**Эскиз**, не схема, которую понимает нынешний Hyper:

```json
{
  "name": "@acme/hyper-team-tools",
  "version": "1.0.0",
  "hyper": {
    "bundle": {
      "schemaVersion": 1,
      "plugins": [
        { "id": "status-board", "path": "plugins/status-board" },
        { "id": "release-notes", "path": "plugins/release-notes" }
      ]
    }
  }
}
```

Manifest перечисляет состав и относительные пути. Название поля `hyper.bundle`, область `@acme`, обязательность `version` и политика включения по умолчанию — **предложения, не утверждённый контракт**. Идентификатор bundle не заменяет runtime namespace каждого плагина. Пути должны оставаться внутри корня и не пересекаться; Hyper валидирует каждый plugin root до исполнения кода. Файл `SKILL.md` и `package.json` у каждого плагина соответствуют его собственному контракту.

## Первая установка: что видит человек и что делает система

Пользователь указывает Git URL и канал обновлений, например ветку `main`. Доступ к приватному репозиторию задаётся **в настройках Git-провайдера**, отдельно от настроек будущих плагинов. URL, ref и приватные учётные данные требуют валидации и ограничений; устанавливаемый код не должен получать эти секреты.

| Шаг | Git-провайдер | Hyper |
| --- | --- | --- |
| 1. Выбор | Проверяет допустимый репозиторий, разрешает `main` в полный commit, например `abc123…` | Показывает bundle-кандидат и источник |
| 2. Получение | Доставляет дерево **точного commit** в пустую временную папку Hyper без запуска скриптов, hooks или кода плагинов | Владеет папкой staging; не монтирует её как runtime |
| 3. Проверка | — | Валидирует manifest, пути, размер, состав плагинов; считает digest всего нормализованного дерева; проверяет namespace-конфликты |
| 4. Review | — | Показывает источник, commit, digest, состав, файлы и риск запуска; спрашивает согласие |
| 5. Включение | — | После подтверждения сохраняет bundle и предлагает отдельно включить `status-board` и `release-notes` |

Если commit изменился между поиском и получением, Git-провайдер **не переключается молча** на новый commit: он получает выбранный commit или сообщает ошибку. Git commit — идентичность в Git, а digest после получения — идентичность дерева файлов Hyper. Извлечение архива/дерева должно отвергать выход за границы, symlink, специальные файлы, подмодули и неявные зависимости в managed-пути. Проверка и согласие не делают исполняемый плагин песочницей: его код после включения доверенный.

После установки сохраняется запись примерно такого смысла (не готовый формат lock):

```json
{
  "provider": "git",
  "repository": "https://github.com/acme/hyper-team-tools.git",
  "updateChannel": { "kind": "branch", "name": "main" },
  "installedCommit": "<full immutable commit hash>",
  "bundleDigest": "sha256:<canonical-tree-digest>",
  "plugins": [
    { "id": "status-board", "enabled": true },
    { "id": "release-notes", "enabled": false }
  ]
}
```

Канал говорит, **куда смотреть при проверке обновлений**. `installedCommit` и `bundleDigest` говорят, **что реально установлено**. Изменение указателя ветки само по себе ничего не меняет в работающем коде. Настройки плагинов живут отдельно от этой записи: `$setting_<key>.ts` объявляет поля, пользовательские значения — Postgres scope `user`, общие — Postgres либо instance settings file, секреты — в защищённом хранилище.

## Проверка обновлений

1. Пользователь нажимает «Проверить обновления» (автоматическая проверка, если появится, **только уведомляет** до явного решения). Git-провайдер смотрит, на какой *полный commit* сейчас указывает сохранённая ветка `main` или выбранный тег. Зафиксированный неизменяемый commit сам по себе не является каналом обновлений: для него нужен отдельный выбор новой ревизии.
2. Если commit совпадает с установленным, обновления нет. Если иной — провайдер получает **именно его** в новую временную папку. Даже если ref сменился ещё раз, кандидат остаётся привязан к выбранному commit.
3. Hyper валидирует manifest и дерево, считает digest и сравнивает с установленным. Если содержимое совпадает, нет кодового обновления; может измениться только известный commit-источник (нужно отдельно решить, записывать ли такой факт в историю). Если различается — показать diff всего bundle, по каждому плагину: добавленные/удалённые плагины, функции, страницы, tools, настройки и файлы.
4. Hyper просит согласие **на конкретный commit и digest**. До подтверждения остаётся установленный код. При изменении кандидата review недействителен и повторяется. После согласия обновляется bundle; включённые/выключенные плагины и пользовательские настройки сохраняются, если их схема совместима. Несовместимость показывается заранее и блокирует без решения пользователя.
5. Если обновление или запуск не удались, Hyper честно показывает состояние *на диске* и *в runtime*. Проверенный локальный снимок предыдущей версии позволяет rollback там, где это безопасно; старый commit ещё можно запустить без сети. Пока нет гарантированной горячей выгрузки, для обновления включённого плагина может потребоваться restart — нельзя обещать атомарную live-замену.

Теги по умолчанию следует считать **потенциально передвигаемыми**: хранить и проверять полный commit, а политику «следить за тегом» либо явно включить, либо использовать версионированные релизы. Git URL не обязан быть глобальным именем: возможный будущий реестр `@scope/bundle` может отдельно разрешать имя в источник, commit и digest, но не участвует в первом прямом Git-пути.

## Что совпадает с filesystem и npm

| Источник | Одно дерево bundle | Как искать новую ревизию | Что закрепляется при установке |
| --- | --- | --- | --- |
| Filesystem | Указанная локальная папка | Пересчитать digest после изменения файлов или при явной проверке | Канонический путь + digest скопированного дерева |
| Git | Корень одного репозитория | Разрешить сохранённый ref/канал в новый commit | URL + канал для поиска; полный commit + digest установленного дерева |
| npm | Корень распакованного пакета | Узнать новую допустимую версию пакета | Имя + правило версий для поиска; точная версия, целостность архива и digest дерева |

**Общее:** только провайдер ищет и доставляет. Проверка, diff, согласие, включение и обновление принадлежат Hyper; одинаковые байты bundle должны давать одинаковый канонический digest независимо от источника. Версия в manifest — метаданные выпуска, не подмена digest.

## Где расходится с текущим кодом

- `$plugin_provider_filesystem.ts` и v1 `search`/`materialize` уже существуют, но v1 selection и `validateTree` рассчитаны на **один plugin tree**, а не на manifest с несколькими плагинами. Текущий filesystem search выдаёт ревизию по `package.json` с `mounted:`, которую materialize напрямую не принимает. Git-провайдер по этому сценарию ещё не реализован.
- Раздельное включение внутри управляемого bundle, хранение его lock, полноценная проверка обновлений и безопасная горячая выгрузка — план, не готовые возможности. Существующие `$start.ts` / `$stop.ts` сохраняются как форма lifecycle; корректная остановка старой версии при замене пока требует отдельной реализации.
- Этот документ описывает поведение для review, а не даёт команд на установку/публикацию. Реализацию и окончательные поля manifest согласуем отдельно.

## Вопросы для решения перед кодом

1. `package.json` + `hyper.bundle` или отдельный корневой manifest? Нужна ли явная версия manifest и обязательна ли версия bundle для локальной папки?
2. Включать ли новые плагины после установки по умолчанию или только после явного выбора?
3. Что значит «обновление», если commit новый, но digest дерева тот же; когда менять lock/provenance без запуска?
4. Как выбирать версионный канал для Git: ветка, неизменяемый тег, релиз или только ручной выбор нового commit?
5. Что делать с удалённым из manifest плагином и его настройками, особенно если он включён или имеет активные задачи?

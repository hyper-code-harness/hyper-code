# Hyper Multiuser — дизайн

Статус: черновик. Автор: агент + niquola.
Контекст: Hyper сегодня — однопользовательская процедурная среда (Bun + Postgres,
одна функция на файл, hot-reload). Задача — понять, как в неё может войти второй
человек, не разрушив то, что делает её быстрой.

---

## 0. Основа (от niquola)

Здесь фиксируются исходные положения, заданные автором. Остальные разделы
подчинены этим положениям и при конфликте переписываются.

**0.1 Система живёт в PostgreSQL.**

**0.2 Это организационная multiuser / multiagent платформа.**
Не персональный инструмент с пристройкой для второго человека, а платформа
организации: много людей и много агентов в одной системе.

**0.3 Внутри платформы есть проекты.**
Проект — это обычно runtime + git-репозиторий. Пример: landing.
То есть у проекта есть свой код, своё исполнение и своё состояние, а не только
папка с файлами.

**0.4 Несколько LLM-провайдеров одновременно.**
От API-ключей до подписок (Claude Code, Codex и т.п.). Это разные по природе
источники доступа: ключ тарифицируется потокенно и делится легко,
подписка привязана к человеку/устройству, имеет свои лимиты и не всегда
юридически делима. Платформа обязана знать, откуда берётся доступ для
каждого вызова и кто за него платит.

**0.5 Подписки принадлежат пользователям, а не организации.**
Агент работает на подписке конкретного человека — значит, у вызова есть не
только автор, но и «на чьём топливе» он выполнен. Следствия:
фоновая работа от моего имени тратит мою подписку; чужой агент не может
молча на неё опереться; в общем проекте нужно явное решение, чьё топливо
используется; организационные ключи и личные подписки — два разных класса
источников с разными правилами.

**0.6 Код пишется внутри системы.**
В Hyper и агент, и пользователи дописывают свои runtime-функции на ходу
(один файл = одна функция, hot-reload) — это не побочная возможность, а суть
платформы. Возможно, право писать функции принадлежит только админам.

Последствие, которое определяет всю остальную безопасность: кто пишет
функцию — пишет код, исполняемый в общем процессе с общей БД.
Значит граница между пользователями не может держаться на проверках внутри
кода — автор функции их просто не напишет. Либо писать функции могут
только доверенные люди (админы), либо чужой код исполняется за границей
процесса. Третьего варианта нет. См. §7.

**0.7 Выдача доступов и подтверждения живут в другом процессе.**
Раз агент может программировать сам себя (hot-reload, `eval`, переопределение
функций через `.hyper/`), любой код в его процессе — включая проверку прав
и диалог подтверждения — агент может переписать. Поэтому authority
(гранты, режимы, approval, аудит) — отдельный процесс, который агент не
может ни изменить, ни обойти. См. §22.

**0.8 У каждого агента и проекта есть identity в форме email-адреса.**
Не только люди: `sales@org`, `landing@org`, `reader.anya@org`. Это адрес для
сообщений и субъект для прав. См. §24.

## 1. Цель и не-цели

**Цель.** Дать нескольким людям работать со своими агентами и разговаривать
вместе в общих комнатах, сохранив персональность данных и скорость разработки.

**Не-цели.**
- Не строим «organization-level harness» (Nautilo: 65 пакетов, 2.9M строк).
  Размер — минус, а не плюс.
- Не вводим ORM, namespace-модель в каждой таблице, E2E-криптографию,
  Electron/мобильные клиенты.
- Не пытаемся изолировать пользователей внутри одного процесса.

**Ведущий принцип.** Изоляция — свойство процесса и базы, а не проверок в коде.
Совместность — свойство протокола между агентами, а не общей памяти.

## 2. Отправная точка (факты о текущей системе)

Проверено по живой БД и исходникам:

- Ядро — 19 таблиц в схеме `public`: `agents`, `messages`, `events`,
  `settings`, `kv`, `local_secrets`, `oauth_credentials`, `attachments`,
  `cron_tasks`, `cron_runs`, `agent_watches`, `functions`, `plugin_docs`, …
- Все 22 плагина уже живут в собственных схемах (`news`, `telegram`, `docs`,
  `healthrepo`, `knowledge`, `crme`, `focus`, …) и адресуют их по имени.
- Весь доступ к БД проходит через единственную точку — `procs.db.conn()`.
- Аутентификация: один общий пароль (`auth.$setting_password`), таблицы
  пользователей нет, `user_id` нет ни в одной миграции.
- `settings` уже имеет `scope_type` / `scope_id` — место для scope=user есть.
- `files.resolveSafe` намеренно НЕ ограничивает пути: агент читает и пишет
  где угодно. Рядом `bash` и `eval` в процессе сервера.
- Живые агенты лежат в `ctx.state.agent[id]`, id двухбуквенные (~700 значений).
- `agents` уже содержит `tools`, `workspace_dir`, `visibility`, `parent_id`.

Вывод: мультиюзер упирается не в схему данных, а в исполнение (bash/eval/ФС/браузер).

## 3. Три варианта и выбор

### A. Один процесс, owner_id везде
Классический SaaS-путь. Требует `owner_id` в каждой таблице ядра и каждого
плагина, фильтр в каждом запросе, инвариант-тест против забытого фильтра.
**Не решает главного**: `bash`, `eval`, файловая система и общий Chrome
остаются общими. Второй пользователь = второй root на машине.
Отклонено.

### B. Namespace-модель (путь Nautilo)
`actors` + `namespaces`, комната 1:1 с namespace, containment-запросы по
`human_actor_ids @>`, крипто-границы. Красиво и последовательно, но это
и есть источник их 297 миграций и 65 пакетов. Для нашей цены изменения —
несоразмерно.
Отклонено как основа; идею «комната как единица доступа» берём (§6).

### C. Инстанс на человека + федерация агентов  ← ВЫБРАНО
Каждый человек получает свой процесс Hyper (контейнер) и свою базу в общем
кластере Postgres. Изоляция данных, файлов, браузера и исполнения достаётся
от ядра ОС бесплатно. Совместная работа выражается не общей БД, а протоколом
«агент → агент» поверх HTTP.

Почему это правильно именно для Hyper: у нас уже есть `delegate` / `ask` /
`steer` — семантика «попросить другого агента и получить результат». Федерация
— то же самое через сеть.

## 4. Архитектура

```
                    ┌──────────────── Postgres (один кластер) ────────────────┐
                    │  db: hyper_sys   users, instances, invites, room_index  │
                    │  db: hyper_u_nik public + схемы плагинов (как сейчас)   │
                    │  db: hyper_u_ann public + схемы плагинов                │
                    └─────────────────────────────────────────────────────────┘
       ┌─────────────────────┐            ┌─────────────────────┐
       │ container: nik      │            │ container: ann      │
       │  Hyper process      │  HTTPS     │  Hyper process      │
       │  /work (его файлы)  │◄──────────►│  /work              │
       │  Chrome-профиль nik │  agent↔agent│  Chrome-профиль ann │
       └─────────────────────┘            └─────────────────────┘
```

- **База на человека.** `procs.db.conn()` выбирает базу по владельцу процесса.
  Ни один SQL в плагинах не меняется: схемы остаются те же, меняется база.
- **Миграции** прогоняются по каждой пользовательской базе одним и тем же
  `procs.migrate.up` — код общий, данные раздельные.
- **Системная база** `hyper_sys` — единственное общее место: пользователи,
  адреса инстансов, приглашения, индекс комнат. Маленькая и редко меняется.
- **Файлы.** В контейнер монтируется только `/work` этого человека; процесс
  идёт под непривилегированным пользователем. `files.resolveSafe` можно не
  чинить — граница не в нём.
- **Браузер.** Свой Chrome-профиль на контейнер. Общий профиль = общие логины,
  это недопустимо.

## 5. Личность и вход

- `hyper_sys.users`: id, handle, display_name, password_hash, created_at.
- Существующий механизм подписанной куки сохраняется; в куку добавляется
  user_id, роутинг направляет запрос в контейнер этого пользователя.
- Ключи моделей и секреты — per-user: `settings` уже умеет
  `scope_type='user'`, `local_secrets` и `oauth_credentials` живут в
  пользовательской базе и потому изолированы автоматически.
- Учёт расхода токенов на пользователя + лимит, иначе один сжигает общий ключ.

## 6. Комната как единица доступа

Групповой чат — место, где встречаются данные разных людей, поэтому именно он,
а не пользователь, становится единицей разграничения.

**Правило 1. Наследование = пересечение, не объединение.**
Комната по умолчанию не имеет доступа ни к чему персональному. Всё сверх —
явным подтверждением владельца, с привязкой к комнате, ресурсу и сроку.

**Правило 2. Pull, не push.**
Агент не получает доступ к чужому источнику. Он отправляет запрос агенту
владельца; тот решает (при необходимости спросив человека) и возвращает
**ответ**, а не сырые данные. Подтверждение спрашивается в момент действия,
у настоящего владельца.

**Правило 3. У LLM нет отзыва знания.**
Что попало в контекст комнаты — там навсегда. Выход участника, отзыв доступа,
удаление сообщения ничего не возвращают. Поэтому решение принимается ДО
раскрытия, и раскрывается минимум.

**Правило 4. Гость получает пустой набор.**
Агент с чужого инстанса по умолчанию умеет только говорить текстом: ни `bash`,
ни `eval`, ни плагинов.

## 7. Капабилити и подтверждения

Нужно независимо от мультиюзера — сегодня любой агент, прочитавший письмо
или веб-страницу, может по инъекции получить `bash`.

- Колонка `agents.tools` становится настоящей границей: набор инструментов
  выдаётся агенту явно при создании и сам не расширяется.
- Единый approval в ядре вместо guard'ов, разбросанных по плагинам
  (`gh/writeGuard`, `sidebar/approval`): плагин помечает функцию как пишущую,
  ядро спрашивает подтверждение у владельца.
- Необратимое (деньги, отправка сообщений, удаление) — всегда через approval,
  даже для собственного агента.

## 8. Федерация агент↔агент

- Один эндпоинт: «сообщение агенту от агента» с подписью инстанса-отправителя.
- Реестр пиров в `hyper_sys.instances` — не булев allowlist, а **уровень доверия**.
- Транспорт для существующей семантики `delegate` / `ask` / `finishTask`.

### 8.1 Лестница доверия

Заимствовано у ruflo (`plugin-agent-federation`). Дефолт для нового пира —
самый нижний уровень; повышение всегда ручное.

| Уровень      | Что разрешено чужому агенту |
|--------------|------------------------------|
| `unknown`    | ничего, кроме факта существования инстанса |
| `known`      | ping, статус, «кто ты» |
| `attested`   | + задать вопрос и получить **очищенный** ответ (`query-redacted`) |
| `trusted`    | + поделиться контекстом комнаты, совместная задача |
| `privileged` | + запросить действие с approval хозяина (никогда — `bash`/`eval`) |

Уровень `privileged` НЕ даёт ни исполнения кода, ни доступа к памяти — это
отличие от ruflo, где на верхнем уровне есть `full-memory` и `remote-spawn`.
У нас потолок федерации — «попросить, получить ответ».

### 8.2 Фильтр на исходящем канале

Единственный практичный ответ на «у LLM нет отзыва знания» (§6, правило 3):
если данные нельзя вернуть обратно, их нельзя выпускать. Всё, что уходит
наружу (в чужой инстанс или в общую комнату), проходит один шаг проверки:

- детекция: ключи и токены, пароли, database_url, email/телефон/адрес,
  медицинские и финансовые идентификаторы;
- действие по политике: `block | redact | hash | pass`;
- действие зависит от уровня доверия получателя: то, что проходит к
  `trusted`, блокируется к `attested`.

Фильтр — на границе процесса, а не в промпте: модель не должна быть
единственной, кто решает, что можно отдать.

### 8.3 Гигиена пиров

- Журнал исходящего: что, кому, когда, какое решение принял фильтр.
- Circuit breaker на пира: серия ошибок/подозрительных запросов → пауза.
- Учёт трат по федерации: чужой агент не должен жечь мои токены без лимита.

## 9. Чего это НЕ решает

- Инъекции через контент остаются главным риском. Контейнер ограничивает
  ущерб, но не мешает агенту добровольно рассказать лишнее в комнате.
- Персональные по своей природе плагины (applehealth, ramp, cuf, lusiadas)
  не должны становиться общими ни при каких настройках — это вопрос политики,
  а не техники.
- Hot-reload и REPL остаются per-instance: горячая правка кода у одного
  пользователя не должна валить чужой процесс. Это аргумент за контейнеры.

## 10. Порядок работ

1. **Капабилити + единый approval** — ценно уже сегодня, без мультиюзера.
2. **`procs.db.conn()` с выбором базы** + `hyper_sys.users` + вход по логину.
3. **Контейнер на человека, docker compose** — заодно даёт воспроизводимый
   запуск и бэкап/восстановление, которых сейчас нет.
4. **Федерация агент↔агент** и комнаты поверх неё.

Шаги 1–3 полезны, даже если мультиюзер так и не понадобится.

## 11. Разбор сценария: почта участников проекта

Сценарий (от niquola): есть проект, в нём несколько участников, есть плагин
Gmail, и агент проекта может читать почту участников — возможно, спрашивая
разрешение. Разбираем на нём всю модель доступов.

### 11.1 Как устроено сейчас

`google.token` берёт аккаунт из `GOOGLE_ACCOUNT` или единственного
авторизованного, читает токен из зашифрованного локального хранилища по
ключу `token:<email>` и явно комментирует: «there is no account allowlist».
То есть любой агент, вызвавший `gmail.list`, читает любой подключённый ящик.
Для одного человека это верно, для организации — недопустимо.

### 11.2 Что здесь на самом деле пересекается

В одном вызове `gmail.list` встречаются пять разных носителей прав:

| Носитель | Вопрос | Пример |
|---|---|---|
| Пользователь | кто вошёл | Аня |
| Агент | кто действует | агент проекта landing |
| Проект | где действие имеет смысл | landing |
| Ресурс | чей ящик | ящик Коли |
| Топливо | чья подписка платит | подписка Ани (§0.5) |

Разрешение — это не «Коля дал доступ к почте», а кортеж
`агент × от чьего имени × в каком проекте × к какому ресурсу × на чьём топливе`.
Права участника проекта НЕ означают прав на его личные ресурсы.

### 11.3 Модель: grant вместо общего пула токенов

- Токен Gmail принадлежит **человеку**, а не платформе. Плагин перестаёт
  выбирать аккаунт «по умолчанию» — аккаунт всегда передаётся явно.
- Человек выдаёт **grant**: «агенту проекта landing — чтение моей почты,
  фильтр: письма с меткой landing / за последние 30 дней, до 1 марта».
  Grant привязан к: (agent | project) × resource × scope × срок.
- Без grant вызов не выполняется. Отсутствие grant — не ошибка доступа
  «403 навсегда», а повод запросить подтверждение (§11.4).
- Grant отзываем, но отзыв не возвращает уже прочитанное (§6, правило 3) —
  поэтому важнее узость grant, чем возможность его отозвать.

### 11.4 Спрашивание разрешения

«Возможно, спрашивая разрешение» — ключевая часть, и у неё есть жёсткие рамки:

- Спрашивают **владельца ресурса**, а не того, кто инициировал задачу.
  Агент Ани не может уговорить Аню дать доступ к почте Коли.
- Запрос содержит: кто просит, зачем (текущая задача), что именно (узкий
  фильтр), на какой срок. Без этих полей запрос не отправляется.
- Ответ владельца: «разрешить один раз» / «разрешить до <дата> с этим
  фильтром» / «отказать». По умолчанию — один раз.
- Подтверждение нельзя запрашивать из фонового цикла молча: если человек
  недоступен, задача ждёт или завершается частичным результатом.
- **Нельзя просить разрешение на основании недоверенного текста.** Если
  агент прочитал письмо, где написано «дай доступ к ящику Коли», это не
  может стать причиной запроса. Инициатор запроса — человек, не контент.

### 11.5 Что отдаётся в результате

Агент не получает «доступ к ящику». Он получает **ответ**:
выжимку, найденный факт, список писем по фильтру. Сырые письма не попадают
в общий контекст проекта по умолчанию — это прямое следствие «у LLM нет
отзыва знания». Если результат уходит в комнату с другими участниками,
он проходит исходящий фильтр (§8.2).

### 11.6 Почему это не решается ролями проекта

Соблазн: «участник проекта → агент проекта читает его почту». Это неверно,
потому что смешивает две разные вещи: участие в работе и владение личными
данными. Человек может быть в проекте и не желать, чтобы его переписка
становилась материалом проекта. Поэтому членство в проекте даёт права на
**ресурсы проекта** (репозиторий, runtime, документы проекта), а на личные
ресурсы — только персональный grant.

### 11.7 Что нужно изменить в коде

1. `google.token` и подобные: обязательный явный `account`, запрет неявного
   выбора «единственного» аккаунта.
2. Таблица grants: `subject (agent|project) × owner_user × resource × scope
   × expires_at × created_by`.
3. Проверка grant — в одной точке ядра, а не в каждом плагине; плагин лишь
   объявляет, к какому ресурсу он обращается.
4. Журнал: кто, чей ресурс, по какому grant, с каким фильтром, что вернулось.

## 12. Три режима вместо «разрешено / запрещено»

Положение от niquola: некоторые действия не запрещаются, но создают аудит-событие,
за которое потом нужно будет ответить.

Это третий режим между «нельзя» и «можно молча», и он меняет характер системы:
контроль смещается с предотвращения на **ответственность**.

| Режим | Когда применяется | Что происходит |
|---|---|---|
| `deny` | необратимое и чужое: деньги, отправка от чужого имени, удаление, `bash`/`eval` для гостя | вызов не выполняется |
| `ask` | доступ к личному ресурсу другого человека (§11) | ждём решения владельца |
| `account` | действие в своём праве, но с последствиями для других | выполняется сразу, пишется событие с обоснованием |
| `allow` | обычная работа в границах проекта | выполняется, обычный лог |

### 12.1 Почему `account` важен

- `ask` на каждый шаг убивает автономность: агент, который спрашивает
  двадцать раз, бесполезен. `deny` на всякий случай убивает пользу.
- Организация — это среда с доверием и последствиями, а не песочница.
  Взрослому сотруднику не запрещают войти в переговорку, но видно, что он
  входил.
- Аудит-событие дешевле подтверждения: не блокирует работу, но делает
  поведение объяснимым.

### 12.2 Что такое «ответить»

Аудит-событие бессмысленно, если его никто не читает. Поэтому у события есть
адресат и жизненный цикл, а не только запись в таблице:

- **Событие** = кто, от чьего имени, что сделал, над чьим ресурсом, в каком
  проекте, на чьём топливе, с каким обоснованием (одна фраза от агента:
  зачем), и что вернулось (размер/тип, не содержимое).
- **Адресат** — владелец затронутого ресурса и владелец проекта. Событие
  попадает к ним в ленту, а не в общий журнал «на всякий случай».
- **Ответ** — человек может: принять, потребовать объяснения (агент обязан
  ответить в контексте той же задачи), отозвать грант, понизить уровень
  агента, откатить результат если он обратим.
- **Накопление** — повторяющиеся `account`-события одного вида поднимают
  вопрос автоматически: «этот агент 40 раз читал чужие календари, оставить
  так или перевести в `ask`?»

### 12.3 Кто отвечает

Отвечает **человек**, от имени которого действовал агент, а не агент.
Агент — инструмент; ответственность не делегируется вместе с задачей.
Для фоновых задач это значит: у каждой фоновой работы есть владелец,
и «агент сам решил» не является объяснением.

### 12.4 Требование к реализации

- Режим — свойство **пары** (действие, ресурс), а не функции вообще:
  `gmail.list` над своим ящиком — `allow`, над чужим — `ask`,
  над ящиком, где есть grant — `account`.
- Режим определяется в ядре, до вызова плагина; плагин не может понизить
  свой режим сам.
- Событие пишется до возврата результата агенту: нет записи — нет ответа.
- Обоснование обязательно для `account`: агент формулирует причину ДО
  действия, иначе действие деградирует до `ask`.

## 13. Роли

Положение от niquola: могут быть роли, и у ролей есть доступы.

### 13.1 Где роль работает, а где нет

Роль — это способ не раздавать права поштучно. Она хорошо описывает
**общие ресурсы** и плохо — личные.

| Область | Механизм | Почему |
|---|---|---|
| Ресурсы организации (проекты, репозитории, runtime, оргключи, настройки) | **роль** | владелец — организация, решение принимает администрация |
| Ресурсы проекта (репозиторий, деплой, документы, комнаты проекта) | **роль в проекте** | владелец — проект, решение принимает владелец проекта |
| Личные ресурсы человека (почта, календарь, здоровье, финансы, подписки) | **grant** (§11) | владелец — человек, роль его не замещает |

Правило: **роль никогда не выдаёт доступ к личному ресурсу другого
человека.** Никакая роль, включая администратора, не означает права читать
чужую почту без гранта. Администратор технически может всё (§0.6), но это
именно `account`-действие с событием, а не право по роли.

### 13.2 Уровни ролей

- **Организация**: `owner`, `admin`, `member`, `guest`.
  `admin` = право писать runtime-функции (§0.6), то есть фактически полный
  технический контроль. Это не «ещё одна роль», а доверенный круг.
- **Проект**: `lead`, `contributor`, `viewer`.
  Определяют доступ к репозиторию, деплою, документам и комнатам проекта.
- Роли складываются: права = роль в организации ∪ роль в проекте ∪ гранты.

### 13.3 Роль агента

У агента тоже есть роль, и она **не наследуется автоматически** от хозяина.
Права агента = (роль хозяина ∩ роль агента ∩ инструменты агента) ∪ гранты,
выданные этому агенту. Пересечение, не объединение — как и у комнаты (§6).

Практически: я `admin`, но мой агент-читатель новостей не должен уметь
менять настройки организации. Роль агента задаётся при создании и сужает,
а не расширяет.

### 13.4 Роль влияет на режим, а не только на «можно/нельзя»

Роль определяет, в какой режим (§12) попадает пара (действие, ресурс):

- `viewer` в проекте: запись в репозиторий → `deny`.
- `contributor`: деплой → `ask` у `lead`.
- `lead`: деплой → `account` (делает, но отвечает).
- `admin` организации: чтение чужого ресурса → всегда `account`, даже если
  технически он может обойти проверку.

То есть роль — не таблица «да/нет», а таблица «насколько громко».

### 13.5 Чего избегаем

- Не строим произвольный RBAC с деревом разрешений и наследованием — это
  та самая машинерия, из-за которой у Nautilo 65 пакетов.
- Роль не должна быть единственным ответом: три уровня (роль → грант →
  режим) закрывают все обсуждённые сценарии.
- Роль не выдаётся автоматически по факту членства в комнате: комната —
  место встречи данных, а не источник прав (§6).

### 13.6 Пример: продавцы и CRM

«Продавцы видят CRM и могут в неё писать» — эталон роли на общем ресурсе.

- CRM принадлежит организации, не человеку → это роль, а не grant (§13.1).
- Роль `sales`: чтение CRM — `allow`, запись (создать сделку, изменить
  этап, добавить заметку) — `allow`, потому что это их работа.
- Роль даётся **человеку**, а его агент получает её только явным сужением:
  агент продавца может читать CRM, но право писать выдаётся отдельно.
  Иначе автономный фон начинает менять чужие сделки по своей инициативе.
- Опасное подмножество остаётся вне роли: удаление сделок, экспорт всей
  базы контактов, массовая рассылка по CRM → `ask` или `account`, даже для
  `sales`. Размер действия меняет режим: одна заметка ≠ выгрузка 10 000
  контактов.
- Письма в CRM — граница между §13 и §11: карточка сделки принадлежит
  организации, а личный ящик продавца — ему. Агент, собирающий переписку
  по сделке, работает по grant владельца ящика, а не по роли `sales`.

## 14. Требование роли плагином и «хотя бы один участник»

Положение от niquola: плагин может требовать роль — и достаточно, чтобы она
была хотя бы у одного участника.

### 14.1 Что это даёт

Плагин объявляет декларативно: «`crm.write` требует роль `sales`».
В комнате, где есть продавец, агент может писать в CRM, даже если сам
инициатор задачи продавцом не является. Это делает комнату рабочей:
люди собираются не чтобы предъявить права, а чтобы сделать дело, и
роль вносится в комнату тем, у кого она есть.

Формально: комната обладает возможностью `X`, если её обладает хотя бы один
участник. Это **объединение** — и оно противоречит правилу §6 (пересечение).
Противоречие разрешается тем, что это разные вещи:

- **Доступ к данным** (чья почта, чьи файлы) — пересечение, никогда не
  объединение. Нельзя сложить личные данные двух людей.
- **Полномочие действовать** (право писать в CRM) — объединение, потому что
  полномочие не является данными и не утекает из комнаты.

### 14.2 Обязательное условие: полномочие вносит человек, а не комната

Иначе получается «один продавец в чате = все пишут в CRM его руками».
Поэтому:

- Действие выполняется **от имени носителя роли**, явно и видимо:
  в CRM записано «изменил Аня (через агента проекта landing)».
- Носитель роли **присутствует** в этот момент: он в комнате и получает
  событие (§12). Ушёл из комнаты — полномочие ушло с ним.
- Носитель может внести роль в комнату явно («да, в этой комнате мой
  sales-доступ доступен») или требовать `ask` на каждое действие.
  По умолчанию для записи — `ask`, для чтения — `account`.
- Ответственность несёт носитель роли (§12.3), а не тот, кто попросил.
  Это правильный стимул: полномочие одалживают тому, кому доверяют.

### 14.3 Как объявляет плагин

Плагин декларирует для каждой функции:

```
requires: role("sales")        — нужна роль, ищем носителя среди участников
requires: grant("gmail", owner) — нужен grant владельца ресурса (§11)
requires: none                  — общая функция
effect:   read | write | irreversible
```

Ядро (не плагин) решает: кто носитель, есть ли он здесь, какой режим (§12),
нужно ли спрашивать. Плагин не реализует проверки — он только объявляет
свои требования. Это то же правило, что §11.7.3.

### 14.4 Ограничения

- `irreversible`-действия (деньги, удаление, массовая рассылка) не
  одалживаются никогда: их выполняет носитель роли сам, `ask` обязателен.
- Одолженное полномочие не транзитивно: агент, получивший право писать в
  CRM в этой комнате, не может передать его другому агенту или унести в
  другую комнату/задачу.
- У одолженного полномочия есть срок жизни задачи, не сессии.
- Гость из чужого инстанса (§8.1) не может быть носителем роли ни при
  каком уровне доверия.

### 14.5 Явный грант роли проекту

Уточнение от niquola: мало того, что роль есть у участника — нужен ещё
**явный грант этой роли проекту**.

Два разных разрешения, и оба обязательны:

1. **Носитель** (человек, у которого есть роль `sales`) разрешает:
   «мой sales-доступ может использоваться в проекте landing».
2. **Проект** получает от этого возможность `crm.write` — как свойство
   проекта, а не разовое одолжение в чате.

Разница с §14.2 существенная: там полномочие жило, пока носитель в комнате.
Здесь оно становится **стабильной способностью проекта**, что и нужно для
настоящей работы (фоновые задачи, автоматизация, ночные прогоны). Цена —
грант должен быть явным, узким и обозримым:

- Грант роли проекту: `носитель × роль × проект × набор действий × срок`.
  Не «весь sales», а «чтение CRM + создание заметок».
- Виден всем участникам проекта: «этот проект пишет в CRM от имени Ани».
  Скрытых полномочий у проекта нет.
- Отзывается носителем в один клик; отзыв останавливает фоновые задачи,
  которые на нём держались (они не падают молча, а сообщают владельцу).
- Работает и без присутствия носителя — это и есть смысл гранта проекту.
  Поэтому режим по умолчанию для действий по такому гранту — `account`
  (§12): делается сразу, событие идёт носителю роли.
- Уход носителя из организации или снятие роли `sales` автоматически
  аннулирует грант: проект не может пережить источник полномочия.

Итого три уровня, которые нельзя путать:

| Уровень | Кто даёт | Живёт | Пример |
|---|---|---|---|
| роль | организация | пока человек в роли | Аня — `sales` |
| грант роли проекту | носитель роли | до отзыва/срока | landing пишет в CRM от Ани |
| одолженное полномочие в комнате | носитель, присутствуя | пока идёт задача | Аня здесь, агент создал сделку |

## 15. Compute — где выполняется работа

Предложение от niquola: ввести понятие compute — «где развёрнуто».

### 15.1 Зачем это отдельная сущность

До сих пор все разрешения отвечали на вопросы «кто», «над чем» и «на чьём
топливе». Не хватало «где». А «где» определяет реальную границу: код
пользователя (§0.6), `bash`, `eval`, файловая система и браузер изолируются
не проверками, а тем, на какой машине они исполняются.

Compute делает эту границу явной вместо неявной «всё в одном процессе».

### 15.2 Что такое compute

Compute — именованная среда исполнения с собственной изоляцией:

| Поле | Смысл |
|---|---|
| `id`, `label` | `prod-landing`, `nikolai-laptop`, `sandbox-shared` |
| `kind` | `server` (общий контейнер), `personal` (машина человека), `ephemeral` (одноразовая песочница) |
| `owner` | организация, проект или человек |
| `trust` | доверенный / песочница / внешний |
| `capabilities` | что здесь вообще разрешено: `bash`, `eval`, сеть, ФС, браузер |
| `secrets` | какие секреты сюда монтируются (не «все», а список) |
| `db_access` | к каким схемам/базам есть соединение |

Проект (§0.3) = git repo + runtime, и runtime теперь имеет адрес: он
развёрнут на конкретном compute. Агент тоже выполняется на compute —
не обязательно там же, где проект.

### 15.3 Правила

- **Каждое действие имеет compute.** Кортеж разрешения (§11.2) дополняется
  шестым измерением: `кто × от чьего имени × в каком проекте × над чем ×
  на чьём топливе × на каком compute`.
- **Права = пересечение.** Агент может не больше, чем позволяет compute.
  Роль `sales` на песочнице без сети не даёт записи в CRM.
- **Личный compute — граница приватности.** Мой ноутбук, мой Chrome-профиль,
  мой `~`. Чужой агент не исполняется на моём compute никогда, независимо
  от роли и гранта. Он может только прислать запрос и получить ответ (§8).
- **Пользовательский код — на compute с `trust=sandbox`.** Это снимает
  развилку §0.6: функции может писать не только админ, если его код
  выполняется на песочнице с узким `db_access` и без секретов. Админ пишет
  код для доверенного compute, обычный участник — для песочницы.
- **Секреты монтируются в compute, а не глобальны.** Подписка Ани (§0.5)
  доступна на её personal compute и на тех server-compute, куда она её
  явно выдала. Это делает §0.5 реализуемым.
- **Compute виден в аудите.** Событие (§12) содержит, где выполнялось
  действие; «прочитал почту с общего сервера» и «прочитал почту на своём
  ноутбуке» — разные по риску события.

### 15.4 Что это решает из ранее открытого

- Изоляцию ФС и браузера (§9) — без правки `files.resolveSafe`.
- Развилку «пользовательский код только для админов» (§0.6) — через
  `trust`-уровень compute.
- Привязку подписок к людям (§0.5) — через монтирование секретов.
- Вопрос «hot-reload у одного не должен ронять других» — разные compute,
  разные процессы.

### 15.5 Минимальная реализация

Не строим оркестратор. Достаточно:

- таблица `computes` + колонка `compute_id` у агента, проекта и задачи;
- один способ запустить Hyper-воркер на удалённом compute и один канал
  «задача → воркер → результат»;
- по умолчанию один compute (`local`) — текущее поведение не меняется,
  система остаётся работоспособной для одного человека.

### 15.6 Несколько машин, на машине несколько проектов

Уточнение от niquola: машин может быть несколько, и на одной машине —
несколько проектов.

```
org
├── compute: build-1 (server, доверенный)
│     ├── project: landing     (runtime + git)
│     ├── project: crm-sync    (runtime + git)
│     └── project: docs-site
├── compute: gpu-box (server, доверенный, есть GPU)
│     └── project: ml-experiments
├── compute: nikolai-laptop (personal)
│     └── project: hyper-code2   ← личная разработка, чужим сюда нельзя
└── compute: sandbox-1 (ephemeral, изолированный)
      └── любой пользовательский код (§15.3)
```

Отсюда следствия:

- **Отношение многие-ко-многим.** Проект может быть развёрнут на нескольких
  compute (dev на ноутбуке, prod на сервере) — это разные *деплойменты*
  одного проекта, с разными правами и разными секретами. Прод-деплоймент
  landing имеет доступ к боевой CRM, дев-деплоймент — нет.
- **Соседство на одной машине — это риск.** Три проекта на `build-1` делят
  ядро, ФС и сеть. Поэтому: проекты на одном compute должны быть сравнимого
  уровня доверия, у каждого свой каталог и свой системный пользователь,
  а секреты монтируются деплойменту, а не машине. «Машина доверенная»
  не означает «всё на ней видит всё».
- **Планирование.** У задачи есть требования (нужен GPU, нужен доступ к
  боевой БД, нужна сеть наружу), у compute — возможности; ядро выбирает
  подходящий compute или отказывает с внятной причиной. Это не оркестратор,
  а сопоставление меток.
- **Отказ машины.** Compute может быть недоступен: задачи ждут его или
  переносятся, если проект это допускает. Личный ноутбук выключен ночью —
  нормальное состояние, а не ошибка; фоновые задачи, привязанные к нему,
  ждут, а не мигрируют молча на сервер.
- **Учёт.** Расход считается по паре (compute, проект): видно, что ml-эксперименты
  жгут gpu-box, а landing почти ничего не стоит.

Таблицы, которых достаточно: `computes`, `deployments (project × compute ×
env × secrets × permissions)`, `compute_id` у задачи и агента.

### 15.7 Абстракция или нет; шареный Postgres

Вопрос от niquola: стоит ли делать абстракцию? И: Postgres точно может быть
общим.

**Ответ: compute — да, абстракция; storage — отдельная абстракция.**
Их нельзя совмещать, и это главный вывод раздела.

Постулат §0.1 («система живёт в PostgreSQL») означает, что общая база —
это не деталь развёртывания, а несущая конструкция: через неё идут очередь
агентов, сообщения, события, поиск, настройки. Значит:

- **Compute — где исполняется код.** Может быть много, разного доверия,
  изолированы друг от друга.
- **Storage — где лежит состояние.** Обычно ОДИН общий Postgres на
  организацию. Именно он делает платформу целой: агенты с разных машин
  видят одни задачи, одну ленту событий, один аудит.

Отсюда важное следствие: **соединение к общей БД — это и есть главный
capability**, а не второстепенная настройка. Два compute с одинаковым
`bash` и разным доступом к БД различаются принципиально.

Поэтому доступ к общему Postgres выдаётся не машине, а деплойменту, и
сужается средствами самой БД, а не обещаниями в коде:

- отдельная роль Postgres на деплоймент (`landing_prod`, `sandbox_1`);
- `GRANT` только на нужные схемы; песочница не видит `public.local_secrets`,
  `public.oauth_credentials`, чужие плагинные схемы;
- RLS там, где строки одной таблицы принадлежат разным людям;
- пул соединений на деплоймент, чтобы расход и аудит считались по нему.

Это отвечает и на §0.6: пользовательский код на `sandbox` compute физически
не может прочитать чужие секреты — не потому, что мы проверили, а потому
что у его роли нет `GRANT`. Проверка в коде — обещание, `GRANT` — граница.

**Чего НЕ абстрагируем** (иначе получим Nautilo на 65 пакетов):

- не делаем свой оркестратор, планировщик и балансировщик;
- не делаем абстракцию «любой storage-бэкенд» — Postgres конкретен и
  постулирован (§0.1), альтернатив не предусматриваем;
- не делаем сетевую файловую абстракцию — файлы живут на своём compute,
  между compute передаются артефакты, а не смонтированные пути;
- compute описывается метками и возможностями, а не иерархией классов.

Рабочее правило: **compute — множественное, storage — единственное,
секреты — по деплойменту, граница — в `GRANT`.**

### 15.8 «Хотя возможно и не везде» — когда общая БД не годится

Уточнение от niquola: общий Postgres — не универсальное правило.

Общая база хороша для того, что делает организацию организацией, и плоха
для того, что принадлежит одному человеку или одной машине. Разделение:

| Что | Где живёт | Почему |
|---|---|---|
| агенты, задачи, сообщения, события, аудит, роли, гранты, проекты, computes | **общий Postgres** | это и есть платформа; всем нужен один взгляд |
| данные оргплагинов (CRM-зеркало, knowledge, news) | **общий Postgres**, своя схема | ресурс организации (§13.1) |
| личные плагины (почта, здоровье, финансы, личные заметки) | **личное хранилище** владельца | роль не даёт к ним доступа (§13.1); общая база создаёт соблазн и утечку |
| секреты и токены человека | **личное хранилище**, монтируется в деплоймент по гранту | §0.5 |
| рабочие файлы, кэши, сборки, чекауты | **на своём compute**, не в БД | §15.7 |
| внешние системы со своей БД (circleback и т.п.) | **остаются у себя** | зеркалим результат, а не переносим источник |

Три модели соединения, все допустимы:

1. **Общая БД, роль на деплоймент** — основной путь (§15.7).
2. **Отдельная БД для личного** — тот же кластер, своя база; доступ только
   у деплойментов, которым владелец выдал грант.
3. **Внешняя БД** — совсем чужой кластер (плагин со своим бэкендом);
   платформа хранит только ссылку и права, не данные.

Правило, отличающее случай 1 от 2: **если у данных один владелец-человек и
роль организации не должна давать к ним доступа — это отдельная база.**
Всё остальное — общая.

Дополнительно: `ephemeral`-compute может вообще не иметь соединения с
платформенной БД. Он получает вход, возвращает артефакт, результат пишет
вызывающая сторона. Для пользовательского кода (§0.6) это самый честный
режим — нет соединения, нечего утекать.

## 16. Сквозной пример организации

Пример от niquola: в организации есть проекты **invoices**, **landing**,
**hr**, **sales**. На нём проверяем, что модель §11–§15 держится.

Первое, что видно: это НЕ однородный список. Проекты различаются по природе,
и именно различие важно для дизайна.

| Проект | Что это | Главный ресурс | Природа |
|---|---|---|---|
| landing | сайт | git repo + деплой | **продукт**: код, который агент ведёт |
| invoices | выставление и приём счетов | деньги, документы, контрагенты | **процесс**: необратимые действия |
| sales | работа со сделками | CRM организации | **процесс** поверх общего ресурса |
| hr | люди, найм, договоры | персональные данные сотрудников | **процесс** поверх чувствительных данных |

Дальше по каждому — кто участники, какие роли, какие гранты, какие режимы,
на каком compute и из какого хранилища.

### 16.1 landing — продукт

- **Природа**: git repo + runtime. Это тот случай, ради которого Hyper и
  существует: агент пишет код и ведёт продукт.
- **Роли**: `lead` (владелец проекта), `contributor` (правит код),
  `viewer` (смотрит). Дизайнер — `contributor` без права деплоя.
- **Compute**: два деплоймента (§15.6) — `landing@dev` на машине разработчика
  и `landing@prod` на сервере. Секреты прода монтируются только во второй.
- **Режимы** (§12): правка кода в ветке — `allow`; merge в main — `ask` у
  `lead`; деплой в prod — `account` для `lead`, `deny` для `contributor`;
  правка прод-БД руками — `deny` всегда.
- **Личных данных нет** → grant'ы не нужны. Это самый простой случай, и он
  же показывает: большинство проектов не требуют сложной модели доступа.

### 16.2 invoices — необратимые действия

- **Природа**: деньги. Ошибка не откатывается извинением.
- **Ресурсы**: банк/платёжный провайдер, бухгалтерская система, PDF-архив,
  почта для отправки счетов.
- **Роль** `finance`: чтение счетов — `allow`; создание черновика счёта —
  `allow`; **отправка счёта контрагенту — `ask`**; **платёж — `deny` для
  агента вообще** (§14.4: irreversible не одалживается никогда).
- Агент здесь делает 90% работы (собрать данные, посчитать, подготовить
  документ) и не делает последний шаг. Это и есть правильная граница
  автономности: подготовка автономна, обязательство — нет.
- **Compute**: `invoices@prod` на доверенном server-compute, без доступа
  наружу кроме API банка; никакого `bash` для агента этого проекта.
- **Хранилище**: своя схема в общей БД (§15.8) — ресурс организации.
- Отдельно: почта для отправки счетов — это **ящик организации**
  (billing@), а не личный ящик бухгалтера. Роль, а не grant (§13.1).

### 16.3 sales — полномочие взаймы

- **Ресурс**: CRM организации → роль `sales` (§13.6).
- Агент проекта пишет в CRM **по гранту роли проекту** (§14.5): Аня
  разрешила «проект sales пишет в CRM от моего имени, действия: заметки и
  смена этапа, до конца квартала». В CRM видно «изменил: Аня (агент sales)».
- **Переписка по сделке** — граница §11: письма лежат в личных ящиках
  продавцов. Агент получает их только по персональному grant владельца
  ящика, узкому (метка/срок), и отдаёт в проект **выжимку**, а не письма.
- **Режимы**: чтение CRM — `allow`; заметка/этап — `account` (событие идёт
  Ане); массовая рассылка по базе — `ask` даже для `lead`; экспорт всей
  базы контактов — `deny` (§13.6).
- **Компетенция агента**: следить за сделками, готовить письма, поднимать
  забытые. Отправку письма от имени человека — `ask`.

### 16.4 hr — чувствительные данные

- **Природа**: персональные данные сотрудников — самый жёсткий случай.
- Ключевое отличие от sales: здесь личные данные ЛЮДЕЙ ОРГАНИЗАЦИИ лежат в
  **ресурсе организации** (договоры, зарплаты, оценки). То есть роль `hr`
  формально даёт доступ, но §12 требует, чтобы это было громко.
- **Режимы**: чтение анкеты кандидата — `allow`; чтение данных действующего
  сотрудника — `account`, событие идёт **самому сотруднику** (он узнаёт, что
  его личное дело открывали); выгрузка зарплатной ведомости — `ask` у
  владельца организации; удаление — `deny`.
- **Что тут делает агент**: обрабатывает входящие резюме, готовит договоры
  по шаблону, ведёт календарь собеседований. Оценки людей и решения по
  людям — не задача агента.
- **Compute**: отдельный, не тот же, где крутится landing (§15.6:
  соседство проектов на одной машине — риск). Никакого доступа к интернету
  кроме почты и календаря.
- **Хранилище**: отдельная база (§15.8), а не схема в общей: у данных есть
  владельцы-люди, и роль организации не должна открывать их автоматически.

### 16.5 Что этот пример доказывает

1. **Модель не однородна и не должна быть.** landing обходится ролями,
   invoices — режимами, sales — грантами, hr — всем сразу. Единый RBAC
   на всё был бы либо дырявым, либо парализующим.
2. **Главная ось — обратимость, а не секретность.** Что можно откатить —
   `allow`; что видно другим — `account`; что нельзя вернуть — `ask`/`deny`.
3. **Личное не растворяется в организационном.** Почта продавца остаётся его
   почтой внутри проекта sales; личное дело сотрудника порождает событие
   ему самому.
4. **Compute отделяет проекты физически**, а не по договорённости: hr и
   landing не должны жить на одной машине.
5. **Агент автономен в подготовке и несамостоятелен в обязательствах.**
   Это правило одинаково работает для счёта, письма клиенту и договора.

### 16.6 Проект = рантайм + (возможно) база + (возможно) скилл для других

Уточнение от niquola: каждый проект — это рантайм; у него может быть база;
и он может быть **скиллом для других проектов**.

Это важнее, чем кажется: проект перестаёт быть папкой с кодом и становится
**единицей, которую можно вызвать**. Организация превращается не в набор
изолированных проектов, а в граф: одни проекты предоставляют возможности,
другие ими пользуются.

**Три необязательные части проекта:**

| Часть | Обязательна | Смысл |
|---|---|---|
| runtime | да | код проекта исполняется на каком-то compute (§15) |
| storage | нет | своя схема или своя база; проект без состояния — нормально |
| exports | нет | функции, которые проект отдаёт другим проектам |

**Экспорт — это контракт, а не импорт кода.** Проект `invoices` объявляет
`invoices.createDraft({ client, items })`. Проект `sales` вызывает её как
обычную функцию — но исполняется она в рантайме и правах `invoices`,
на его compute, со своими секретами. Это ровно то же правило, что уже есть
в Hyper («никаких cross-import, только `ctx.fns`»), поднятое на уровень
организации.

**Почему так, а не через общую библиотеку:**

- банковский ключ остаётся в `invoices`; `sales` его никогда не видит;
- права проверяются один раз в месте, где живёт ресурс, а не у каждого
  вызывающего;
- `invoices` может менять реализацию, не ломая вызывающих;
- в аудите видно цепочку: «агент sales → invoices.createDraft → банк».

**Права при вызове скилла (ключевое правило):**

Вызов не расширяет права. `sales` получает не полномочия `invoices`,
а только результат разрешённого вызова:

- проект-владелец объявляет, кто может звать: «`invoices.createDraft`
  доступна проектам с ролью `finance` или явно — проекту `sales`»;
- это тот же грант, только субъект — проект, а не человек (§14.5);
- режим наследуется от **вызываемого**: `createDraft` — `allow`,
  `invoices.send` — `ask` у финансов, даже если зовёт `lead` из sales;
- цепочка не транзитивна: если `sales` может звать `invoices.createDraft`,
  это не даёт `sales` звать всё, что может звать `invoices`;
- в событии (§12) сохраняется весь путь вызова, а не последний шаг.

**Примеры скиллов в нашем примере:**

- `invoices` экспортирует `createDraft`, `status(id)` → пользуется `sales`.
- `hr` экспортирует `isEmployee(email)`, `orgChart()` → пользуется `landing`
  (страница «команда») и `sales`. Заметь: экспорт отдаёт **факт**, а не
  доступ к базе hr — это §11.5 на уровне проектов.
- `landing` экспортирует `publishPost(md)` → пользуется маркетинг-агент.
- общий проект `docs` экспортирует поиск по базе знаний всем.

**Граница злоупотребления:** экспорт не должен превращаться в «дай мне
сырые данные». Хороший экспорт возвращает ответ или совершает действие;
плохой — отдаёт таблицу. Правило: если экспортируемая функция возвращает
больше, чем нужно вызывающему для его задачи, она спроектирована неверно.

## 17. Правки по итогам research (02-authorization.md)

Research по 22 первоисточникам (Zanzibar, OpenFGA, SpiceDB, Cedar, Casbin,
Postgres RLS/SET ROLE/PgBouncer, RFC 8693, Entra OBO, Google DWD, GitHub Apps,
Slack, SPIFFE, macaroons/biscuit, sudo, BeyondCorp, ConsoleMe, Teleport)
даёт четыре правки, меняющие реализацию.

### 17.1 Грант = tuple с caveat и обязательным сроком

Схема из OpenFGA Conditions и SpiceDB (миграции 0009/0021):

```
grants(
  subject_type,     -- user | agent | project
  subject_id,
  relation,         -- read | write | call
  resource_type,    -- mailbox | crm | project_export | ...
  resource_id,
  owner_user_id,    -- кто выдал (владелец ресурса)
  caveat jsonb,     -- фильтр: метка, период, лимит объёма
  expires_at timestamptz NOT NULL,   -- обязателен, с индексом
  revoked_at timestamptz,            -- отзыв = не DELETE
  created_by, created_at
)
```

- **Срок обязателен.** Бессрочный грант — ошибка ввода, а не опция.
- **Отзыв не удаляет строку**: аудит (§12) должен видеть, что грант был.
- **Проверка — обычным SQL по (subject, resource)**, без обхода графа.
  Из issues OpenFGA: «перечисли всё доступное» через граф не масштабируется.

### 17.2 Граница — роль в соединении, а не `SET ROLE`

Исправление §15.7:

- `SET ROLE` **обратим**: `RESET ROLE` доступен любому, значит для
  недоверенного кода (§0.6) это не граница, а договорённость.
- PgBouncer не умеет безопасно переключать роли в пуле (issue #75, won't-fix).
- Поэтому: **отдельный пул соединений на деплоймент, роль задана в DSN**,
  плюс `FORCE ROW LEVEL SECURITY` и политика default-deny на таблицах с
  разными владельцами строк.
- Следствие для §15.5: `compute_id` мало, нужен `deployment_id` как единица
  подключения — у него DSN, роль, пул и лимиты.

### 17.3 Attenuation как инвариант ядра

Из macaroons/biscuit: **сужать может кто угодно, расширять — никто.**

- Любая передача полномочия (агент → подагент, проект → проект §16.6,
  инстанс → инстанс §8.1) может только сузить caveat и срок.
- Расширение невозможно технически, а не по соглашению: наследник гранта
  ссылается на родителя, и проверка берёт пересечение цепочки.
- НО хранить как строку в Postgres, а не bearer-токен: bearer невидим в
  использовании, а §12.2 требует записи каждого применения.
- «Sealed» из biscuit = грант, который нельзя делегировать дальше; нужен
  для личных ресурсов (§11): доступ к моей почте не передаётся третьему.

### 17.4 `account` обязан иметь разбор, иначе вырождается в `allow`

Research не нашёл индустриального аналога режима `account` — есть либо JIT
(блокируй и выдай по запросу), либо «разреши и залогируй». Из break-glass
следует условие, без которого наш режим бессмыслен:

- у каждого `account`-события есть **срок разбора** (например, 7 дней);
- неразобранные события копятся и видны владельцу проекта;
- превышение порога неразобранных → действия этого класса автоматически
  понижаются до `ask`, пока разбор не сделан;
- «разбор» = адресат нажал «принято» или «объясни» (§12.2).

Дополнительно из рассмотренных систем:

- **sudo**: «записать» и «уведомить» — разные свойства пары (кто, что),
  а не один флаг. В §12.4 это две колонки, не одна.
- **Teleport**: нельзя одобрить собственный запрос; запрашивают роль, а не
  ресурс. Применимо к §11.4 и §13.4.
- **ConsoleMe**: запрос прав формулируется на понятном языке и превращается
  в узкую политику — хороший паттерн для §11.4 (агент формулирует, ядро
  превращает в caveat).
- **GitHub Apps**: долгое право ≠ короткий токен. Грант живёт месяц, а
  выданный по нему доступ — час. Разделить в §11.3.
- **Google DWD** — антипример ровно нашего §11.1: администратор выдаёт
  приложению доступ к личным данным сотрудников без их участия. Это
  текущее поведение `google.token`, и это надо сломать.

## 18. Правки по итогам research (01-agent-platforms.md)

Изучено 15 платформ (Windmill, n8n, Temporal, Dify, LangGraph Platform,
CrewAI, Codex, Claude Code, Cursor, Zapier, OpenHands, Lindy, Letta,
AutoGen Studio, Devin). Самый близкий аналог — **Windmill**: RLS в Postgres,
путь объекта как ACL, `permissioned_as` на джобе.

### 18.1 Подтверждено (менять не нужно)

- §0.1 граница в БД, а не в коде — у Windmill RLS на 8+ таблицах.
- §11.3 credential принадлежит человеку — n8n end-user credentials.
- §11.6 членство в проекте ≠ доступ к личному — n8n, Codex.
- §15.2 compute как сущность — Temporal namespaces, OpenHands backends.
- §15.3 права = пересечение — Codex: sandbox × approval, две независимые оси.
- §0.5 топливо привязано к человеку — Lindy от противного (общий пул кредитов
  теряет владельца).

### 18.2 Что меняем

1. **`permissioned_as` в очереди.** У Windmill это колонка джоба, по которой
   работает RLS. Наша очередь живёт inline в `agents` — добавить туда «от
   чьего имени выполняется». Без этого §12.3 («у фоновой работы есть
   владелец») не имеет технического носителя.

2. **Комбинирование режимов — минимум, а не приоритет.** Из Claude Code:
   для security-настроек побеждает самое строгое значение из любого
   источника. Итоговый режим = самый строгий среди (роль, grant, политика
   проекта, capabilities compute). Асимметрия: `deny`/`ask` принимаются от
   любого источника немедленно, `allow` — только от доверенного (никогда из
   кода самого проекта).

3. **Секрет имеет не только место, но и фазу жизни.** Из Codex (секреты
   доступны в setup-фазе и удаляются до агентной) и Cursor (build secrets).
   Уточнение §15.3: секрет монтируется на фазу, а не на compute целиком.
   Это самая дешёвая защита от инъекций: в момент чтения недоверенного
   текста секрета в процессе уже нет.

4. **Исходящий фильтр (§8.2) — конкретные места:** результаты вызовов
   инструментов, транскрипт, коммиты и сообщения коммитов. Честная граница
   (Cursor это признаёт про Runtime Secrets): если на том же compute есть
   `bash`/`eval`, редактирование в транскрипте — косметика. Значит `bash` и
   «скрытые от модели секреты» обязаны жить на разных compute.

5. **Approval — приостановка в БД, не блокирующий вызов.** Из Windmill:
   suspend + resume-событие + обязательный таймаут + явная ветка
   «отказано/истекло» + форма по JSON Schema. Ложится на наш `wakeUpWhen`.
   Отличие от Windmill: возобновление проверяет личность одобряющего, а не
   знание секретного URL.

6. **Грант роли проекту (§14.5) держать в git.** У Windmill `extra_perms`
   трекается в исходниках и деплоится через git sync. «Проект пишет в CRM
   от имени Ани» становится ревьюабельным диффом, а не кликом в UI — и
   автоматически выполняется требование «виден всем участникам».

7. **Для секретов нет read-only.** Из CrewAI: у переменных окружения и
   LLM-подключений только Manage / No access. Право «увидеть секрет»
   эквивалентно праву им воспользоваться, шкала viewer/writer неприменима.

8. **Критерий нового compute (§15.6).** Из Temporal: отдельный namespace
   заводят там, где граница арендатора обязана быть границей credential.
   Наше правило: **новый compute нужен ровно там, где нужен отдельный набор
   смонтированных секретов**; иначе достаточно тега/очереди. Их же цифра
   «namespace на арендатора практичен примерно до 50» — аргумент против
   наивного «инстанс на человека».

9. **Дефолт видимости — `only_me`.** Из Dify (где дефолт `ALL_TEAM` —
   ошибка) и CrewAI (где Private — верно). Словарь видимости:
   `only_me / all_team / partial_members`; на подключении — колонки
   `credential_type` (`api-key` | `oauth2`) и `expires_at`.

10. **Показывать, почему действие получило этот режим.** Из Claude Code
    `/status`, называющего выигравший источник настройки. Режим считается
    из четырёх источников, значит человеку нужен ответ «почему `ask`, а не
    `allow`» — иначе модель недиагностируема.

11. **Разделить три разных решения** (из Codex): «плагин установлен»,
    «возможность включена», «полномочие выдано». Отключение возможности не
    деинсталлирует плагин.

### 18.3 Чего нет ни у кого (наша оригинальная часть)

- Режим `account` — везде только можно/нельзя плюс иногда approval.
- Учёт «на чьём топливе» (§0.5); ближайшее — Lindy с общим пулом кредитов,
  то есть противоположное решение.
- Спрашивание разрешения у **владельца ресурса**, а не у инициатора задачи.
- Запрет инициировать запрос разрешения на основании недоверенного текста.
- Связка «роль → грант роли проекту → одолженное полномочие в комнате».

Это одновременно наш вклад и наш риск: образца для подражания нет.

### 18.4 Шаблон подключения vs подключение (из n8n)

Лучшая найденная формулировка нашего §11.3 — n8n End-user credentials.
Забираем модель целиком, она снимает дыру §11.1:

- **Шаблон подключения** принадлежит проекту: «проект sales умеет работать
  с Gmail, вот OAuth-приложение». Создаёт только админ проекта, один раз.
- **Подключение** принадлежит человеку: каждый участник привязывает свой
  аккаунт по этому шаблону. Токен — его, и остаётся его.
- В рантайме аккаунт резолвится по тому, **от чьего имени** идёт работа
  (`permissioned_as`, §18.2.1). Запустил Коля — читается ящик Коли.
  Аккаунта «по умолчанию» не существует в принципе — это прямо закрывает
  §11.7 п.1.
- Админ видит только факт: шаблон есть, к нему привязано N подключений.
  Ни содержимого, ни возможности воспользоваться чужим подключением.
- Fixed и end-user смешиваются в одном сценарии: общий Slack организации —
  fixed, личный календарь — end-user. Следствие для §0.5: **и credential,
  и топливо указываются на уровне шага, а не всей задачи.**

Чего избегаем, тоже из n8n:

- **«Поделиться credential» как операции не существует.** У них получатель
  «может использовать, но не может посмотреть» — иллюзия: имея право
  запустить произвольный workflow с этим credential, он извлекает токен
  тривиально. То же, что §0.6 говорит про код. У нас есть только grant на
  *действие* с фильтром либо собственное подключение человека.
- **Ничто не должно выпадать из модели прав.** В n8n variables и tags
  глобальны мимо RBAC — признано в их же документации. Наш аналог —
  настройки и `$setting_*`; любой класс объектов вне модели прав станет
  каналом утечки.
- **Удаление шаблона не должно убивать чужие подключения.** У них админ
  одним действием обнуляет работу всех. Отзыв — право носителя и точечен.

## 19. Правки по итогам research (03-agent-security-compute.md)

Изучено: OWASP LLM Top 10 2025, «lethal trifecta» (Willison), реальные
инциденты (GitHub MCP / Invariant Labs, EchoLeak, tool poisoning в Cursor),
спецификация MCP, CaMeL (DeepMind), песочницы (E2B, Modal, Daytona, Fly,
Cloudflare Workers, gVisor/Firecracker, Deno permissions), DLP (Presidio,
Google DLP, Nightfall).

### 19.1 Исходящий фильтр (§8.2): канал важнее содержимого

Главная поправка: детектор — второй рубеж, а не первый.

- **Два класса фильтра.** Детерминированный (секреты, токены,
  `database_url`, checksum-идентификаторы) — блокирует, это граница.
  Вероятностный (имена, адреса, мед./фин. сущности, NER) — не блокирует,
  а redact/hash + `account`-событие. Из Presidio (`PatternRecognizer` vs NER)
  и Google DLP (likelihood).
- **Уверенность — измерение политики**: действие = f(уверенность находки,
  доверие получателя), а не только f(доверие).
- **Формат находки**: `{ entity_type, score, start, end }` + действие
  `block|redact|hash|pass` — готовая модель данных для журнала §8.3.
- **Основная защита — не детектор**, а: (а) незамыкание lethal trifecta
  на одном деплойменте, (б) allowlist адресатов, (в) отсутствие секретов
  внутри песочницы.
- **Не фильтровать разметку.** EchoLeak обошёл фильтр markdown-ссылок
  reference-формой. Фильтруем адресата, а не форму ссылки.

### 19.2 Режимы (§12): подтверждения ломаются об усталость

- **Approval fatigue доказан**: GitHub MCP эксплуатировался через «Always
  Allow»; Anthropic измерила −84% промптов при переходе от подтверждений к
  границам. Вывод: **лучший способ уменьшить `ask` — сузить границу, внутри
  которой вопрос не нужен**, а не смягчить режим. Иначе `ask` деградирует в
  `allow` руками человека.
- **`ask` обязан показывать полные аргументы.** Tool poisoning в Cursor
  прошёл, потому что диалог показывал имя инструмента, а ключ был спрятан в
  аргументе. Требование к UI подтверждения.
- **Fail-closed усилить**: было «нет записи — нет ответа», становится
  **«нет записи решения — нет действия»** (из Deno permission broker,
  который убивает процесс при аномалии канала решений).
- **Режим — свойство последовательности, а не только пары.** Из правила
  Invariant «один репозиторий за сессию»: если в текущей задаче уже читался
  личный ресурс владельца X, все исходящие действия и действия над ресурсами
  других владельцев поднимаются в более строгий режим. Это упрощённый
  taint-tracking (идея CaMeL без своего интерпретатора) — дёшево и работает.
- **Событие несёт метку источника данных и хэш набора описаний инструментов.**
  Первое — чтобы `account` был разбираем (что именно могло утечь), второе —
  из-за tool shadowing: видимый список инструментов не отражает, кто реально
  влиял на поведение.

### 19.3 Compute (§15): сеть, прокси, соседство

- **Сеть — отдельное измерение, не флаг.** Из Daytona и Modal:
  `network: { egress: block|cidr|domains|proxy, ingress: none|token }`,
  вход и выход раздельно.
- **Секреты живут не в compute, а в прокси деплоймента.** Из Anthropic
  (Claude Code on the web: креды никогда не внутри песочницы, прокси
  подставляет настоящий токен и проверяет операцию), Cloudflare
  (`globalOutbound`), E2B (секреты metadata-only на control plane).
  Уточнение §15.2/§15.7: деплоймент имеет **право** на секрет, значение
  живёт в прокси. Это же делает реализуемым §18.2.3 (фаза жизни секрета).
- **ФС-изоляция без сетевой бессмысленна** (прямая цитата Anthropic).
  Правило валидации: compute с `bash`/`eval` и без ограничения исходящей
  сети — недопустимая конфигурация при `trust != доверенный`.
- **Соседи не видят друг друга по сети** (Daytona: sandbox-to-sandbox нет
  по умолчанию). Закрывает риск §15.6 про три проекта на одной машине.
- **Создать деплоймент ≠ запустить воркер** (Fly Machines: create дорогой и
  централизованный, start дешёвый и локальный). §15.5 разделяем на две
  операции.
- **Control plane / data plane не смешивать** (E2B): общая БД решает *где*
  и записывает *что*, трафик задачи идёт напрямую к воркеру. Защищает §0.1
  от превращения общей БД в узкое место.
- **Механизм изоляции выбирается по `trust`, а не универсально**: общий
  Postgres не песочим — ограничиваем GRANT'ом; gVisor/microVM только для
  `ephemeral` с пользовательским кодом.
- **`ephemeral` может быть внешним**: E2B (Apache-2.0), Modal, Daytona —
  готовые реализации. Внешний провайдер = ещё один compute с
  `trust: песочница`, а не повод писать свой Firecracker-слой.
- **V8-изолят как дополнительный слой** (Cloudflare Dynamic Worker Loader):
  для Hyper на Bun это реализуемый способ сузить `ctx.fns` для
  пользовательской функции без контейнера — но **не граница между
  пользователями**; §0.6 остаётся в силе.

### 19.4 Честные пробелы

- Независимых замеров точности DLP/PII на выводе LLM в проде не найдено;
  все цифры вендорские или на синтетике. Значит §8.2 не должен опираться
  на детектор как на гарантию.
- Цифры старта песочниц несопоставимы между собой (разные операции).
- Систем с режимом `account` нет ни одной. Подтверждается только его
  мотивация — approval fatigue измерена и уже эксплуатировалась.

## 20. Как совместить «агенты программируют» с мультиюзером

Задача от niquola: сохранить §0.6 (агенты и люди дописывают функции на лету)
и при этом дать многопользовательские доступы. Пример: «я даю поискать по
моей почте и смотрю, что ответит» или «разрешаю читать письма только от
определённого адреса».

### 20.1 Почему это выглядит несовместимым

Если агент пишет код, который исполняется там же, где лежат креды и
соединение с БД, то любая проверка доступа — вежливая просьба: код просто
не станет её вызывать. Отсюда и был вывод §0.6 «писать код = быть админом».

### 20.2 Разрешение: разделить «где пишут код» и «где лежит доступ»

Агент программирует свободно — но его код исполняется в деплойменте, у
которого нет ни токена почты, ни соединения к личной базе. Доступ к моей
почте для него не библиотека, а **вызов наружу**, исполняемый на моей
стороне. Caveat гранта применяется там, где живёт ресурс, а не там, где
живёт код.

Это §16.6 (проект как скилл), распространённое на человека: **человек —
тоже носитель экспортов**.

```
Аня даёт проекту sales доступ к своей почте. Это означает:

  mailbox(anya).search(query)      -- экспорт, caveat: from=partner@acme.com
  mailbox(anya).readFrom(address)  -- экспорт, caveat: from=partner@acme.com

Агент проекта sales пишет любой код, какой хочет:

  const hits = await ctx.fns.mail.search({ owner: "anya", q: "invoice" });
  // ...дальше его собственная логика, функции, разбор

но mail.search исполняется НЕ в его деплойменте: запрос уходит в
деплоймент Ани, там применяется caveat (только письма от partner@acme.com),
там пишется событие, и назад приходит результат — не ящик.
```

Свойства, которые это даёт:

- **Код агента не ограничен.** Он может писать любые функции, свои утилиты,
  парсеры, отчёты. Ограничен не код, а то, до чего он дотягивается.
- **Caveat неподделываем.** Фильтр «только от этого адреса» применяется на
  стороне владельца, в коде, который агент не писал и не может изменить.
- **Нет секрета — нечего украсть.** Токен Gmail никогда не попадает в
  деплоймент агента (§19.3: секреты в прокси, а не в песочнице).
- **Совпадает с тем, что уже есть в Hyper.** Правило «никаких cross-import,
  только `ctx.fns`» превращается в границу процесса: часть `ctx.fns`
  исполняется локально, часть — удалённо, у владельца ресурса.

### 20.3 Два класса кода

| Класс | Где исполняется | Что может | Кто пишет |
|---|---|---|---|
| **Платформенный** | доверенный compute, полное соединение с БД | всё | админы (§0.6) |
| **Проектный** | деплоймент проекта, узкая роль в DSN, без чужих секретов | свои функции + разрешённые экспорты | любой участник и его агенты |

Проектный код — обычный Hyper-код: один файл, одна функция, hot-reload.
Отличие только в том, что его `ctx.fns` собран из: своих функций проекта,
экспортов проектов, которым выдан грант, и экспортов людей, которые выдали
грант. Всё остальное просто не существует в его пространстве имён.

Реализация выбора — по `trust` деплоймента (§19.3): для проектного кода
достаточно отдельного процесса с узкой ролью Postgres; V8-изолят —
дополнительный слой, но не граница между пользователями.

### 20.4 «Я смотрю, что он ответит» — созревание гранта

Твой пример описывает не разовое разрешение, а **процесс доверия**.
Оформляем его как жизненный цикл гранта:

| Стадия | Режим | Что видит владелец | Что видит агент |
|---|---|---|---|
| `preview` | `ask` на каждый вызов | запрос + **результат до передачи** | ничего, пока владелец не отпустит |
| `probation` | `ask`, но пакетно | результаты постфактум, лентой | результат сразу |
| `active` | `account` | событие в ленту (§12) | результат сразу |
| `revoked` | `deny` | история сохранена | ошибка с причиной |

- В `preview` владелец буквально «проверяет, что ответит»: запрос
  выполнился, результат показан **ему**, и он решает — отдать агенту,
  отдать урезанным или отказать. Это дешёвый способ понять, не просит ли
  агент лишнего, до того как что-то утечёт (§6, правило 3).
- Переход `preview → probation → active` — решение владельца, а не
  автоматика по счётчику. Автоматика допустима только вниз: всплеск
  запросов или неразобранные события (§17.4) понижают стадию.
- Стадия — свойство гранта, значит хранится в той же строке (§17.1):
  `stage` рядом с `caveat` и `expires_at`.

### 20.5 Узкий грант как первичная форма

«Читать письма только от определённого адреса» должно быть не исключением,
а нормальным способом выдачи. Практически:

- Владелец выдаёт грант **из своего интерфейса**, формулируя по-человечески
  («письма от partner@acme.com за последний месяц»), система превращает это
  в caveat (паттерн ConsoleMe, §17.4).
- Агент может **попросить** грант, но формулирует его сам и узко: чего
  именно не хватает для текущей задачи. Запрос «дай доступ к почте» без
  фильтра отклоняется как некорректный.
- Запрос, инициированный недоверенным текстом, запрещён (§11.4).
- Узость гранта подкрепляется сроком: грант — на месяц, выданный по нему
  доступ — на минуты (§17.4, GitHub Apps).

### 20.6 Что остаётся честно опасным

- **Админ всё ещё может всё.** Платформенный код не ограничен ничем, кроме
  аудита. Это принимается осознанно: платформу кто-то должен писать.
  Смягчение — не права, а видимость: действия админа над чужими ресурсами
  всегда `account` с событием владельцу (§13.1).
- **Агент с грантом может рассказать лишнее.** Грант ограничивает вход, а
  не выход; выход ограничивает §8.2 и taint-правило §19.2.
- **Проектный код может быть вредоносным** — но в пределах своих грантов.
  Это то же, что вредоносный сотрудник с теми же правами: задача аудита,
  а не изоляции.

## 21. Как это делают другие: «агент пишет код, но не держит доступ»

Проверка §20 по первоисточникам. Индустрия пришла к той же схеме с двух
сторон — и это сильное подтверждение.

### 21.1 Cloudflare Code Mode — ближе всех к §20

Источник: https://developers.cloudflare.com/agents/api-reference/codemode/ ,
https://blog.cloudflare.com/code-mode/

- Модели даётся **один инструмент — «выполни TypeScript»**. Код исполняется
  в V8-изоляте (Dynamic Worker).
- Внутрь песочницы попадают не токены, а **connectors** — RPC-объекты
  (`WorkerEntrypoint`), доступные как глобалы. Код зовёт `gmail.search()`,
  а вызов пересекает границу и исполняется снаружи, где лежат креды.
- `globalOutbound` — единственный выход в сеть, с подстановкой credentials:
  «the agent itself never knows the secret credentials, and therefore cannot
  leak them».
- **Approval встроен в исполнение**: у метода коннектора флаг
  `requiresApproval`; исполнение ставится на паузу, `approve({ executionId })`
  возобновляет его через **replay** (повторный прогон кода с сохранёнными
  результатами уже сделанных вызовов).
- **`rollback({ executionId })`** вызывает `revert` у методов в обратном
  порядке — где `revert` объявлен.
- `search` / `describe` — код находит методы коннекторов и **сохранённые
  сниппеты** по запросу, а не получает их все в контекст.

Для нас это почти один в один §20.2: «человек и проект — носители
экспортов, код агента видит их как `ctx.fns`, исполнение — у владельца».
Hyper на Bun — тот же V8, модель переносится буквально.

**Забираем:**
- approval как **пауза исполнения + replay**, а не блокирующий вызов —
  совпадает с §18.2.5 (Windmill), но точнее: возобновление не
  перезапускает задачу, а доигрывает код с записанными ответами;
- `revert` как **необязательная часть контракта экспорта**: если метод
  объявил `revert`, его режим можно смягчить (обратимо → §16.5 «ось
  обратимости»); без `revert` — строже;
- поиск по экспортам и сохранённым функциям вместо загрузки всего —
  у нас это уже `runtime.docs.search`.

**Не забираем:** изолят как границу между пользователями (§19.3). Cloudflare
сама держит «cordons» — разные процессы по уровню доверия.

### 21.2 Anthropic «Code execution with MCP» — токенизация вместо доступа

Источник: https://www.anthropic.com/engineering/code-execution-with-mcp

- Та же идея: MCP-серверы представлены агенту как **код-API**, агент пишет
  код, фильтрует данные **до** того, как они попадут в модель.
- Ключевое для нас — **privacy-preserving operations**: клиент MCP
  перехватывает результат и **токенизирует PII** до модели. Модель видит
  `[EMAIL_1]`, а при передаче в следующий вызов (например, в Salesforce)
  клиент подставляет настоящее значение по таблице. Данные проходят из
  источника в назначение, **минуя модель**.
- Агенты **сохраняют свой код как переиспользуемые функции** (skills) —
  то, что у Hyper есть по построению.
- Прямо признаётся цена: код агента требует песочницы, лимитов и
  мониторинга.

**Забираем — это новая, четвёртая форма ответа на «проверь, что он
ответит»:**

| Что получает агент | Когда уместно |
|---|---|
| сырые данные | свой ресурс, `allow` |
| выжимка/факт (§11.5) | чужой ресурс, обычный грант |
| **токенизированные данные** | агенту нужно *переложить* данные, а не понять их |
| ничего до решения владельца (§20.4 `preview`) | новый грант |

Токенизация решает частный, но частый случай: «перенеси контакты из
письма в CRM». Агенту не нужно знать адрес — ему нужно, чтобы адрес
оказался в CRM. Тогда адрес ни разу не попадает в контекст, а значит и
в комнату, и в чужой инстанс — это единственный способ **не нарушить
правило «у LLM нет отзыва знания»**, при этом дав агенту работать.

### 21.3 Microsoft Exchange: узкий грант на уровне провайдера

Источник: https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac

- «RBAC for Applications»: приложению даётся `Mail.Read` не на весь
  тенант, а на **Management Scope** — набор ящиков по фильтру (группа,
  атрибут). Ящик вне scope недоступен, даже если scope приложения
  формально шире.
- Это граница на стороне провайдера, а не в коде приложения.

**Вывод:** где провайдер умеет сужать — сужаем там (двойная защита).
Где не умеет — сужаем в нашем экспорте.

### 21.4 Gmail: провайдер НЕ умеет «только от этого адреса»

Источник: https://developers.google.com/workspace/gmail/api/auth/scopes

- Скоупы Gmail — по типу операции (`readonly`, `metadata`, `send`,
  `modify`), а не по содержимому. Фильтра «только письма от X» на уровне
  OAuth **не существует**; `gmail.metadata` отдаёт только заголовки.
- Значит твой пример «читать письма только от определённого email»
  **физически невозможно выразить токеном** Google. Единственное место,
  где этот caveat может жить, — наш экспорт на стороне владельца (§20.2).

Это прямой аргумент за §20: если отдать агенту токен, никакой фильтр по
отправителю уже не удержать. Узкий доступ к почте существует только
как вызов через экспорт.

### 21.5 Итог сравнения

| Вопрос | Cloudflare Code Mode | Anthropic code+MCP | Hyper §20 |
|---|---|---|---|
| Агент пишет код | да, одноразовый | да, может сохранить | да, **становится частью системы** |
| Креды в песочнице | нет, в `globalOutbound` | нет, в MCP-клиенте | нет, у владельца ресурса |
| Узкий фильтр | в коннекторе | в коде клиента | caveat гранта у владельца |
| Approval | пауза + replay | — | пауза + replay + стадии гранта |
| Откат | `revert` у метода | — | `revert` в контракте экспорта |
| Данные мимо модели | — | **токенизация** | берём (§21.2) |
| Многопользовательность | нет, один аккаунт | нет | **владелец ресурса ≠ автор кода** |

Никто из них не решает то, ради чего наш дизайн: **чей это ресурс и кто
отвечает**. Cloudflare и Anthropic изолируют код от кредов одного
пользователя. Мы изолируем код одного человека от ресурсов другого — это
тот же механизм, но с владельцем на каждой стороне вызова.

## 22. Authority — отдельный процесс

Положение от niquola (§0.7): если агент может программировать сам себя, то
часть, которая выдаёт доступы и спрашивает подтверждения, должна находиться
в другом процессе.

### 22.1 Почему это не опция

В сегодняшнем Hyper агент в том же процессе может: выполнить `eval`,
перезагрузить любую функцию, **переопределить её по имени через `.hyper/`**
(этот корень сканируется после `src/` и побеждает), править `src/` и
вызывать hot-reload. Значит `sidebar/approval`, `gh/writeGuard` и любая
будущая проверка гранта в этом процессе — не граница, а соглашение: агент
может заменить `approval.check` на `return true`.

Правило: **то, что ограничивает агента, не может быть кодом, который агент
может изменить.**

### 22.2 Что уходит в authority

| Компонент | Почему не в процессе агента |
|---|---|
| таблицы grants, roles, project grants (§17.1, §14.5) | агент не должен выдать себе грант |
| вычисление режима (§12, §18.2.2) | агент не должен понизить свой режим |
| очередь подтверждений и их решения | агент не должен одобрить себя |
| аудит-журнал (§12.2) | агент не должен стереть или подделать событие |
| секреты и прокси с подстановкой кредов (§19.3) | агент не должен увидеть токен |
| исполнение экспортов владельца (§20.2) | caveat применяется там, где агент не пишет код |

Процесс агента всё это **вызывает**, но не содержит.

### 22.3 Граница держится на Postgres, а не на договорённости

§0.1 делает это дешёвым: общая БД уже есть, нужно только развести роли.

- Роль `authority` — единственная, у кого есть `INSERT/UPDATE` на
  `grants`, `approvals`, `roles`, и `INSERT` на `audit_events`.
- Роль деплоймента агента — `SELECT` на свои гранты (чтобы знать, что
  можно просить), **без права записи**. На `audit_events` — ничего или
  только чтение своих.
- `audit_events` — append-only: ни у одной роли нет `UPDATE/DELETE`,
  включая `authority`. Исправление события — новое событие.
- Роль задаётся в DSN процесса (§17.2), не через `SET ROLE`.

Даже если агент перепишет весь свой код, у его соединения физически нет
права выдать себе грант или стереть след.

### 22.4 Код authority — не hot-reloadable агентом

- Отдельный репозиторий или хотя бы отдельный корень, которого нет ни в
  `src/`, ни в `.hyper/` агентских деплойментов.
- Изменения — через ревью человеком и деплой, а не через `repl.load`.
- Маленький и скучный: это единственная часть системы, где мы
  **отказываемся** от «программируй на лету». Всё остальное — можно.

### 22.5 Канал подтверждения — вне досягаемости агента

Отдельного процесса мало, если человек подтверждает в интерфейсе, до
которого агент дотягивается. А он дотягивается: у Hyper есть browser-плагин,
управляющий **реальным Chrome пользователя с его сессиями**. Агент может
открыть страницу подтверждения и нажать «Разрешить» сам.

Поэтому:

- UI подтверждений отдаёт authority, на **отдельном origin** (свой
  домен/порт), не через HTTP-роуты процесса агента.
- Этот origin недоступен browser-плагину агента: другой профиль Chrome
  или явный блок-лист в плагине — и второе недостаточно само по себе,
  потому что плагин тоже код агента.
- Для `ask` над чужими ресурсами и для `irreversible` — **второй фактор,
  который агент не может нажать**: passkey/WebAuthn (требует присутствия
  человека) или push в мобильное приложение.
- Диалог показывает полные аргументы вызова (§19.2) — и формирует их
  authority из самого запроса, а не текст, который прислал агент.
  Иначе агент нарисует безобидное описание к опасному вызову.

### 22.6 Протокол «агент → authority»

Минимальный, чтобы authority оставался маленьким:

```
request(action, resource, args, justification, task_id)
  → { decision: allow | account | ask | deny, grant_id?, approval_id?, reason }

wait(approval_id)            -- пауза исполнения (§21.1: pause + replay)
call_export(owner, fn, args) -- исполнение экспорта у владельца (§20.2)
```

- Агент не присылает «я имею право» — только «я хочу». Решение и его
  причина (§18.2.10) всегда от authority.
- `justification` пишется в аудит как есть и **не влияет на решение**:
  иначе это канал для prompt injection в authority.
- Authority не использует LLM для принятия решения. Решение — детерминированная
  функция от (роль, грант, стадия, режим проекта, compute, taint задачи).
  LLM в authority — это тот же уязвимый агент, только с большими правами.

### 22.7 Что это меняет в порядке работ (§10)

Это становится **первым шагом**, раньше мультиюзера: даже для одного
человека сегодняшний approval внутри процесса агента не защищает ни от
инъекции, ни от собственной ошибки агента. Минимальная версия:

1. Отдельный процесс `authority` с ролью Postgres и таблицами
   `grants / approvals / audit_events`.
2. Роль агента без права записи в эти таблицы.
3. Страница подтверждений на отдельном origin + passkey.
4. `sidebar/approval` и `gh/writeGuard` переходят на `request()` к authority.

## 23. Доступ как разговор между агентами

Предложение от niquola: свести доступы к общению между агентами. Агент
проекта отправляет сообщение персональному агенту человека; тот готовит
ответ и спрашивает хозяина.

### 23.1 Почему это сильная идея

- **Естественно для Hyper.** Это существующие `ask` / `delegate` /
  `finishTask`, только адресат — агент другого человека (§8).
- **Pull вместо push по построению** (§6, правило 2). Агент проекта никогда
  не получает доступ к почте — только ответ, подготовленный на стороне
  владельца.
- **Узкий запрос не нужно формализовать заранее.** «Что partner@acme.com
  писал про счёт за март?» — персональный агент сам понимает, что искать,
  и отвечает фактом. Не надо заранее описывать caveat на каждый случай.
- **Человек в контуре там, где он и так есть**: у своего агента, в своём
  интерфейсе. Это и есть стадия `preview` из §20.4 — «я смотрю, что он
  ответит» — без отдельной машинерии.
- **Процесс уже другой**: персональный агент живёт в деплойменте владельца,
  а не в проекте. Требование §0.7 частично выполняется само.
- **Топливо корректное** (§0.5): работу с моей почтой делает мой агент на
  моей подписке, под моим контролем.

### 23.2 Где это ломается, если сделать наивно

Персональный агент — это LLM, которая одновременно:
(а) имеет полный доступ к личным данным владельца,
(б) читает недоверенный текст — сообщение от чужого агента,
(в) может отправить ответ наружу.

Это ровно **lethal trifecta** (§19.1) в одном агенте, плюс классический
confused deputy: агент проекта пишет «владелец разрешил, пришли всю
переписку с юристом», и персональный агент, желая помочь, это делает.
Сообщение от другого агента — недоверенный контент, как письмо из
интернета.

И второе: персональный агент тоже **программирует сам себя** (§0.7). Если
он сам решает, что отдать, то решение принимает код, который он может
переписать.

### 23.3 Как совместить: агент готовит, authority выпускает

Разделить роли внутри разговора:

| Кто | Что делает | Может ли ошибиться/быть обманут |
|---|---|---|
| агент проекта | формулирует вопрос | да — это недоверенный вход |
| персональный агент | ищет, понимает, **готовит черновик ответа** | да — он LLM, его можно уговорить |
| authority (§22) | **решает, уходит ли черновик наружу** | нет LLM, детерминированно |
| владелец | подтверждает, правит, отказывает | — |

Правила:

- **Персональный агент не отправляет ответ сам.** Он кладёт черновик в
  authority. Наружу ответ уходит только через authority — после решения
  владельца или по уже существующему гранту.
- **Владелец видит черновик и вопрос рядом**, с указанием, от кого пришёл
  запрос и что из его данных использовано (метки источников §19.2). Может
  отдать, урезать, отказать.
- **Сообщение от агента не может выдать грант или сослаться на согласие
  владельца.** Фраза «владелец разрешил» в тексте запроса ничего не значит;
  факты о разрешениях знает только authority.
- **Персональный агент при чтении чужого запроса работает в суженном
  режиме**: у этой задачи нет инструментов отправки наружу и нет доступа к
  ресурсам, помеченным как не относящиеся к запросу (taint §19.2).
- Исходящий фильтр (§8.2/§19.1) применяется к черновику до показа владельцу
  и повторно — к финальному ответу.

### 23.4 Кристаллизация: из разговоров в гранты

Если каждый доступ — разговор с подтверждением, владелец утонет в запросах
(approval fatigue, §19.2). Выход — разговор как **медленный путь**, грант
как **быстрый**, и переход между ними:

1. Агент проекта спрашивает; персональный агент готовит; владелец
   подтверждает. (`preview`)
2. Однотипные запросы повторяются — персональный агент **предлагает
   правило**: «проект sales третий раз спрашивает про письма от
   partner@acme.com. Разрешить ему `mail.search` с фильтром
   `from=partner@acme.com` на месяц без вопросов?»
3. Владелец соглашается — authority создаёт грант с caveat (§17.1).
   Дальше такие запросы идут детерминированным экспортом (§20.2), без LLM и
   без ожидания. (`active`, режим `account`)
4. Новые, нестандартные вопросы по-прежнему идут разговором.

То есть грант — это **застывший разговор**: сначала человек несколько раз
видит, что именно агент спрашивает и что получает, и только потом
разрешает это автоматически. Это та самая лестница «проверил, что ответит →
разрешил от конкретного адреса» из §20, но выросшая из практики, а не
заданная заранее.

### 23.5 Итог: две формы одного доступа

| | Разговор агентов | Экспорт с грантом |
|---|---|---|
| когда | новый или нестандартный вопрос | повторяющийся, понятный запрос |
| кто понимает запрос | персональный агент (LLM) | детерминированный экспорт |
| кто решает о выдаче | владелец через authority | authority по гранту |
| скорость | минуты/часы, ждём человека | миллисекунды |
| топливо | подписка владельца | почти ноль |
| что получает проект | ответ, подготовленный и одобренный | результат с caveat |
| риск | инъекция в персонального агента | узость фильтра |

Обе формы проходят через authority. Разговор не заменяет §22 — он
становится **основным пользовательским интерфейсом** к нему.

## 24. Identity: у каждого агента и проекта — адрес

Положение от niquola (§0.8): каждого агента и проект привязать к условному
email-ящику, то есть дать всем identity.

### 24.1 Что это даёт

- **Единое пространство субъектов.** Человек, агент, проект — все
  адресуемы одинаково: `anya@acme`, `sales@acme`, `reader.anya@acme`.
  Грант (§17.1), роль (§13), аудит (§12), разговор (§23) ссылаются на один
  тип идентификатора вместо `user_id` / `agent_id` / `project_id` вразнобой.
- **Разговор агентов (§23) получает естественную адресацию.** Агент проекта
  пишет `anya.personal@acme` — это то же, что написать человеку.
- **Федерация (§8) бесплатно.** Домен в адресе = инстанс/организация:
  `sales@acme` и `sales@partner` различимы без отдельного реестра имён.
  Это та же идея, что SPIFFE ID (§17), но в понятной людям форме.
- **Читаемый аудит.** «`sales@acme` прочитал письма `anya@acme` по гранту
  от `anya@acme`» понятно без справочника.
- **Вход из внешнего мира.** Если адрес настоящий, проекту можно просто
  написать письмо: `invoices@acme` принимает счета, `hr@acme` — резюме.
  Проект становится участником переписки так же, как сотрудник.

### 24.2 Схема имён

| Субъект | Адрес | Пример |
|---|---|---|
| человек | `<name>@<org>` | `anya@acme` |
| персональный агент человека | `<name>.<agent>@<org>` | `anya.assistant@acme` |
| проект | `<project>@<org>` | `sales@acme` |
| агент проекта | `<project>.<agent>@<org>` | `sales.followup@acme` |
| деплоймент (для машинного аудита) | `<project>+<env>@<org>` | `landing+prod@acme` |

Владелец субъекта выводится из адреса и подтверждается authority, а не
угадывается по строке: `anya.assistant@acme` принадлежит `anya@acme`,
`sales.followup@acme` — проекту `sales@acme`.

### 24.3 Три вещи, которые нельзя смешивать

Адрес удобен, но за ним три разных понятия:

1. **Identity** — кто это. Выдаётся authority, неизменна, одна на субъект.
2. **Ящик** — куда приходят сообщения. Может быть внутренним (сообщения
   между агентами) и/или настоящим почтовым.
3. **Полномочия** — что этот субъект может. Живут в грантах и ролях (§13,
   §17), **не в адресе**.

Главное правило: **identity ≠ authority**. Наличие адреса `invoices@acme`
не даёт права платить; письмо «от» `anya@acme` не является согласием Ани.

### 24.4 Опасности настоящего ящика

Если адрес принимает внешнюю почту, у агента появляется открытый входной
канал для недоверенного текста — главный вектор инъекций (§19.1).

- **Внешнее письмо — недоверенный контент**, всегда. Оно может стать задачей
  для агента проекта, но не может: выдать грант, сослаться на разрешение,
  запросить доступ к чужим ресурсам (§11.4), изменить режим.
- **`From:` подделывается.** Внутренние сообщения (агент↔агент, §23)
  идентифицируются **подписью authority**, а не заголовком. Письмо, которое
  пришло снаружи с `From: anya@acme`, для системы — внешнее письмо.
  Внешняя почта проверяется DKIM/SPF/DMARC, но даже прошедшая проверку
  остаётся недоверенным входом, а не командой.
- **Агент с настоящим ящиком наружу = канал эксфильтрации.** Отправка
  внешнего письма — всегда исходящий фильтр (§19.1) и по умолчанию `ask`
  для личных данных. Внутренняя адресация и внешняя отправка — разные
  возможности, выдаются раздельно.
- **Taint (§19.2):** задача, начатая внешним письмом, помечена как
  «внешний недоверенный источник» с самого начала, и все её исходящие
  действия идут в более строгом режиме.

### 24.5 Реализация по минимуму

- Таблица `principals(address, kind: human|agent|project|deployment,
  owner_address, created_by, disabled_at)` — в зоне authority (§22).
- Все остальные таблицы ссылаются на `address` как на субъект.
- Внутренняя «почта» — это сообщения в общем Postgres с подписью authority;
  SMTP не нужен, пока нет внешнего входа.
- Внешний ящик — опционально на субъект: входящее письмо превращается в
  сообщение с меткой `external`, исходящее идёт через authority.
- Отключение субъекта (`disabled_at`) мгновенно гасит все его гранты и
  фоновые задачи — один рычаг вместо обхода таблиц.

## 25. Hyper как распределённая система

Тема от niquola: подумать о системе как о распределённой в целом.

### 25.1 Что уже распределено, даже если так не называлось

После §15–§24 система фактически распределена на трёх уровнях:

| Уровень | Что распределено | Что общее |
|---|---|---|
| внутри организации | compute и деплойменты (§15) | один Postgres (§0.1), одна authority (§22) |
| между людьми | персональные агенты и личные хранилища (§15.8, §23) | адреса (§24) |
| между организациями | инстансы с доменами (`@acme`, `@partner`) | только протокол сообщений (§8) |

Вопрос не «делать ли распределённую систему», а **где проходят швы и что
через них передаётся**.

### 25.2 Главный принцип: authority живёт у ресурса

Каждый ресурс имеет ровно одного владельца, и право на него проверяется
**только на стороне владельца**. Из этого следует почти всё остальное:

- **Не нужен глобальный консенсус о правах.** Нет общей таблицы грантов
  на весь мир, которую надо синхронизировать; каждая authority отвечает за
  свои ресурсы.
- **Отзыв мгновенный.** Грант проверяется при каждом вызове у владельца
  (§20.2), поэтому отзыв не надо «распространять» — следующий вызов просто
  получит отказ. Это главный выигрыш pull-модели перед раздачей токенов.
- **Личные данные не реплицируются.** Между узлами ходят вопросы и ответы,
  а не таблицы. Нечего синхронизировать — нечему расходиться и утекать.

Это модель email и акторов, а не модель общей базы: каждый узел — хозяин
своего состояния, общение — сообщениями.

### 25.3 Сообщения: store-and-forward, как почта

Раз у всех есть адрес (§24), транспорт между узлами — асинхронные
сообщения с доставкой «когда получатель доступен»:

- **Outbox/inbox в Postgres.** Сообщение пишется в `outbox` в той же
  транзакции, что и действие (transactional outbox); отдельный доставщик
  отправляет его и повторяет до подтверждения. Получатель пишет в `inbox`
  идемпотентно по `message_id`.
- **Доставка «хотя бы раз» + идемпотентность** вместо «ровно раз».
  Повтор сообщения не должен повторять действие.
- **Отсутствие узла — нормальное состояние.** Ноутбук Ани выключен ночью —
  запрос ждёт в очереди, как письмо на сервере. Фоновая задача проекта не
  падает, а переходит в ожидание с понятной причиной (§15.6).
- **Порядок — только внутри разговора.** Глобального порядка событий нет и
  не нужно; у каждого разговора/задачи своя последовательность.
- **Ответ — тоже сообщение**, с `in_reply_to`. Это то же, что
  `ask`/`finishTask` сегодня, только через границу узла.

### 25.4 Комната живёт в одном доме

Открытый вопрос из §8 («комната у одного хозяина или реплицируется») —
закрываем: **у комнаты один дом** (инстанс её создателя или проекта).
Участники с других узлов читают и пишут через сообщения этому дому.

Почему не репликация: Matrix реплицирует состояние комнаты по всем
серверам и расплачивается сложным алгоритмом разрешения конфликтов
состояния. Нам это не нужно: у комнаты есть владелец, и он же — источник
истины. Цена — если дом недоступен, комната недоступна; для рабочих комнат
организации это приемлемо.

### 25.5 Обнаружение и доверие между узлами

- **Адрес → узел** через домен: `.well-known` на домене организации отдаёт
  endpoint и публичный ключ authority (как DKIM/SPF для почты).
- **Подпись сообщений ключом authority** (§24.4) — единственный способ
  узнать отправителя; заголовок `from` не доказывает ничего.
- **Уровень доверия к чужому домену** — лестница §8.1, по умолчанию
  `unknown`. Доверие к домену не переносится на все его адреса автоматически
  для личных ресурсов.
- **Ротация ключей и отзыв узла** — через тот же `.well-known`; отключённый
  адрес (§24.5) перестаёт приниматься.

### 25.6 Внутри организации: не распределять состояние

Внутри одной организации соблазн — шардировать и реплицировать. Не делаем:

- **Один primary Postgres** на организацию; реплики только на чтение.
  Никакого multi-master — это конфликты записи, которых у нас сейчас нет.
- **Compute распределён, состояние — нет** (§15.7). Воркеры на разных
  машинах берут задачи из общей очереди (атомарный `UPDATE…RETURNING`,
  как сегодня в `agents`), пишут результат обратно.
- **Трафик данных идёт мимо БД** (§19.3, E2B): БД решает *где* и хранит
  *что*, большие артефакты передаются между compute напрямую.
- **Код распределяется через git** — он уже распределённый. Деплоймент
  тянет ревизию, а не получает её из БД.

### 25.7 Что делает распределённость трудной (честно)

- **Частичные отказы.** Вызов экспорта у владельца (§20.2) может уйти и
  не вернуться. Нужны таймауты, идемпотентные ключи и явный статус
  «неизвестно, выполнилось ли» — особенно для `irreversible` (§14.4),
  где повтор = двойной платёж.
- **Долгие ожидания.** Задача, ждущая подтверждения человека (§22) или
  выключенный ноутбук, может висеть сутки. Durable execution и replay
  (§21.1) обязательны, а не опциональны.
- **Отладка.** Цепочка «агент sales → anya.assistant → authority Ани →
  gmail» идёт через несколько узлов. Нужен сквозной `trace_id` в каждом
  сообщении и событии аудита, иначе причину отказа не найти.
- **Версии протокола.** Узлы обновляются независимо; формат сообщений
  версионируется с первого дня.

### 25.8 Прототипы, на которые стоит посмотреть

Не исследовано глубоко, отмечено для research:

- **Email / SMTP** — store-and-forward, адреса, DKIM; ближе всего к §24.
- **Matrix** — федеративные комнаты; урок про стоимость репликации
  состояния (§25.4).
- **ActivityPub** — inbox/outbox акторов между серверами.
- **AT Protocol (Bluesky)** — персональные серверы данных (PDS) и
  переносимая identity; близко к «личное хранилище у человека» (§15.8).
- **Erlang/OTP, акторы** — сообщения, супервизия, «let it crash».
- **Temporal** — durable execution для долгих ожиданий (§25.7).

### 25.9 У проекта есть compute и DNS, на котором доступны его сервисы

Уточнение от niquola: проект должен иметь compute и DNS-имя, по которому
доступны его сервисы.

Это замыкает §0.3 («проект = runtime + git») до полноценной единицы:

```
проект sales
├── identity        sales@acme                  (§24)  — кто
├── git             git.acme/sales               (§0.3) — код
├── storage         schema sales / db sales      (§15.8)— состояние
├── deployments     sales+prod на build-1        (§15.6)— где исполняется
│                   sales+dev  на ноутбуке Ани
└── DNS             sales.acme.internal          — где доступны сервисы
                    ├── api.sales.acme.internal       (HTTP/RPC экспорты §16.6)
                    ├── app.sales.acme.internal       (UI проекта)
                    └── prod / dev поддомены на деплоймент
```

**Почему DNS, а не просто compute:**

- **Адрес сервиса отвязан от машины.** Проект переезжает с `build-1` на
  `build-2` — DNS-имя остаётся, вызывающие не меняются. Compute — деталь
  размещения, DNS — контракт.
- **Экспорты проекта (§16.6) становятся сетевыми адресами.**
  `invoices.createDraft` = вызов на `api.invoices.acme.internal`. Это
  естественный транспорт для «исполняется в рантайме владельца».
- **Identity и сеть совпадают по имени.** `sales@acme` (кто) и
  `sales.acme.internal` (где) выводятся друг из друга; сертификат сервиса
  выпускается на имя проекта (как SPIFFE, §17).
- **Внешние сервисы проекта.** landing — это и есть проект с публичным
  DNS (`acme.com`). Разница между внутренним и публичным — в том, где
  опубликовано имя, а не в устройстве проекта.

**Правила:**

- **DNS-имя выдаёт authority** вместе с identity (§24.5), а не сам проект.
  Проект не может занять чужое имя или имя с более высоким доверием.
- **По умолчанию имя внутреннее** (`*.acme.internal`), доступно только из
  сети организации. Публикация наружу — отдельное решение с `ask` у владельца
  организации: это меняет поверхность атаки.
- **Каждый деплоймент — своё имя** (`prod.sales…`, `dev.sales…`), чтобы
  dev по ошибке не ходил в prod-экспорты другого проекта.
- **Вход в сервис проекта — только с identity.** Сеть отвечает «можно
  достучаться», authority — «можно ли вызвать» (mTLS или подписанный токен
  с identity вызывающего). DNS — адрес, а не разрешение (как §24.3:
  identity ≠ authority).
- **Соседние проекты на одной машине по сети изолированы** (§19.3):
  достучаться до соседа можно только через его DNS-имя и его проверку,
  не через localhost.

**Минимальная реализация:** внутренний DNS-сервер (или просто записи в
общем Postgres + резолвер), reverse-proxy на каждом compute, который
маршрутизирует имя деплоймента на локальный порт и проверяет identity
вызывающего. Для публичного — стандартные записи у регистратора и TLS.
Это то, что у Hyper уже частично есть в плагине `tunnel` (FRP для
публикации локальных портов).

## 26. Упрощённый деплой: одна защищённая виртуалка

Идея от niquola: начать не с кластера, а с простой secure-виртуалки.

### 26.1 Почему это правильный первый шаг

Весь дизайн (§15–§25) сводится к нескольким границам: процесс authority
отдельно от агентов (§22), роль Postgres на деплоймент (§17.2), секреты
вне агентского процесса (§19.3), закрытая сеть (§25.9). **Всё это есть в
одном Linux-хосте** без Kubernetes: пользователи ОС, systemd, роли
Postgres, файрвол. Кластер добавляет масштаб, но не добавляет границ,
которых нет на одной машине.

Одна VM = один compute (§15) с несколькими деплойментами. Когда понадобится
второй — модель уже готова к этому.

### 26.2 Состав

```
VM (Debian, e2-standard-4, без публичного IP)
├── tailscale            — единственный вход; сеть организации (есть headscale)
├── caddy                — TLS + маршрутизация по именам *.hyper.<tailnet>
├── postgres (local)     — один кластер, роли на деплоймент, FORCE RLS
├── hyper-authority      — unix-user `authority`, свой DSN, свой origin
│                          гранты, approvals, audit, секреты, прокси
├── hyper@sales          — unix-user `p-sales`,   DSN роли `sales`
├── hyper@landing        — unix-user `p-landing`, DSN роли `landing`
├── hyper@anya           — персональный агент Ани, своя роль и своя база
└── backup               — pg_dump + restic в GCS, по таймеру
```

### 26.3 Как границы дизайна ложатся на одну машину

| Требование | Реализация на VM |
|---|---|
| authority в другом процессе (§22) | отдельный systemd-юнит под своим unix-пользователем; код в `/opt/authority`, агентам — только чтение/нет доступа |
| роль в DSN, не `SET ROLE` (§17.2) | у каждого юнита свой `DATABASE_URL` из systemd-credentials |
| audit append-only (§22.3) | `GRANT INSERT` только роли `authority`, без `UPDATE/DELETE` ни у кого |
| секреты не в агенте (§19.3) | `systemd-creds` / файлы 0600 владельца `authority`; агенты ходят через прокси authority |
| изоляция проектов (§15.6) | unix-user на деплоймент + systemd hardening: `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`, `ReadWritePaths=/srv/<project>` |
| сеть между соседями (§19.3) | агенты слушают unix-сокеты или `127.0.0.1` с проверкой identity в caddy; `IPAddressDeny` на юнитах, исходящая сеть — только через прокси |
| ФС без сети бессмысленна (§19.3) | исходящий трафик агентов через egress-прокси authority с allowlist доменов |
| DNS проекта (§25.9) | `sales.hyper.<tailnet>` → caddy → сокет юнита `hyper@sales` |
| UI подтверждений вне досягаемости агента (§22.5) | отдельное имя `approve.hyper.<tailnet>`, passkey; браузер агентов (headless Chrome) не имеет маршрута на это имя |
| пользовательский код (§0.6, `ephemeral`) | на первом этапе — нет; позже bubblewrap/gVisor на той же VM или внешний E2B |

### 26.4 Защита самой машины

- **Нет публичного IP.** Вход только через tailnet; SSH — через Tailscale
  SSH / OS Login, без паролей.
- **Автообновления** безопасности (`unattended-upgrades`), минимальный
  набор пакетов.
- **Shielded VM + диск с CMEK**, snapshot-расписание в GCP.
- **Отдельный сервис-аккаунт GCP** с правами только на бакет бэкапов.
- **Журналы** authority и системные — во внешнее хранилище, чтобы
  скомпрометированный агент не мог их стереть локально.

### 26.5 Что сознательно упрощаем

- Один Postgres на той же машине — никакого HA. Защита — бэкап и быстрое
  восстановление (restic + проверенный restore-скрипт), а не реплики.
- Один compute — `trust: доверенный`. Недоверенный код не исполняем, пока
  не добавлена песочница.
- Федерации (§8, §25) нет: одна организация, один домен.
- Браузер для агентов — headless Chrome с отдельным профилем на
  деплоймент; личные браузерные сессии людей на сервер не переносятся.

### 26.6 Путь роста

1. **Одна VM** — всё выше. Доказывает модель прав на реальных проектах.
2. **Вторая VM** для недоверенного/тяжёлого (`ephemeral`, GPU) — это второй
   compute (§15), без смены архитектуры.
3. **Перенос в кластер** (samurai-backoffice уже имеет CNPG, Traefik,
   external-secrets, Flux) — когда упрёмся в ресурсы или нужен HA.
   Юниты становятся подами, unix-user → ServiceAccount, systemd-creds →
   external-secrets. Границы те же.

Критерий, что VM достаточно: authority, роли Postgres и прокси работают, и
агент проекта не может ни прочитать чужой секрет, ни выдать себе грант, ни
открыть страницу подтверждения — проверяется тестом, а не обещанием.

## 27. Tailnet как сетевой слой организации

Интерес от niquola к tailnet. Факты о текущей инфраструктуре (проверено):

- В кластере `samurai-backoffice` в namespace `vpn` работает **headscale
  v0.29.3** (открытая реализация control-server Tailscale) с UI headplane,
  доступен по `ep.cs.aidbox.dev`. Управляется Flux (GitOps).
- Политика ACL уже описывает людей **по их Google Workspace email**
  (`niquola@health-samurai.io`) и **группам** (`group:cto`, `group:devops`,
  `group:core`, `group:atomic`, …) и даёт доступ к тегам узлов
  (`tag:hetzner`). DNS-записи — ConfigMap `headscale-dns` (сейчас пуст).
- Мак, с которого работает Hyper, при этом в **личном** tailnet на
  tailscale.com (`niquola@gmail.com`, `tail32c871.ts.net`), а не в
  корпоративном headscale.

### 27.1 Почему tailnet подходит почти идеально

Tailnet уже делает то, что наш дизайн требует от сети, и делает это так же,
как мы решили про права:

| Наше требование | Что даёт tailnet |
|---|---|
| identity = email (§24) | каждый узел принадлежит пользователю с email Google Workspace |
| сеть по identity, а не по IP (§25.9) | ACL пишутся по людям, группам и тегам |
| роли (§13) | `group:*` в ACL — это и есть роли на уровне сети |
| узел ≠ человек (§15) | теги (`tag:hyper-authority`, `tag:hyper-project`) для машин и сервисов |
| DNS проекта (§25.9) | MagicDNS + свои записи |
| нет публичного IP (§26.4) | весь вход через WireGuard-туннель |
| distributed, узлы уходят и возвращаются (§25.3) | ноутбук вне сети — штатное состояние tailnet |
| политика в git, ревью человеком (§18.2.6, §22.4) | ACL headscale уже во Flux |

И главное: **вызывающему сервису известно, кто пришёл** — `tailscale whois`
по IP возвращает пользователя и узел. Это даёт identity на входе без
собственной аутентификации.

### 27.2 Как положить Hyper в tailnet

- VM (§26) регистрируется в корпоративном headscale с тегом
  `tag:hyper`. У неё нет публичного IP — только tailnet.
- Каждый деплоймент получает **свой узел** в tailnet через `tsnet`
  (Tailscale как библиотека в процессе) или отдельный sidecar:
  `sales.hyper`, `landing.hyper`, `authority.hyper`, `approve.hyper`.
  Тогда адрес проекта в сети = его identity (§24, §25.9), и ACL пишутся
  прямо по проектам.
- ACL:
  ```
  люди группы sales  → sales.hyper:443
  tag:hyper-project  → authority.hyper:api      (запрос прав)
  tag:hyper-project  ✗ approve.hyper            (UI подтверждений — только людям)
  tag:hyper-project  ✗ другие tag:hyper-project (соседи не видят друг друга)
  люди               → approve.hyper:443        (+ passkey поверх)
  ```
- Входящий запрос в сервис проекта проходит через `whois`: сервис знает
  человека или узел-вызывающий и передаёт его authority как субъект.

### 27.3 Что tailnet НЕ решает (граница из §24.3 и §22)

- **Сетевая доступность ≠ право.** ACL отвечает «можно ли достучаться до
  порта». Можно ли прочитать почту Ани — решает authority по гранту.
  Tailnet — первый рубеж и источник identity, не замена авторизации.
- **Агент на моём ноутбуке ходит с моей identity.** Персональный агент,
  запущенный на ноутбуке niquola, в tailnet выглядит как niquola. Поэтому
  для агентов нужны **отдельные узлы с тегами** (tsnet на деплоймент), а
  не общий узел машины — иначе агент получает сетевые права человека.
- **Внутри одной VM tailnet не разделяет процессы.** Если все деплойменты
  используют один `tailscaled` хоста, для сети они один узел. Отсюда
  рекомендация tsnet/sidecar на деплоймент, либо проверка identity в caddy
  по unix-сокету.
- **Control-server = корень доверия.** Кто администрирует headscale, тот
  может выдать узлу любой тег и открыть любой ACL. Headscale должен
  администрироваться вне досягаемости агентов (как authority, §22.4):
  агенты не получают API-ключ headscale никогда.

### 27.4 Что нужно решить

- Hyper использует **корпоративный headscale** (identity =
  `@health-samurai.io`, есть группы) — да, это правильная сеть для
  организационной платформы; личный tailnet `niquola@gmail.com` остаётся
  для личного compute.
- Как соединить личный compute (ноутбук с персональным агентом) с
  корпоративной сетью: ноутбук в обоих tailnet не может быть одновременно —
  клиент Tailscale держит одно активное подключение. Варианты: личный
  агент как отдельный tsnet-узел в корпоративном headscale, или федерация
  через сообщения (§25.3) без общей сети.

## 28. Hetzner как площадка для VM

Вопрос от niquola: будет ли секьюрно поднять в Hetzner? (В ACL headscale уже
есть `tag:hetzner` — машины там у организации есть.)

### 28.1 Ответ: да, при тех же условиях, что и в GCP

Модель §26 не опирается на облачные сервисы безопасности: граница — это
unix-пользователи, роли Postgres, authority отдельным процессом, отсутствие
публичного входа (tailnet, §27). Всё это одинаково работает на любом Linux.
Hetzner безопасен ровно настолько, насколько мы сами закроем машину.

### 28.2 Что в Hetzner нужно сделать руками (в GCP было «из коробки»)

| GCP | Hetzner — чем заменить |
|---|---|
| нет публичного IP, вход через IAP/OS Login | Hetzner Cloud Firewall: **закрыть всё входящее**, кроме UDP для WireGuard; SSH только через tailnet |
| Shielded VM, CMEK | полнодисковое шифрование (LUKS) с ключом, который не лежит на диске — иначе при изъятии/снятии диска данные читаемы |
| сервис-аккаунт для бэкапов | отдельный S3-ключ (Hetzner Object Storage или GCS) только на запись в бэкап-бакет; restic шифрует сам |
| snapshots по расписанию | Hetzner snapshots + restic во **внешнее** хранилище (не в тот же аккаунт) |
| audit logs облака | логи authority и системы — наружу (в Grafana/Loki кластера или отдельно) |
| управление ключами | секреты не на диске открытым текстом: `systemd-creds` с TPM нет → шифровать ключом, подаваемым при старте |

### 28.3 Риски, специфичные для Hetzner

- **Доступ к аккаунту Hetzner = доступ к машине.** Консоль позволяет
  сбросить root, смонтировать диск в rescue, снять снапшот. Обязательно:
  2FA на всех логинах Hetzner, минимум людей с доступом, отдельный проект
  под Hyper. Без LUKS rescue-режим даёт прочитать базу целиком.
- **Юрисдикция и данные.** Германия/Финляндия, ЕС, GDPR — для личных
  данных сотрудников (§16.4 hr) это скорее плюс. Для данных клиентов
  (медицинские, если попадут) — проверить договоры: DPA с Hetzner есть,
  а вот требования HIPAA/US-клиентов могут требовать US-региона
  (у Hetzner есть Ashburn/Hillsboro).
- **Нет managed-сервисов.** Postgres, бэкапы, обновления, мониторинг —
  на нас. Для одной VM это приемлемо, если восстановление проверено
  (§26.5: проверенный restore, а не «бэкап есть»).
- **Dedicated vs Cloud.** Cloud-VM — проще firewall и снапшоты;
  dedicated (Robot) — дешевле на мощность, но firewall/rescue устроены
  иначе и шифрование диска критичнее.

### 28.4 Вывод

Hetzner Cloud VM + LUKS + Cloud Firewall «всё закрыто» + вход только через
корпоративный headscale + restic во внешнее хранилище + 2FA на аккаунте —
это уровень безопасности не ниже одиночной GCP-VM, дешевле в разы.
Главное отличие — ответственность: то, что GCP делает сам, в Hetzner
должно быть в нашем скрипте разворачивания и проверяться тестом.

## 29. Минимальный путь от сегодняшнего Hyper

Вопрос от niquola: что конкретно сделать, чтобы добавить multiuser в Hyper.

### 29.1 Что уже есть в коде и пригодится

- `agents.visibility` (`nav | team | hidden`) — зачаток видимости.
- `agents.workspace_dir` — у агента уже свой рабочий каталог.
- `settings.scope_type / scope_id` — место для scope=user.
- `secrets.*` с namespace — место для владельца секрета.
- **`sharedAgent.publish / delegate / result`** — уже работающий механизм
  «опубликовать агента как носителя контекста и поручить ему задачу».
  Это прямой зародыш §23 (доступ как разговор агентов): не хватает
  identity запросившего, подтверждения владельца и выпуска ответа
  через authority.

### 29.2 Две фазы, а не одна

Пока у агента есть `bash` и `eval` в общем процессе (§0.6), второй человек —
это второй root. Поэтому multiuser делится на две фазы с разной целью:

**Фаза A — «команда доверенных людей» (дни, не месяцы).**
Цель: несколько человек работают в одном Hyper, видят свои и общие
агенты, у каждого действия есть автор. Безопасности между людьми нет —
как у общего сервера, где все sudo. Это честно и уже полезно.

1. **Вход по identity.** Вместо общего пароля (`src/auth`) — identity
   из tailnet (`tailscale whois` по IP запроса, §27) или Google OAuth
   домена `health-samurai.io`. Таблица `principals` (§24.5).
2. **Владелец у агента.** Колонки `agents.owner` и `agents.permissioned_as`
   (§18.2.1); новый агент получает автора из сессии.
3. **Видимость.** Список агентов фильтруется: мои + `team` моего проекта +
   опубликованные. Остальные — не в навигации (но технически доступны,
   это фаза A).
4. **Автор в событиях.** Каждое сообщение и действие несёт `actor` —
   чтобы в общей ленте было видно, кто что сделал.
5. **Секреты и подписки по владельцу** (§0.5): `secrets`, `oauth_credentials`,
   LLM-ключи получают `owner`; агент использует подписку своего владельца.
   Google-плагин перестаёт выбирать аккаунт по умолчанию (§11.7).
6. **sharedAgent → разговор с персональным агентом** (§23): в `delegate`
   записывается identity запросившего, а ответ владельцу показывается
   до отправки (стадия `preview`, §20.4).

**Фаза B — «граница между людьми» (после A).**
Цель: человек, которому не доверяют как root, не может достать чужое.

7. **Authority отдельным процессом** (§22): гранты, подтверждения, аудит,
   секреты и прокси. `sidebar/approval` и `gh/writeGuard` переходят на
   запрос к authority.
8. **Роль Postgres на деплоймент** (§17.2) и unix-пользователь на проект
   на VM (§26) — у агентских процессов нет прав писать гранты и видеть
   чужие секреты.
9. **Проектный код в своём деплойменте** (§20.3): чужие ресурсы — только
   через экспорты владельца.
10. **Страница подтверждений на отдельном имени + passkey** (§22.5).

### 29.3 Самый короткий первый шаг

Фаза A, пункты 1–3, на одной VM в корпоративном tailnet: Hyper узнаёт
человека по `tailscale whois`, записывает его как владельца агента и
показывает каждому своё. Никакой новой инфраструктуры, кроме таблицы
`principals` и двух колонок в `agents`. Это сразу даёт «Hyper для
команды» и проверяет модель identity (§24) на живых людях — до того,
как строить authority.

## 30. Шаг 0: просто user & auth

Решение от niquola: начать с минимума — в Hyper появляются пользователи и вход.
Без прав, грантов, authority и изоляции. Всё остальное в этом документе
строится поверх этого шага.

### 30.1 Что есть сейчас (проверено в коде)

- `src/auth`: один общий пароль (`auth.password`), `POST /auth/login`
  выпускает подписанную куку с захардкоженными claims
  `{ sub: "password-user", name: "Hyper user", role: "owner" }`.
- `src/procs/auth`: подпись/проверка токена (`sign`, `verify`,
  `authenticate`, `cookie`) уже общие, и в комментариях упомянуты
  magic link и SSO от manager — то есть механизм сессий готов к разным
  способам входа, не хватает только настоящего пользователя.
- `$middleware.ts` уже кладёт результат `authenticate` в `session.user`.

То есть «пользователь» в коде уже есть как форма, просто всегда один и тот же.

### 30.2 Что добавляем

1. **Таблица `users`**: `id`, `email` (unique), `name`, `password_hash`
   (Bun.password, argon2id), `role` (`owner | member`), `created_at`,
   `disabled_at`.
2. **Логин по email + паролю**: `POST /auth/login` ищет пользователя,
   проверяет хеш, выпускает куку с `sub = users.id`, `name`, `role`.
   Отключённый пользователь не входит; `authenticate` проверяет
   `disabled_at` при каждом запросе, чтобы отключение действовало сразу.
3. **Миграция с общего пароля**: при первом запуске, если `users` пуст,
   создаётся `owner` с текущим `auth.password` — существующий вход не
   ломается.
4. **Управление пользователями**: owner добавляет/отключает участников
   (страница или функции `auth.createUser`, `auth.disableUser`,
   `auth.setPassword`).
5. **Автор у агента**: колонка `agents.created_by` заполняется из
   `session.user` при создании. Пока только запись — фильтрации нет.
6. **Кто сейчас в системе**: `GET /auth/session` возвращает настоящего
   пользователя; UI показывает имя.

### 30.3 Сознательно НЕ делаем на этом шаге

- Видимость: все пользователи видят всех агентов (как сейчас).
- Права: все участники — фактически админы, у агентов есть `bash`/`eval`.
  Это «команда доверенных людей» (§29, фаза A) — записать явно в UI и
  документации, чтобы не создавать ложного ощущения изоляции.
- Секреты, подписки, гранты, роли проектов — позже.
- SSO/tailnet-identity — позже; способ входа заменяем, не трогая модель
  `users`.

### 30.4 Почему это правильный первый шаг

- Даёт identity (§24) самую простую форму — строку в `users` с email.
- Всё последующее (владелец агента §29, `permissioned_as` §18.2.1,
  подписки по владельцу §0.5, аудит §12) требует «кто» — и получает его.
- Объём — одна миграция, правка трёх роутов и одного `authenticate`.

### 30.5 Уточнение: несколько пользователей из коробки

Уточнение от niquola: multiuser — не режим и не миграция, а поведение
Hyper по умолчанию.

- **Нет отдельного «однопользовательского режима».** Таблица `users`
  есть всегда; один человек — это просто система с одним пользователем.
  Код никогда не проверяет «включён ли multiuser».
- **Первый запуск = создание первого owner.** Пустая `users` → экран
  setup: email, имя, пароль. Если задан `HYPER_PASSWORD` (старые
  установки) — owner создаётся из него автоматически, и дальше вход
  идёт по email.
- **Общий пароль уходит.** `auth.password` остаётся только как источник
  для первого owner; входа «по одному паролю без email» больше нет.
- **Добавить человека — штатное действие:** owner создаёт пользователя
  или отправляет приглашение (одноразовая ссылка, механизм `kind`-токенов
  в `procs.auth` для этого уже есть — magic link).
- **Локальная разработка.** Сейчас без пароля auth выключен целиком.
  Из коробки это меняется: вход нужен всегда, но запрос с `127.0.0.1`
  при единственном пользователе может автоматически входить как owner —
  чтобы локальный запуск не стал тяжелее. Решение открытое.
- **Каждое действие с автором с первого дня**: `agents.created_by`,
  автор сообщения — потому что пользователи есть всегда, а не «когда
  включат».

### 30.6 Чего не хватает, чтобы пользователи были «из коробки»

Инвентаризация по коду и живой схеме (53 456 агентов в `agents`).

**A. Нет самого пользователя**

| Чего нет | Где сейчас | Что нужно |
|---|---|---|
| таблицы людей | — | `users` (§30.2) |
| входа по email | `auth/$route_login_POST` выпускает `sub:"password-user"` всем | поиск пользователя, `sub = users.id` |
| setup первого запуска | без пароля auth выключен целиком | экран создания owner / авто-owner из `HYPER_PASSWORD` |
| приглашений | `procs.auth` умеет `kind`-токены (magic link), но нет роута | `auth.invite` → одноразовая ссылка |
| проверки отключения | `authenticate` верит подписи 30 дней | сверять `users.disabled_at` на каждом запросе |

**B. Нет автора в данных**

Живая схема: ни в одной таблице ядра нет «кто».

| Таблица | Колонки сейчас | Чего не хватает |
|---|---|---|
| `agents` | … `visibility`, `workspace_dir` | `created_by`, позже `owner` |
| `messages` | `role`, `content`, … | **`author`** — кто из людей написал user-сообщение; в общем агенте иначе неясно, кто говорил |
| `events` | `type`, `payload` | `actor` |
| `settings` | `scope_type/scope_id` есть | использовать `scope_type='user'` |
| `local_secrets`, `oauth_credentials` | `namespace`, `account` | `owner` (§0.5) |
| `attachments`, `cron_tasks` | — | `created_by` |

**C. Нет пользователя в путях, которые идут в обход HTTP-сессии**

- **Мобильное API** (`src/api/$route_mobile_v1_*`, ~20 роутов) — проходит
  через тот же middleware, но ответы и список агентов не знают о
  пользователе; push-уведомления и «прочитано» (`read_POST`) сейчас общие
  на всех — **«прочитано» должно стать per-user**.
- **SSE-лента событий** (`procs/events/$route__GET`, `procs/events/join`) —
  единственное место, которое уже читает `session.user`; нужно проверить,
  что подписка несёт пользователя.
- **REPL** (`procs/repl`) — отдельный токен `kind:"repl"` из
  `.runtime/repl-token`, по сути root машины. Правильно для владельца
  машины, но у REPL нет «кто»; вызовы из REPL должны идти от имени
  конкретного пользователя (owner).
- **Фоновые задачи** (`workerLoop`, cron, wake, watch) — выполняются без
  сессии. Для «из коробки» минимум: агент помнит `created_by`, и фоновые
  действия пишутся от его имени.
- **Sidebar / browser-extension мост** (`/sidebar/api`, `/sidebar/approve`)
  — своя bearer-авторизация в обход пользователей; нужно привязать
  pairing к пользователю.

**D. Нет разделения в UI**

- Шапка без «кто я» и без выхода.
- Список агентов — один на всех (фильтрация — позже, но хотя бы
  «созданные мной» как вкладка).
- Страница управления пользователями для owner.
- Явная надпись «все участники — доверенные, изоляции нет» (§30.3).

**E. Нет per-user настроек, которые люди сразу заметят**

- модель по умолчанию, ключи/подписки LLM (§0.4–§0.5) — у каждого своя
  подписка Claude/Codex;
- `status_line`, тема, язык;
- Google-аккаунт по умолчанию (§11.7) — у каждого свой ящик.

**Порядок:** A целиком → `agents.created_by` и `messages.author` из B →
«прочитано» per-user и `session.user` в SSE из C → «кто я» и страница
пользователей из D. E и остальное B — следующим шагом.

## 31. Решение: пользователи и вход в Hyper (спецификация)

Статус: **только дизайн, в коде не реализовано.** Пробная реализация была
сделана и полностью откачена; её уроки учтены ниже (§31.9).

### 31.1 Цель

Hyper из коробки знает, **кто** работает: несколько людей входят каждый под
собой, у каждого действия есть автор. Это фундамент для всего остального
(§11–§30), но сам по себе шаг **не даёт изоляции**: все пользователи —
доверенные, у агентов по-прежнему `bash`/`eval` (§30.3).

### 31.2 Что входит и что нет

| Входит | Не входит |
|---|---|
| таблица пользователей, вход по email + паролю | видимость агентов по владельцу |
| первый owner через setup | права, гранты, роли проектов |
| отключение пользователя, действующее сразу | секреты и подписки по владельцу |
| автор у новых агентов | автор у сообщений, per-user «прочитано» |
| совместимость со старым общим паролем | SSO, tailnet-identity, приглашения по ссылке |

### 31.3 Модель данных

```sql
CREATE TABLE users (
  id            TEXT PRIMARY KEY,          -- 'u_' + 12 символов
  email         TEXT NOT NULL,             -- уникален без учёта регистра
  name          TEXT NOT NULL,
  password_hash TEXT NOT NULL,             -- argon2id через Bun.password
  role          TEXT NOT NULL DEFAULT 'member' CHECK (role IN ('owner','member')),
  created_at    BIGINT NOT NULL,
  updated_at    BIGINT NOT NULL,
  disabled_at   BIGINT                     -- не null = отключён
);
CREATE UNIQUE INDEX users_email_lower_idx ON users (lower(email));
ALTER TABLE agents ADD COLUMN created_by TEXT;  -- users.id, пишется один раз
```

Одна миграция в `src/auth`. Обратимая (`down` удаляет колонку и таблицу).

### 31.4 Функции (`src/auth`)

| Функция | Что делает |
|---|---|
| `auth.createUser({ email, name, password, role? })` | создаёт пользователя, хранит только хеш, email уникален |
| `auth.verifyUser({ email, password })` | активный пользователь или `null` (не раскрывает, что именно не так) |
| `auth.getUser({ id })` | активный пользователь по id или `null` |
| `auth.listUsers({ includeDisabled? })` | список без хешей |
| `auth.setUserDisabled({ email, disabled })` | отключить/включить; нельзя отключить последнего owner |
| `auth.currentUser({ req })` | пользователь запроса: подпись куки **и** проверка строки в `users` |
| `auth.enabled({})` | нужен ли вход: есть пользователи или задан старый пароль |

Механизм подписи и кук (`procs.auth.sign/verify/authenticate/cookie`) не
меняется: в токен кладутся `sub = users.id`, `name`, `email`, `role`.

### 31.5 Потоки

**Первый запуск / переход со старого пароля.**
1. Пока `users` пуст — всё как сейчас: вход по общему паролю.
2. `/auth/setup` доступен только при пустой `users`. Если задан старый
   пароль, форма требует его (иначе чужой через туннель станет owner).
3. Создаётся owner, он сразу входит. С этого момента общий пароль
   **перестаёт работать**, а старые сессии «password-user» недействительны.

**Вход.** `/auth/login`: email + пароль → `verifyUser` → кука на 30 дней.
Неверные данные — одинаковый ответ и задержка 250 мс.

**Каждый запрос.** Middleware вызывает `auth.currentUser`: проверка подписи
**плюс** чтение строки `users`. Отключённый пользователь теряет доступ на
следующем запросе, не дожидаясь истечения куки.

**Автор агента.** `session.save` пишет `created_by` из `session.user.id`
только при вставке (не в `ON CONFLICT UPDATE`). Для старого общего пароля
и фоновых агентов — `NULL`, а не `'password-user'`.

### 31.6 Затрагиваемые файлы

- новые: `src/auth/$migration_…_users.ts`, `User.ts`, `createUser.ts`,
  `verifyUser.ts`, `getUser.ts`, `listUsers.ts`, `setUserDisabled.ts`,
  `currentUser.ts`, `enabled.ts`, `page.ts`, `$route_setup_GET.ts`,
  `$route_setup_POST.ts`;
- правка: `src/$middleware.ts` (гейт по `auth.enabled`, пользователь через
  `auth.currentUser`, `/auth/setup` публичный), `$route_login_GET/POST.ts`,
  `$route_session_GET.ts`, `src/session/save.ts` (одна колонка);
- тесты: `$middleware.test.ts` + тесты на функции пользователей.

### 31.7 Что сломается у клиентов — решить ДО включения

- **iPhone-приложение** отправляет в `/auth/login` только `password`.
  После setup оно войти не сможет. Нужно: либо обновить приложение (поле
  email), либо до обновления принимать вход без email **только** если
  пользователь один. Решение — до включения.
- **Все текущие сессии** разлогинятся в момент создания owner (браузер,
  телефон). Предупредить в форме setup.
- **Sidebar/browser-extension мост** и **REPL** работают со своими токенами
  мимо пользователей — не ломаются, но и автора не получают (§30.6 C).
- **Фоновые задачи** (worker, cron, wake) — без сессии, `created_by = NULL`.

### 31.8 Проверка перед включением

1. Миграция применяется и откатывается на копии базы.
2. Сценарии: вход по паролю при пустой `users`; setup требует старый
   пароль; после setup старый пароль и старые куки не работают; неверный
   пароль / чужой email / отключённый — один и тот же отказ; последнего
   owner отключить нельзя; `created_by` пишется один раз.
3. iPhone-приложение входит (после решения §31.7).
4. Смоук живого Hyper: страница входа, API без куки = 401, сохранение агента.

### 31.9 Уроки пробной реализации

- Работала на живом инстансе с первого раза, миграция и откат прошли без
  потерь (53 456 агентов, `created_by` не заполнялся).
- `session/save.ts` и `ctx_ns.d.ts` уже содержали чужие незакоммиченные
  правки — изменения делать отдельной веткой/worktree, не в рабочем `main`.
- Для старого пароля нельзя писать `created_by = 'password-user'` — это не
  пользователь; писать `NULL`.
- Порядок отката важен: сначала код (иначе middleware обращается к
  удалённой таблице), потом база.
- **Процесс:** реализация — только по явному «делай», в отдельной ветке,
  с включением через setup в конце, а не при деплое.

## 32. Решение: первый этап — multiuser без security

Решение от niquola: пока делаем multiuser **без безопасности**. Все
пользователи — доверенная команда; изоляции между людьми нет и не
заявляется. Слой 3 (authority, роли Postgres, unix-пользователи, passkey —
§22, §26) откладывается.

**Что входит в этап:**

1. **Пользователи и вход** — §31 целиком.
2. **Автор везде, где он виден людям:**
   - `agents.created_by` (§31);
   - `messages.author` — кто из людей написал user-сообщение;
   - `events.actor` — кто совершил действие.
3. **Своё у каждого:**
   - «прочитано» per-user (сейчас общее);
   - вкладка «мои агенты» в навигации (общий список остаётся);
   - «кто я» и выход в шапке;
   - страница пользователей для owner (добавить / отключить).
4. **Личные настройки** через `settings.scope_type='user'`:
   модель по умолчанию, свои LLM-ключи и подписки (§0.5), свой
   Google-аккаунт (плагин перестаёт брать аккаунт по умолчанию).
5. **Владелец у фоновой работы:** worker/cron/wake выполняются от имени
   `created_by` агента — чтобы использовалась подписка и аккаунт того,
   кто агента создал.

**Что сознательно НЕ делаем на этапе:** видимость и права по владельцу,
гранты, подтверждения, аудит как отдельный процесс, изоляция ФС/процессов,
`permissioned_as` как граница. `bash`/`eval` у агентов остаются.

**Обязательно:** явная надпись в UI — «все участники доверенные,
изоляции между пользователями нет».

## 33. Решение: два режима — single user и multiuser

Решение от niquola: нужны оба режима. **Это отменяет §30.5** («нет отдельного
однопользовательского режима»).

### 33.1 Главный принцип: режим меняет вход и интерфейс, а не модель данных

Чтобы не плодить `if (multiuser)` по всему коду, данные устроены одинаково
в обоих режимах:

- таблица `users` есть всегда; в single-режиме в ней ровно один
  пользователь — **неявный owner** (`id = 'owner'`), создаётся миграцией;
- `created_by`, `messages.author`, `events.actor`, `settings` с
  `scope_type='user'` заполняются всегда — в single это просто `owner`;
- фоновые задачи работают от имени `created_by` — в single это всегда owner.

Режим влияет только на три места: **как входить**, **что показывать в UI**
и **можно ли добавлять людей**.

### 33.2 Чем режимы отличаются

| | single | multi |
|---|---|---|
| вход | как сейчас: без входа локально или общий пароль (`auth.password`) | email + пароль (§31) |
| кто в сессии | всегда неявный `owner` | конкретный пользователь из `users` |
| пользователи | один, нельзя добавить | owner добавляет/отключает |
| UI | без «кто я», без «мои агенты», без авторов у сообщений | «кто я», выход, «мои агенты», авторы, страница пользователей |
| личные настройки | глобальные = настройки owner | у каждого свои |
| надпись «изоляции нет» | не нужна | обязательна (§32) |

### 33.3 Как задаётся режим

- Настройка `auth.mode = single | multi`, env `HYPER_MODE`.
- **По умолчанию `single`** — текущие установки и локальная разработка
  не меняются вообще.
- Режим читается один раз на запрос в middleware и кладётся в сессию;
  остальной код смотрит на `session.user`, а не на режим.

### 33.4 Переходы между режимами

**single → multi** (основной сценарий):
1. Owner включает `multi` и проходит setup: указывает свой email, имя и
   пароль.
2. Неявный `owner` **становится этим пользователем** — не создаётся новый.
   Все существующие агенты, сообщения и настройки автоматически принадлежат
   ему, миграции данных не нужно.
3. Общий пароль перестаёт работать, старые сессии разлогиниваются
   (предупреждение в setup, §31.7).

**multi → single:**
- Разрешено, только если активный пользователь **один** (остальные
  отключены). Он становится неявным owner, вход снова по общему паролю.
- Данные других пользователей не удаляются: их агенты остаются в базе с
  их `created_by`, просто войти под ними нельзя. При обратном переключении
  в `multi` они снова доступны.
- Если активных пользователей больше одного — переключение запрещено с
  понятной ошибкой: «сначала отключите остальных».

### 33.5 Что это меняет в §31–§32

- §31.3: миграция создаёт `users` **и** строку `owner` (без email и пароля,
  `role='owner'`); `password_hash` и `email` допускают NULL только для неё.
- §31.5: setup — это не «создание первого owner», а **перевод в multi**:
  заполнение email/пароля у существующего `owner`.
- §31.7: iPhone-приложение в single-режиме продолжает работать без
  изменений; проблема появляется только при переходе в multi.
- §32 целиком относится к режиму `multi`; в `single` из него остаётся
  только запись автора (всегда `owner`).

## 34. Решение: single = multi с одним пользователем

Уточнение от niquola: single mode — это просто система с одним пользователем.
**Заменяет §33** (отдельная настройка режима не нужна). По сути возвращает
идею §30.5, но с правилами входа, которые не ломают текущий Hyper.

### 34.1 Режима как настройки нет — он вычисляется

- Код всегда работает с `users` и `session.user`. Одна ветка кода.
- «Режим» = число активных пользователей:
  - **1** → интерфейс как сейчас (без «кто я», авторов, «мои агенты»);
  - **2+** → появляются «кто я», авторы у сообщений, «мои агенты»,
    страница пользователей, надпись «изоляции нет».
- Нет `auth.mode`, нет `HYPER_MODE`, нет переходов «single ↔ multi» как
  отдельной операции.

### 34.2 Вход зависит от того, что задано у пользователя

| Состояние | Вход |
|---|---|
| один пользователь без пароля | вход не нужен (как сейчас локально без `auth.password`) |
| один пользователь с паролем | только пароль, email не спрашиваем (как сейчас с общим паролем; iPhone работает без изменений) |
| 2+ пользователя | email + пароль |

Миграция: создаётся один пользователь `owner`; если задан `auth.password`,
он становится паролем этого пользователя. Для текущих установок снаружи
не меняется ничего.

### 34.3 Добавление второго человека

- Owner добавляет пользователя (страница пользователей или функция).
- Условие: у owner должен быть email и пароль — иначе при входе нельзя
  различить людей. Если их нет, система просит заполнить.
- С этого момента вход требует email; iPhone-приложению нужно поле email
  (§31.7) — это единственное место, где что-то ломается, и только у тех,
  кто добавил второго человека.
- Отключили всех, кроме одного, → интерфейс и вход снова «как у одного».
  Данные отключённых остаются.

### 34.4 Что это даёт по сравнению с §33

- Нет настройки режима, нет запрета переключения, нет «неявного owner»
  как особого случая — owner обычная строка в `users`.
- Все данные (`created_by`, `author`, `actor`) с первого дня указывают на
  реального пользователя; второй человек просто добавляется.
- Единственная развилка в коде — «сколько активных пользователей» в
  middleware и в шаблонах UI.

### 34.5 Первый пользователь — с настоящим именем, не `owner`

Уточнение от niquola: пользователя можно сразу назвать по имени.

- Миграция не создаёт безликого `owner`. Имя первого пользователя берётся
  из явного источника, по порядку:
  1. `HYPER_USER` / `HYPER_USER_EMAIL` (env) — если заданы;
  2. иначе — `git config user.name` / `user.email` рабочей машины;
  3. иначе — имя ОС-пользователя (`os.userInfo().username`).
- `id` — стабильный slug от имени/email (`niquola`), а не `owner`:
  он попадает в `created_by`, `author`, `actor` и в будущий адрес
  identity (§24: `niquola@<org>`).
- `owner` — это **роль** (`role='owner'`), а не имя пользователя.
- Переименовать можно в любой момент (имя и email — обычные поля);
  `id` не меняется, поэтому ссылки в данных не ломаются.
- Старые строки (агенты, сообщения до миграции) получают `id` этого
  первого пользователя.

### 34.6 Имя задаётся при настройке

Уточнение от niquola: пользователя добавляют при настройке, а не выводят
автоматически. **Заменяет автоматический выбор имени из §34.5.**

- **Первый запуск / первое открытие после обновления** показывает короткий
  шаг настройки: имя (обязательно), email и пароль (необязательно).
- Значения из `HYPER_USER`, `git config`, имени ОС — только **подсказка**
  в поле, а не решение за человека.
- **Существующие установки:** до завершения настройки Hyper работает как
  сейчас (без входа или по общему паролю), миграция создаёт пользователя
  с временным `id` и пометкой «не настроен». После настройки `id` и имя
  фиксируются, старые агенты и сообщения переходят на него.
- Если общий пароль уже задан, настройка переносит его в пароль
  пользователя — вход для тебя и для iPhone не меняется.
- В той же настройке можно сразу **добавить остальных людей** (имя +
  email + пароль); тогда вход сразу становится «email + пароль» (§34.2).
- Для серверного развёртывания без браузера — тот же шаг через env
  (`HYPER_USER`, `HYPER_USER_EMAIL`, `HYPER_PASSWORD`), без экрана.

### 34.7 Источник правды — база; env только для первичной настройки

Уточнение от niquola: пользователи хранятся в базе, env — иногда, как способ
задать их.

- **Источник правды — таблица `users`.** Всё чтение (вход, автор, UI) идёт
  только из базы. Env никогда не читается на каждом запросе.
- **Env — только seed.** `HYPER_USER`, `HYPER_USER_EMAIL`, `HYPER_PASSWORD`
  применяются **один раз**, при старте, если в `users` ещё нет ни одного
  настроенного пользователя. После этого env игнорируется.
- **Env не перезаписывает базу.** Если пользователь уже есть, изменение env
  ничего не меняет — правки идут через UI или функции (`auth.createUser`,
  смена имени/пароля). Иначе рестарт с устаревшим env молча откатывал бы
  пароль.
- **Пароль из env сразу хешируется** и хранится только хеш; сам env можно
  убрать после первого запуска.
- **Для серверного развёртывания** этого достаточно: первый старт с env
  создаёт пользователя, дальше всё в базе.
- Старый `auth.password` (настройка/`HYPER_PASSWORD`) — тот же seed: при
  миграции переносится в хеш пароля первого пользователя.

## 36. Hyper Control Plane

Решение от niquola: вынести общее для всех Hyper в отдельный сервис — **Hyper Control Plane**.
Hyper-инстансы (CS, marketing, личные, будущие) — data plane: там живут агенты, чаты и код.
Control plane решает только общие вопросы: кто ты, куда тебе можно, где что находится, как
доставить сообщение.

### 36.1 Зачем

- **Google SSO не масштабируется на много Hyper.** Google принимает redirect URI только на публичных
  доменах (`.internal` отклоняется) и требует ручной регистрации каждого адреса в консоли. Один
  control plane на публичном адресе регистрируется в Google один раз; каждый Hyper входит через
  него по OIDC.
- **Доступы, каталог и inbox** — общие для всех Hyper, их нельзя держать в каждом по отдельности.

### 36.2 Что делает (по этапам)

| Этап | Функция | Смысл |
|---|---|---|
| 1 | **Вход (OIDC provider)** | один вход через Google Health Samurai для всех Hyper; Hyper — OIDC-клиент |
| 1 | **Каталог Hyper** | реестр инстансов: адрес, владелец, назначение; Hyper регистрируется сам |
| 2 | **Доступы** | кто в какой Hyper может войти и с какой ролью; приходит в токене при входе; отзыв сразу |
| 3 | **Inbox** | сообщения между людьми и агентами разных Hyper по адресам (`anna@cs`, `sales@marketing`, §24), доставка «когда доступен» (§25.3) |

### 36.3 Протокол

- Стандарт **OpenID Connect** (поверх OAuth 2.0). Hyper — обычный OIDC-клиент: authorization code
  flow, проверка ID token по JWKS control plane (у нас уже есть `googleVerify` — обобщить до любого
  OIDC-issuer).
- В ID token, кроме `sub`/`email`/`name`, — claim с ролью в этом Hyper (`hyper_role`), чтобы доступ
  решался при входе, без отдельного запроса.
- Новый Hyper не трогает Google: только регистрируется в control plane (client id + redirect URI).

### 36.4 Из чего строить

- **Dex** (Go, Apache 2.0, CNCF) умеет только вход: Google-коннектор с `hostedDomains`, статические
  клиенты, OIDC. Доступов, каталога и inbox нет, и не будет — проект намеренно узкий.
- Поэтому control plane — **свой небольшой сервис** (Hyper-стек: Bun + Postgres), говорящий с Google
  напрямую (код уже есть в `src/auth/google*`). Dex опционально как движок входа, но не обязателен.
- У NetBird уже есть встроенный Dex (`netbird.health-samurai.io/oauth2`) — можно использовать для
  входа на первом этапе, если он разрешает сторонних клиентов (проверить).

### 36.5 Правила

- **Маленький и скучный.** Это корень доверия (§22): никаких агентов, `eval`, hot-reload кода агентом;
  изменения через ревью.
- **Не единственная точка отказа.** В каждом Hyper остаётся запасной вход по паролю (уже есть), чтобы
  недоступный control plane не запирал людей.
- **Hyper хранит своих пользователей сам.** Control plane удостоверяет личность и выдаёт право войти;
  данные, чаты и роли внутри Hyper остаются в его базе (§34).
- **Только `health-samurai.io`** на этапе 1 (consent screen Internal уже настроен в `hs-hyper-code`).

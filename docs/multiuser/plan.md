# Hyper multiuser — план рефакторинга и миграции

Цель: доверенная команда в одном Hyper (DESIGN §32–§34). Каждый входит под
собой, видит своё, работает на своих подписках и своих аккаунтах.
**Изоляции между людьми нет** (security — отдельный этап, §22/§26).

Принципы, общие для всех фаз:
- **Одна ветка кода.** Нет `if (multiuser)`. Один пользователь — частный случай.
- **Каждая фаза — отдельная ветка, миграция и точка отката.** Живой Hyper
  переключается только после репетиции на копии базы (`script/multiuser.ts`
  как образец).
- **Миграции только добавляют** (nullable-колонки, новые таблицы, catalog-only),
  с `lock_timeout`, идемпотентны, с точным `down`. Никаких переписываний
  больших таблиц; если нужно заполнить старые строки — пачками, отдельной
  командой, по желанию.
- **Старое поведение сохраняется до явного включения.** Сначала код, умеющий
  и так и так; потом переключение данных.
- **Тесты не подгружают плагины** (`src/$test.ts` из main) — иначе пишут в
  живые схемы.

## Фаза 1. Пользователи и вход — **готово, ветка `multiuser-users`**

Таблица `users`, вход (пароль / email+пароль), автор у агентов, сообщений,
событий. Переключение — `SWITCH.md`. Отрепетировано.

## Фаза 2. «Своё у каждого» в данных

Что меняется в модели:

| Сейчас (общее) | Станет (у каждого) | Где в коде |
|---|---|---|
| `kv` `seen-at:<agent>`, `seen:<agent>` | `seen-at:<user>:<agent>` | `session/list.ts`, `nav/next_unread`, `api/*_read_POST` |
| `kv` `mobile-pin-agent:<agent>` | `pin:<user>:<agent>` | `api/*_pin_POST`, `api/agents_GET`, `nav/*_pin_POST` |
| список агентов — все | вкладка «мои» = `created_by = me`; «все» остаётся | `session/list.ts`, `nav/items.ts` |

- Лучше отдельная таблица `user_agent_state(user_id, agent_id, seen_at, seen_idx, pinned)`
  вместо ключей в `kv`: индексы, нет строкового парсинга, чистый join в `session.list`.
- **Миграция данных:** одна — перенести текущие `seen-at:*` и `mobile-pin-agent:*`
  в `user_agent_state` для владельца (`niquola`). Маленький объём (≈ число агентов),
  одна транзакция. Старые ключи `kv` не удалять до следующей фазы — откат = код
  снова читает `kv`.
- **Совместимость:** пока пользователь один, результат тот же, что сейчас.

## Фаза 3. Настройки у каждого

`settings` уже имеет `scope_type / scope_id`. Добавляем уровень `user`.

- Порядок разрешения: `agent` → **`user`** → `global` → env → default.
- `settings.get` берёт `userId` из сессии (или `created_by` агента в фоне,
  через `auth.actorId`).
- Какие настройки становятся личными (по умолчанию): модель по умолчанию,
  `status_line`, язык, тема. Остальные — глобальные, как сейчас.
- В декларации настройки поле `scope: "user" | "global"`, чтобы UI знал, где
  показывать.
- **Миграция данных:** нет. Текущие глобальные значения остаются глобальными и
  продолжают работать; личное значение появляется, только когда человек его
  задал.

## Фаза 4. Подписки и ключи LLM у каждого — **самое важное**

Факт из кода: у LLM уже есть **account** — `provider/account:model`
(`codex/personal:gpt-…`), таблица `oauth_credentials(provider, account)`,
`llm.listAccounts`. Файловые логины: `~/.codex/auth*.json`, `~/.kimi/credentials`,
`~/.hyper/accounts/`.

Это готовый крючок. Делаем «account принадлежит пользователю»:

- `oauth_credentials.owner_id` (nullable). `NULL` = общий аккаунт организации
  (как оргключ, §0.5), иначе личная подписка.
- Файловые логины (`~/.codex/auth.personal.json`) — привязка
  `account → owner_id` в новой таблице `llm_account_owners(provider, account, owner_id)`,
  сами файлы не трогаем.
- **Выбор аккаунта при вызове:** если в модели account не указан —
  берём аккаунт **владельца агента** (`created_by`) для этого провайдера, иначе
  общий, иначе `default` (как сейчас).
- Учёт расхода (`llm/recordUsage`) — добавить `user_id`. Лимиты по
  пользователю — позже.
- Нельзя: взять чужую личную подписку, даже если она единственная. Лучше
  понятная ошибка «у тебя нет подписки на X, есть общий ключ Y?».
- **Миграция данных:** все существующие аккаунты → `owner_id = niquola`
  (это действительно твои подписки). Одна команда, откат — `owner_id = NULL`.
- **Проверка:** на копии — агент Ани с `claude-code:…` без своей подписки
  получает ошибку, а не твою подписку.

## Фаза 5. Google и другие личные аккаунты плагинов

- `google.token`: убрать выбор «единственного авторизованного» и
  `GOOGLE_ACCOUNT` как молчаливый дефолт (§11.7). Аккаунт по умолчанию =
  аккаунт **текущего пользователя** (владельца агента).
- Секреты по `namespace/name` в `local_secrets` (google — 16 мест, telegram — 22):
  добавить `owner_id` для личных (токены Gmail, Telegram-сессия), `NULL` для общих.
- Какие плагины личные по своей природе (applehealth, ramp, cuf, lusiadas,
  telegram, gmail/gcal) — пометить в `SKILL.md`/манифесте `personal: true`.
  Для них ядро требует, чтобы вызов шёл от владельца аккаунта.
- **Миграция данных:** существующие токены → `owner_id = niquola`.
- Это фаза с самым широким касанием кода (плагины), делать по одному плагину:
  google → telegram → остальные.

## Фаза 6. Интерфейс

- Шапка: кто я, выход, переключатель «мои / все».
- Автор у сообщений в чате (показываем, только если пользователей > 1).
- Страница «Пользователи» для owner: добавить, отключить, сменить пароль,
  роль. Второй email (алиасы) — таблица `user_emails(user_id, email)`, вход по
  любому.
- Страница «Мои аккаунты»: подписки LLM, Google, Telegram — подключить /
  отключить свои.
- Надпись «изоляции между пользователями нет» (§32).

## Фаза 7. Клиенты и мосты

- iPhone: поле email, показывать при `multiuser: true` из `/auth/session`
  (поле уже отдаём). До обновления приложения второй пользователь ломает вход
  с телефона — поэтому фаза 7 идёт **до** добавления второго человека.
- Sidebar/browser-extension: `sidebar_pairs` получает `user_id`; pairing
  подтверждается в сессии пользователя.
- REPL: токен `kind:"repl"` → вызовы от имени owner (сейчас без автора).
- Push-уведомления: адресат — владелец агента / участник.

## Фаза 8. Второй человек

Только после фаз 2–7. Чек-лист перед добавлением:
- у него своя подписка LLM (или явно выданный общий ключ);
- свой Google, если нужен;
- iPhone обновлён;
- `verify` показывает `signIn: email + password`.

## Порядок и зависимости

```
0 гигиена ─► 1 users (готово) ─► 2 своё в данных ─┐
                                   3 настройки ────┼─► 6 UI ─► 7 клиенты ─► 8 второй человек
                                   4 подписки LLM ─┤
                                   5 google/плагины┘
```

2, 3, 4, 5 независимы друг от друга и могут идти в любом порядке. По
ценности: **4 → 5 → 2 → 3** — без 4 и 5 второй человек фактически
работает на твоей подписке и с твоей почтой.

## Сводка миграций

| Фаза | Схема | Данные | Откат |
|---|---|---|---|
| 1 | `users`, `agents.created_by`, `messages.author`, `events.actor` | создать `niquola` | `multiuser.ts down` |
| 2 | `user_agent_state` | копия `seen/pin` из `kv` → `niquola` | код читает `kv`; drop таблицы |
| 3 | нет (есть `scope_type`) | нет | код |
| 4 | `oauth_credentials.owner_id`, `llm_account_owners`, `usage.user_id` | все аккаунты → `niquola` | `owner_id = NULL`; drop |
| 5 | `local_secrets.owner_id` | личные токены → `niquola` | `owner_id = NULL`; drop |
| 6 | `user_emails` | `<personal email>` → `niquola` | drop |
| 7 | `sidebar_pairs.user_id` | существующие pairs → `niquola` | drop колонки |

Все — только добавление, catalog-only, с `lock_timeout`, репетиция на копии
перед живой базой.

## Оценка

Фаза 1 заняла основную долю риска (модель, вход, миграция на живых данных).
Фазы 2–3 — по 1 дню. Фаза 4 — 2–3 дня (самая важная, аккуратная). Фаза 5 —
2–4 дня (много плагинов, по одному). Фазы 6–7 — 3–5 дней (UI + iPhone).
Итого до «второй человек может работать» — порядка 2–3 недель.

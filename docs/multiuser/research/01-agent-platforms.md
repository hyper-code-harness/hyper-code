## 1. Windmill — самый близкий к нам аналог

Источники:
- https://www.windmill.dev/docs/core_concepts/roles_and_permissions
- https://www.windmill.dev/docs/core_concepts/variables_and_secrets
- https://www.windmill.dev/docs/core_concepts/resources_and_types
- https://www.windmill.dev/docs/core_concepts/worker_groups
- https://www.windmill.dev/docs/flows/flow_approval
- https://github.com/windmill-labs/windmill/blob/main/backend/migrations/20220123221903_first.up.sql
- https://github.com/windmill-labs/windmill/blob/main/backend/migrations/20221219032311_folders.up.sql

### Как устроено

Workspace — основная единица изоляции; почти каждая таблица (`script`,
`flow`, `variable`, `resource`, `schedule`, `queue`, `completed_job`, `usr`,
`audit`) имеет `workspace_id` в составе первичного ключа. Внутри workspace
права выражены **через путь объекта**: `u/<user>/<name>` — личное
пространство пользователя, `f/<folder>/<name>` — папка с собственными
владельцами. Таблица `folder` имеет колонки `owners VARCHAR(255)[]` и
`extra_perms JSONB` (GIN-индекс). Три роли на объект: Admin/Owner, Writer,
Viewer; админ workspace обходит ACL целиком.

Ключевое: изоляция реализована **Postgres Row Level Security, а не
проверками в коде**. Миграция включает `ENABLE ROW LEVEL SECURITY` на
`audit`, `queue`, `completed_job`, и в DO-блоке — на `resource`, `script`,
`variable`, `schedule`, `flow`. Политики читают переменные сессии:

```sql
CREATE POLICY see_own ON queue FOR ALL
USING (SPLIT_PART(queue.permissioned_as, '/', 1) = 'u'
   AND SPLIT_PART(queue.permissioned_as, '/', 2) = current_setting('session.user'));

CREATE POLICY see_member ON queue FOR ALL
USING (SPLIT_PART(queue.permissioned_as, '/', 1) = 'g'
   AND SPLIT_PART(queue.permissioned_as, '/', 2)
       = any(regexp_split_to_array(current_setting('session.groups'), ',')::text[]));

CREATE POLICY see_extra_perms_user ON %I FOR ALL
USING (extra_perms ? CONCAT('u/', current_setting('session.user')));
```

Отдельно стоит колонка **`permissioned_as` в таблицах `queue` и
`completed_job`**: у задачи в очереди записано, *от чьего имени* она
выполняется, и RLS фильтрует очередь по этому полю, а не по автору. Это
ровно «от чьего имени» из §11.2, вынесенное в БД.

Variables — key-value, **все** (не только секретные) шифруются симметричным
ключом, специфичным для workspace. Resources — те же variables, но с JSON и
типом (Resource Type), что даёт типизированный выбор в автоформах. Секреты
опционально выносятся во внешний бэкенд (HashiCorp Vault через JWT-роль и
JWKS-эндпоинт Windmill, Azure Key Vault, AWS Secrets Manager) с
fail-closed-семантикой. `extra_perms` для scripts/flows/apps/variables
**трекается в исходниках** и деплоится через git sync/CLI — права ревьюятся
как код.

Compute: worker groups через тег. Воркер получает `WORKER_GROUP` как env,
сам присоединяется к группе и подтягивает конфиг (включая init-скрипты) с
hot-reload. Скрипт/флоу/шаг помечается тегом, воркеры слушают свои очереди.
Явно заявлено: Windmill не спавнит воркеры сам, а «играет вместе» с
Kubernetes/ECS/Nomad/Compose.

Approval: шаг флоу с опцией Suspend. `wmill.getResumeUrls()` генерирует
персональные секретные URL; флоу висит, пока не придёт заданное число
approve-событий. Есть таймаут, `continue on disapproval`, форма с JSON
Schema на странице approval, и flow-level pre-approvals (одобрение в начале
засчитывается позже).

### Что забрать / чего избежать

**Забрать.**
1. **RLS как несущая конструкция** (§0.1, §15.7). Windmill — доказательство,
   что тезис «граница — GRANT в Postgres, а не проверки в коде» работает на
   продакшн-масштабе. Конкретная техника: `current_setting('session.user')`
   и `current_setting('session.groups')` + политика на каждой таблице.
   Для нас это прямой рецепт: соединение на запрос выставляет session-vars,
   и никакой автор runtime-функции (§0.6) не может их обойти изнутри SQL.
2. **`permissioned_as` на задаче** (§11.2, §12.3). У нас в `agents` уже есть
   inline-очередь; добавить туда `permissioned_as` (кто владелец действия) —
   минимальное изменение, закрывающее «у каждой фоновой работы есть
   владелец». Фильтровать очередь надо по владельцу, а не по автору.
3. **Путь как ACL**: `u/<user>/...` vs `f/<folder>/...` — одно поле несёт и
   имя, и владельца, и область видимости. Для §13 это дешёвый способ не
   заводить отдельную таблицу прав на каждый объект.
4. **Права в git** (§14.5). `extra_perms` в исходниках → грант роли проекту
   тоже должен быть текстом в репозитории проекта, а не кликом в UI:
   «этот проект пишет в CRM от имени Ани» становится ревьюабельным диффом.
5. **Approval как suspend + персональный URL, а не блокирующий вызов**
   (§11.4). Задача не держит процесс; она приостановлена в БД и
   возобновляется событием. Это точно ложится на наш `wakeUpWhen`.
   Оттуда же: обязательный таймаут и явная ветка «отказано/истекло».
6. **Worker groups по тегу** (§15.6). «У задачи есть требования, у compute —
   возможности» реализуется как совпадение строковых тегов, без
   оркестратора. Windmill прямо отказывается спавнить воркеры — и нам не надо.

**Избежать.**
1. **Админ workspace читает всё.** У Windmill админ workspace обходит ACL по
   определению. Для нас это прямо запрещено §13.1: роль, включая
   администратора, не даёт доступа к личному ресурсу другого человека.
   Значит наши RLS-политики не должны иметь ветки `OR is_admin`.
2. **Владелец credential — workspace, не человек.** Variables шифруются
   ключом workspace; личного владения токеном нет. Это ровно то, что §11.3
   отвергает («токен принадлежит человеку, а не платформе»).
3. **Одноуровневость.** Нет понятия организации над workspace, и нет
   различия «общий ресурс / личный ресурс» — всё сводится к ACL. Наш §13.1
   (роль для общего, grant для личного) — сознательное отступление от этой
   модели, и его нельзя сворачивать обратно в один ACL.
4. Approval-URL — это bearer-секрет: кто переслал ссылку, тот и одобрил.
   У нас §11.4 требует знать *личность* одобряющего, значит возобновление
   должно проверять сессию, а не только знание URL.

## 2. n8n — самая близкая модель «агент от имени пользователя»

Источники:
- https://docs.n8n.io/user-management/rbac/projects/
- https://docs.n8n.io/user-management/rbac/role-types/
- https://docs.n8n.io/administer/manage-credentials/share-credentials-securely
- https://docs.n8n.io/administer/manage-credentials/end-user-credentials

### Как устроено

Два уровня ролей. **Instance roles** — что человек может во всём инстансе
(owner, admin). **Project roles** — что он может в конкретном проекте:
Admin / Editor / Viewer, и один человек может иметь разные роли в разных
проектах. Проект группирует workflows и credentials. Есть личные проекты
(personal) и командные (team). Матрица прав явная: Viewer не может даже
запустить workflow вручную. Важная дыра, зафиксированная в самой
документации: **«Variables and tags aren't affected by RBAC: they're global
across the n8n instance»** — то есть часть конфигурации живёт вне модели прав.

Обычный шаринг credential: владелец (создатель или проект) делится им с
пользователем или проектом. Получатель **может использовать credential, но
не может посмотреть его содержимое**. Инстанс-админы видят и шарят все
credentials.

Главное — **End-user credentials** (Enterprise, в статусе Preview). Это
явная реализация «агент действует от имени пользователя»:

- Credential бывает двух типов: **Fixed** (один аккаунт на всех, дефолт) и
  **End-user** (аккаунт того, кто запустил).
- End-user credential — это **шаблон**: админ проекта один раз настраивает
  OAuth-приложение (например, для Gmail), а каждый пользователь подключает
  свой аккаунт по этому шаблону. Connection принадлежит подключившему.
- В рантайме n8n резолвит credential в подключённый аккаунт триггернувшего
  пользователя. Запустил A — читается ящик A; запустил B — ящик B.
- **Приватность данных исполнения**: метаданные выполнения (статус, время,
  факт использования end-user credential) видны всем, у кого есть доступ к
  executions, но input/output этих нод видит только тот, чьё подключение
  использовалось. Для всех остальных, **включая администраторов инстанса**,
  вывод редактируется (redacted).
- Что видит админ: что шаблон существует и сколько подключений к нему
  привязано. Счётчик — всё. Он не может посмотреть отдельное подключение,
  его секреты, использовать чужой аккаунт в своих workflow или увидеть
  скрытый вывод чужого исполнения.
- Ограничения: только в team-проектах (не в личных), создавать по умолчанию
  может только project admin, права выдаются через custom roles. Шаринг
  шарит **шаблон, а не подключения**. Удаление шаблона убивает все
  подключения всех пользователей.
- Можно смешивать в одном workflow: личный календарь через end-user
  credential, общий Slack — через fixed.

### Что забрать / чего избежать

**Забрать.**
1. **Разделение «шаблон подключения» и «подключение»** — это наш §11.3 в
   чистом виде и лучшая найденная формулировка. Плагин/проект объявляет,
   *к какому ресурсу* он обращается (шаблон), а токен приносит человек
   (подключение). Прямо ложится на §11.7 п.1: «запрет неявного выбора
   единственного аккаунта» — в n8n у ноды вообще нет аккаунта по умолчанию.
2. **Админ не видит содержимое** (§13.1). n8n — редкий пример, где
   документация явно перечисляет, чего админ не может. Наше правило «роль
   никогда не выдаёт доступ к личному ресурсу другого человека» здесь уже
   реализовано, и это доказывает его практичность.
3. **Приватность данных исполнения, а не только доступа** (§11.5). Метаданные
   события публичны, содержимое — нет. Это ровно наша формулировка «агент
   получает ответ, а не доступ к ящику»: в аудит-событие (§12.2) пишем
   размер/тип, не содержимое.
4. **Смешивание fixed и end-user в одном сценарии.** У нас это «оргключ»
   против «личной подписки» (§0.4, §0.5): один процесс может законно
   использовать оба источника, значит топливо и credential указываются на
   уровне шага, а не всей задачи.
5. **Централизованное создание шаблона** (только team-проект, только
   project admin) — совпадает с §14.5: грант проекту должен быть явным,
   узким и обозримым, а не создаваться каждым участником втихую.

**Избежать.**
1. **Глобальные variables вне RBAC.** Документация признаёт, что variables и
   tags глобальны. У нас аналог — настройки и `$setting_*`; если хоть один
   класс объектов выпадет из модели прав, он станет каналом утечки (§15.3
   «секреты монтируются в compute, а не глобальны»).
2. **Обычный шаринг credential = «используй, но не смотри».** Это иллюзия
   защиты: имея право запускать произвольный workflow с этим credential,
   получатель извлекает токен тривиально. У нас §0.6 говорит то же самое про
   код. Вывод: «поделиться credential» не должно существовать как операция —
   только grant на *действие* с фильтром (§11.3), либо чужое подключение.
3. **Удаление шаблона убивает все подключения.** Плохая связность владения:
   один админ может обнулить работу всех. У нас отзыв — право носителя
   (§14.5), и он обязан быть точечным.
4. n8n не имеет режима `account` (§12): только можно/нельзя. Поэтому у них
   автономность агента упирается либо в общий fixed-credential (небезопасно),
   либо в ручной запуск пользователем (неавтономно). Это практическое
   подтверждение, зачем нам третий режим.

## 3. Temporal — namespaces и task queues (модель для нашего compute)

Источники:
- https://docs.temporal.io/namespaces
- https://docs.temporal.io/production-deployment/multi-tenant-patterns
- https://docs.temporal.io/evaluate/development-production-features/multi-tenancy

### Как устроено

**Namespace — единица изоляции, а не единица арендатора.** Task Queues и
Workflow Executions принадлежат namespace. Что он даёт конкретно:
уникальность Workflow ID внутри namespace; изоляцию ресурсов («тяжёлый
трафик одного namespace не влияет на другие на том же кластере»); границу
конфигурации (Retention Period, Archival настраиваются per-namespace);
границу доступа. Namespaces изолированы по умолчанию, и **Nexus — единственный
контролируемый путь**, которым workflow одного namespace вызывает операцию
в другом.

Ключевой момент для нас — в self-hosted Temporal нет встроенного RBAC:
доступ ограничивается **custom Authorizer на Frontend Service**. Роли
появляются только в Temporal Cloud. То есть в опенсорсной версии модель
прав — это точка расширения, а не данность.

Документация явно предупреждает: **«один namespace всё ещё
multi-tenant»** — несколько приложений или команд могут делить namespace, но
обязаны координировать именование Workflow ID и Task Queue во избежание
конфликтов. То есть namespace сам по себе не решает мультиарендность.

Четыре паттерна мультиарендности, отсортированы от рекомендуемого к
нерекомендуемому:

1. **Task queue на арендатора (рекомендуется).** Каждый tenant получает свои
   task queues, воркеры опрашивают несколько tenant-очередей одним процессом.
   Сильная изоляция, тысячи арендаторов на namespace.
2. **Одна очередь + Fairness keys.** Каждому tenant — fairness key и вес;
   есть per-key rate limits. Веса меняются без редеплоя, новый tenant не
   требует новых воркеров. Минус: честность вероятностная, тяжелее
   отлаживать, вес применяется в момент планирования, а не диспетчеризации.
3. **Общая workflow-очередь, раздельные activity-очереди.** Для случая, когда
   workflow лёгкие, а activities тяжёлые или требуют изоляции зависимостей.
4. **Namespace на арендатора.** Полная изоляция, свои rate limits, максимальная
   граница безопасности — но операционно дорого. Прямая цифра из документации:
   практично примерно **до 50 арендаторов**, не годится при 10 000+.
   Выбирается тогда, когда «границы арендатора обязаны быть границами
   credential»: свои service accounts, API-ключи, дашборды, лимиты.

### Что забрать / чего избежать

**Забрать.**
1. **Различать изоляцию и арендатора** (§15.2). Наш compute — это ровно
   temporal-namespace: единица изоляции, конфигурации и лимитов, а не
   «пользователь». На одном compute живут несколько проектов (§15.6), как в
   одном namespace — несколько команд, и Temporal честно говорит, что это
   риск, требующий соглашения об именовании. Наше «у каждого свой каталог и
   свой системный пользователь» — тот же вывод, только жёстче.
2. **Правило выбора границы, сформулированное за нас.** «Namespace на
   арендатора выбирают, когда граница арендатора обязана быть границей
   credential». Переводим в §15.3: раз секреты монтируются в compute, то
   **отдельный compute нужен ровно там, где нужен отдельный набор секретов**.
   Это готовый критерий, когда заводить новый compute, а когда хватит тега.
3. **Task queue как дешёвая единица маршрутизации** (§15.6 «планирование»).
   Temporal рекомендует именно очереди, а не namespace, потому что очередь —
   это строка, а namespace — это операционная единица. У нас: тег/требование
   задачи — дёшево, новый compute — дорого. По умолчанию выбираем тег.
4. **Воркер опрашивает несколько очередей одним процессом.** Наш workerLoop
   может обслуживать несколько проектов на одном compute — это штатный
   паттерн №1, а не компромисс.
5. **Nexus как единственный путь между namespace** (§8). Подтверждает наш
   потолок федерации «попросить и получить ответ»: межграничный вызов — это
   именованная операция с контрактом, а не прямой доступ к состоянию соседа.
6. **Fairness keys + per-key rate limit** — готовый ответ на §8.3 («чужой
   агент не должен жечь мои токены без лимита») и на учёт по паре
   (compute, проект) из §15.6.

**Избежать.**
1. **Не строить изоляцию на namespace-per-user.** Цифра «до 50» —
   предупреждение против варианта C из §3 в его наивной форме (инстанс на
   человека): операционная стоимость растёт линейно и упирается в потолок
   довольно рано. Наш §15.7 («compute — абстракция, storage — один общий
   Postgres») этот потолок обходит, и Temporal подтверждает, что выбор верный.
2. **Отсутствие модели прав в ядре.** В self-hosted авторизация — это
   заглушка, которую каждый пишет сам, из-за чего у пользователей Temporal
   нет общего языка про доступ. Нам это запрещено §12.4: режим определяется
   **в ядре, до вызова плагина**, а не в подключаемом авторизаторе.
3. **Вероятностная честность.** Для «на чьём топливе» (§0.5) веса не годятся:
   расход подписки — это учёт, а не приоритет. Ограничение по топливу должно
   быть жёстким (hard limit), а не весовым.

## 4. Dify — tenant-модель в исходниках

Источники:
- https://github.com/langgenius/dify/blob/main/api/models/account.py
- https://github.com/langgenius/dify/blob/main/api/models/tools.py
- https://github.com/langgenius/dify/blob/main/api/models/enums.py
- https://docs.dify.ai/en/use-dify/workspace/team-members-management

### Как устроено

Модель данных плоская и явная. Таблица `tenants` (id, name,
`encrypt_public_key`, plan, status, custom_config) — это workspace.
`tenant_account_joins` связывает аккаунт с тенантом:
`UNIQUE(tenant_id, account_id)`, колонки `role`, `invited_by`, `current`
(флаг текущего активного workspace у пользователя), `last_opened_at`.
Ролей пять: `owner`, `admin`, `editor`, `normal`, `dataset_operator`, с
хелперами `is_privileged_role` (owner|admin), `is_editing_role` и т.п. —
то есть роль это enum-строка, а проверки — статические методы в коде, а не
таблица разрешений. Уровня «организация над workspace» нет: tenant и есть
верхний уровень.

Credentials. Все провайдеры инструментов — `tool_builtin_providers`,
`tool_api_providers`, `tool_workflow_providers`, `tool_mcp_providers` —
несут **одновременно `tenant_id` и `user_id`** (комментарий в коде: «who
created this tool provider») плюс `encrypted_credentials`. То есть в схеме
запомнено, кто конкретно принёс credential, а не только в каком workspace он
лежит. Есть `credential_type` (`api-key` | `oauth2`) и `expires_at`.

Самое интересное — колонка `visibility` типа `PermissionEnum` с дефолтом
`ALL_TEAM`. Сам enum (`api/models/enums.py`) описан как «Shared permission
levels for resources (datasets, credentials, etc.)» и имеет три значения:

```python
class PermissionEnum(StrEnum):
    ONLY_ME = "only_me"
    ALL_TEAM = "all_team_members"
    PARTIAL_TEAM = "partial_members"
```

Отдельно есть OAuth-клиенты двух уровней: `tool_oauth_system_clients`
(общие для инстанса) и `tool_oauth_tenant_clients` (`UNIQUE(tenant_id,
plugin_id, provider)`) — то есть организация может подставить своё OAuth-
приложение вместо системного. Права на плагины вынесены в
`account_plugin_permissions` (`install_permission`, `debug_permission`) и
`tenant_plugin_auto_upgrade_strategies` — установка и отладка плагинов
регулируются на уровне тенанта.

### Что забрать / чего избежать

**Забрать.**
1. **`visibility` на самом credential** (§11.3). Трёхзначная шкала
   `only_me / all_team / partial_members` — минимальный практичный словарь
   владения, и он живёт **на записи с credential**, а не в отдельной системе
   прав. Для нас: у подключения человека должна быть такая же колонка, и
   дефолт обязан быть `only_me`, а не `all_team` (у Dify дефолт опасный).
2. **`user_id` рядом с `tenant_id` на каждом credential.** Даже в системе,
   где владелец — workspace, схема сохраняет, кто принёс доступ. Это
   дешёвое и обязательное для нас поле (§11.7 п.2: `owner_user` в grants) —
   без него невозможно адресовать аудит-событие (§12.2).
3. **`expires_at` и `credential_type` в схеме.** Срок жизни — свойство самого
   подключения, а не внешнего расписания (§11.3 «grant привязан к сроку»).
   Различение `api-key` vs `oauth2` совпадает с §0.4 (ключ против подписки).
4. **Два уровня OAuth-клиента: системный и тенантный.** Прямой аналог §0.4:
   организационный ключ и личная подписка — разные классы источников.
   Полезно: организация может подменить OAuth-приложение, не трогая код
   плагина.
5. **Права на установку и отладку плагинов как отдельная сущность**
   (`account_plugin_permissions`). Это наш §0.6: «право писать функции
   принадлежит только админам» — у Dify это уже отдельное поле, а не
   производная от роли.

**Избежать.**
1. **Дефолт `ALL_TEAM`.** Credential по умолчанию виден всей команде — прямое
   нарушение §11.6 («членство в проекте не даёт прав на личные ресурсы»).
   Наш дефолт — `only_me`, и расширение видимости всегда явный акт носителя.
2. **Роли как статические методы в коде.** `is_privileged_role(role)`
   разбросано по контроллерам — ровно та архитектура, которую §0.6 объявляет
   несостоятельной: автор кода просто не напишет проверку. У нас решение —
   RLS (см. Windmill), а не хелперы.
3. **Плоскость tenant = верхний уровень.** Нет организации над workspace и
   нет проекта внутри, поэтому «личное» и «общее» неразличимы. §13.1 требует
   трёх слоёв (организация / проект / личное), и Dify показывает, во что
   вырождается модель без них.
4. **Нет `permissioned_as` на выполнении.** В `tool_model_invokes` есть
   `user_id` и `tenant_id`, но это автор вызова, а не «от чьего имени» —
   для фоновых задач (§12.3) этого недостаточно.

## 5. LangGraph Platform / LangSmith

Источники:
- https://docs.langchain.com/langsmith/rbac
- https://docs.langchain.com/langsmith/administration-overview
- https://docs.langchain.com/langsmith/deploy-with-control-plane

### Как устроено

Два уровня сущностей: **organization** и **workspace**. У каждого
пользователя ровно одна организационная роль (Organization Admin / Operator
/ User / Viewer — системные, не редактируются) и **по одной роли на каждый
workspace**, членом которого он является. Workspace-роли (Admin / Editor /
Viewer) и custom roles с гранулярными комбинациями прав — Enterprise-фича;
на остальных планах все получают Admin. Права именованы как строки вида
`organization:manage`, `organization:pats:create`, `organization:pats:read`,
`organization:pats:manage`. Роли могут назначаться автоматически из IdP
через SCIM groups или SSO Groups Sync. Упоминается также ABAC поверх RBAC.

Показательная деталь: у Organization Admin есть право **видеть, отзывать и
удалять personal access tokens любого участника организации**
(`organization:pats:read`, `organization:pats:manage`).

Деплой: включение LangSmith Deployment добавляет к инстансу **control
plane**, **data plane listener** и **operator**, который провиженит Agent
Servers в кластере Kubernetes. Пользователь собирает Docker-образ
(`langgraph build`), пушит в реестр, доступный кластеру, и деплоит через UI
control plane, указав URL образа. Базовая платформа (трейсы, оценка,
промпты) продолжает работать отдельно; развёрнутые Agent Servers шлют трейсы
обратно в неё.

### Что забрать / чего избежать

**Забрать.**
1. **Разделение control plane и data plane** (§15.7). Это ровно наш вывод
   «compute — одна абстракция, storage — другая, совмещать нельзя»:
   control plane знает, что и где развёрнуто, data plane исполняет, и
   телеметрия течёт обратно в общее хранилище. Подтверждает, что §15.7 — не
   изобретение, а стандартная топология.
2. **Одна роль на организацию + одна роль на каждый workspace.** Простое
   правило, снимающее неоднозначность «какая роль применяется». Для §13.2
   (уровни ролей) — хороший минимальный контракт: роль в организации и роль
   в проекте разные, но их ровно по одной.
3. **Права как строки вида `<область>:<объект>:<действие>`.** Пространство
   имён прав, которое можно объявлять плагином (§14.3) и показывать в UI.
4. **Назначение ролей из IdP (SCIM/SSO Groups).** Для §13 важно: роль
   приходит из кадровой системы, значит «уход носителя из организации
   автоматически аннулирует грант» (§14.5) имеет технический источник
   истины, а не ручной процесс.
5. **Образ как единица деплоя** (§15.6). Деплоймент = (проект × compute) +
   конкретный образ; это то, что делает деплоймент отдельной сущностью, а не
   просто пометкой на проекте.

**Избежать.**
1. **Админ организации управляет чужими personal access tokens.** Прямое
   нарушение §13.1. PAT — личный носитель полномочия; у нас админ может
   *отозвать* участие человека в организации, но не должен иметь права
   *читать* его личные токены. Отзыв и чтение обязаны быть разными правами.
2. **RBAC только в Enterprise, иначе все Admin.** Если модель прав —
   платная опция, то дефолт системы небезопасен, и большинство инсталляций
   живут без разграничения. У нас модель доступа должна быть в ядре и в
   бесплатном пути (§12.4), иначе она не будет работать никогда.
3. Нет ни понятия «на чьём топливе», ни понятия личного ресурса: workspace
   владеет всем. §0.5 и §11 остаются нашей собственной работой — готового
   образца здесь нет.

## 6. CrewAI Enterprise (AMP)

Источники:
- https://docs.crewai.com/en/enterprise/features/rbac
- https://enterprise-docs.crewai.com/configuration/configuration

### Как устроено

Два слоя прав, явно названные в документации:
**feature permissions** — что роль может делать по областям платформы, и
**entity-level permissions** — доступ к конкретным экземплярам: отдельным
автоматизациям, переменным окружения, LLM-подключениям и git-репозиториям.

Предопределённые роли: Owner (полный доступ, не ограничивается) и Member
(чтение большинства областей, но **manage** на environment_variables,
llm_connections и studio_projects). Плюс кастомные роли. Уровни прав:
Manage / Read / No access, но для environment_variables, llm_connections,
default_settings, organization_settings и studio_projects **read-only не
поддерживается** — только Manage или No access. Видимость автоматизации
настраивается отдельно: Private либо whitelist пользователей/ролей.

Практический пример из документации: чтобы задеплоить из GitHub, нужны
`crews_dashboards` ≥ Read, доступ к конкретному git-репозиторию через
entity-level RBAC, и `studio_projects: Manage` если крю собирается в Studio.

### Что забрать / чего избежать

**Забрать.**
1. **Два слоя: право на класс операций + право на конкретный экземпляр**
   (§13.1). Это ровно наше «роль для общих ресурсов, grant для конкретного»,
   выраженное в терминах одного продукта. Особенно полезно, что
   entity-level права применяются именно к git-репозиториям и LLM-
   подключениям — то есть к тем же объектам, что у нас в §0.3 и §0.4.
2. **Признание, что для секретов не бывает read-only.** CrewAI честно
   отмечает: у environment_variables и llm_connections есть только Manage
   или No access. Это важный вывод для §12.4: «прочитать секрет» — не более
   слабое право, чем «изменить»; шкала Viewer/Writer к секретам неприменима.
3. **Видимость автоматизации: Private или whitelist** — дефолт-приватность
   на уровне объекта (в отличие от Dify).

**Избежать.**
1. **Owner «не может быть ограничен».** Такая же проблема, что и у
   Windmill-админа: §13.1 требует, чтобы никакая роль не открывала личные
   ресурсы. Неограничиваемая роль несовместима с §12 (за действия в режиме
   `account` должен отвечать человек, а не «у него полный доступ»).
2. **Member по умолчанию имеет Manage на LLM-подключениях.** То есть любой
   участник управляет тем, чьё топливо тратится (§0.5). У нас источник
   доступа привязан к человеку, и менять его за другого нельзя.
3. Нет approval-механизма и нет режима «сделай, но отчитайся» — только
   можно/нельзя, как и у n8n.

## 7. OpenAI Codex — enterprise-режим, sandbox × approvals

Источники:
- https://developers.openai.com/codex/agent-approvals-security
- https://developers.openai.com/codex/enterprise/admin-setup

### Как устроено

Безопасность разложена на **две независимые оси**, и документация явно это
подчёркивает:

- **Sandbox mode** — что агент может технически (куда писать, есть ли сеть).
- **Approval policy** — когда он обязан спросить, прежде чем действовать.

Режимы песочницы различаются по месту запуска. Codex cloud — изолированные
контейнеры OpenAI с **двухфазной моделью выполнения**: фаза setup имеет сеть
и ставит зависимости, затем фаза agent идёт офлайн по умолчанию; **секреты,
сконфигурированные для облачных окружений, доступны только во время setup и
удаляются до старта агентной фазы**. Локально (CLI/IDE) — песочница
средствами ОС: по умолчанию сети нет, запись ограничена рабочей директорией.

Approval policy — значения `on-request` и др.; ретированное значение
`untrusted` больше не поддерживается и может помешать запуску клиента.
Строгий режим теперь выражается через доверие проекту в `~/.codex/config.toml`:

```toml
[projects."/path/to/project"]
trust_level = "untrusted"
```

При этом project-local конфигурация отключается, а managed-политика
организации (`allowed_approval_policies`) задаёт, какие policy вообще
разрешены. Сеть управляется отдельно и двухступенчато: сначала
`sandbox_workspace_write.network_access`, затем опциональный прокси с
доменными правилами:

```toml
[features.network_proxy]
enabled = true
domains = { "api.openai.com" = "allow", "example.com" = "deny" }
```

Документация явно перечисляет комбинации: сеть выключена + прокси включён →
прокси ничего не делает; сеть включена + прокси выключен → неограниченный
исходящий доступ. То есть фича меняет способ enforcement, но сама доступ не
выдаёт. Есть также «автоматический разбор approval» — отдельный слой,
оценивающий конкретные действия, требующие подтверждения, и мониторинг
безопасности, оценивающий поведение модели в течение задачи (это разные
вещи: одобренное действие может входить в задачу, которую мониторинг позже
остановит).

Админский слой: доступ к Codex cloud выдаётся через workspace-контролы, но
**Codex уважает права репозиториев исходной системы — доступ к workspace их
не обходит**. Плагины, bundled skills, коннекторы и авторизация в
исходной системе рассматриваются как **отдельные решения**: отключение
возможности на базе коннектора не деинсталлирует плагин и его скиллы.
Наблюдаемость разведена по назначению: Workspace analytics, Analytics API
(агрегаты), Compliance API (аудит и расследования).

### Что забрать / чего избежать

**Забрать.**
1. **Sandbox × approval — две ортогональные оси** (§12 и §15.3 вместе).
   Подтверждает наше «права = пересечение»: режим (`deny/ask/account/allow`)
   отвечает на вопрос «когда спрашивать», compute — на вопрос «что вообще
   возможно». Их нельзя схлопывать в одну шкалу.
2. **Секреты доступны только в фазе setup и удаляются до агентной фазы.**
   Лучшая найденная техника против §9 (инъекции через контент): агент
   физически не имеет секрета в момент, когда читает недоверенный текст.
   Прямое применение к §15.3: «секреты монтируются в compute» стоит уточнить
   до «монтируются на фазу, а не на весь срок жизни процесса».
3. **Доступ к workspace не обходит права исходной системы.** Наш §11.6 в
   другой формулировке: членство в организации не заменяет владение
   ресурсом. Хороший принцип для §14: платформа не может выдать больше, чем
   выдал владелец нижележащей системы.
4. **Managed-политика задаёт множество допустимых политик**
   (`allowed_approval_policies`), а не одно значение. Для §13.4 («роль
   влияет на режим, а не только на можно/нельзя») это готовая механика:
   роль сужает диапазон допустимых режимов, конкретный выбор остаётся за
   человеком.
5. **Явная таблица комбинаций сеть × прокси.** Нам нужна такая же для пар
   (режим, compute): документировать, что происходит при каждом сочетании, —
   требование §12.4.
6. **Плагин, скиллы, коннектор и авторизация — отдельные решения.**
   Совпадает с §14.3 (плагин лишь объявляет требование), и защищает от
   ложного чувства, что «выключил коннектор — убрал доступ».
7. **Разделение мониторинга поведения и одобрения действий.** Одобренное
   действие может входить в задачу, которую мониторинг остановит. Это наш
   §12.2 «накопление»: повторяющиеся события поднимают вопрос автоматически.

**Избежать.**
1. Одобрение локально принимает сам пользователь за себя — это годится для
   персонального инструмента, но не для §11.4, где спрашивают **владельца
   ресурса**, а не инициатора задачи.
2. Понятия «на чьём топливе» нет: расход привязан к workspace-кредитам.
   §0.5 остаётся нашей задачей.

## 8. Claude Code — managed settings

Источники:
- https://docs.claude.com/en/docs/claude-code/settings
- https://docs.claude.com/en/docs/claude-code/iam

### Как устроено

Иерархия источников настроек с явным приоритетом: managed (организационные,
через managed settings file, MDM-профиль или кешированные server-managed
settings) → командная строка (`--settings`) → пользовательские → проектные →
локальные. `/status` показывает, какой источник выиграл.

Несколько содержательных правил, важных именно для модели доступа:

- **Security-ключи сохраняют строгое значение из любого файла**: если
  проектный файл ставит `disableClaudeAiConnectors: true`, это остаётся,
  даже если уровень выше разрешает. То есть для ключей безопасности
  побеждает не приоритет, а строгость.
- **`permissions.defaultMode` со значениями `auto` и `bypassPermissions` не
  действует из проектных и локальных настроек** — только из пользовательских
  или managed. Раньше (до v2.1.257) `bypassPermissions` работал из любого
  файла; это чинили.
- **`permissions.allow` применяется только после того, как участник доверил
  папку, а `deny` и `ask` действуют сразу.** Асимметрия намеренная:
  разрешения из чужого репозитория ждут доверия, запреты — нет.
- Часть ключей вообще не применяется из общего репозиторного файла (scope
  User/managed/Global config).

Credentials: сессионный OAuth-профиль (рекомендуется, автообновляемый) или
статический API-ключ (legacy). Профиль привязан к логину человека; при
провале обновления запросы падают с «Anthropic profile login expired».
`forceLoginOrgUUID` / `forceLoginMethod` в managed-настройках принуждают к
способу входа. Есть federation-профили, которые sign-in отказывается
перезаписывать.

### Что забрать / чего избежать

**Забрать.**
1. **`deny` и `ask` применяются немедленно, `allow` — только после доверия.**
   Это самое ценное здесь и прямо ложится на §12: наши четыре режима должны
   наследоваться асимметрично. Ужесточение принимается от кого угодно,
   ослабление — только от доверенного источника. Иначе §0.6 («автор функции
   не напишет проверку») превращается в «автор функции выпишет себе `allow`».
2. **Строгое значение побеждает приоритет для security-ключей.** Для нас:
   режим действия — это минимум по всем источникам (роль, compute, grant,
   политика проекта), а не значение самого приоритетного. Формализует
   §15.3 «права = пересечение».
3. **Опасные режимы недоступны из репозиторного файла.** Аналог: `bash`,
   `eval` и `bypass` нельзя включить из кода проекта — только из
   организационной политики или настроек compute (§15.3).
4. **Исторический баг как урок**: `bypassPermissions` когда-то работал из
   любого файла. Подтверждает, что «источник настройки» — это часть модели
   безопасности, и её надо задавать сразу, а не чинить потом.
5. **OAuth-профиль вместо статического ключа, привязанный к человеку.**
   §0.5: подписка принадлежит человеку; протухание логина — нормальное
   состояние, которое система обязана внятно сообщать, а не молча
   переключаться на другой источник.
6. **`/status`, показывающий выигравший источник.** Обязательная вещь для
   §12.4: человек должен видеть, почему действие получило именно этот режим.

**Избежать.**
1. Модель по-прежнему персональная: это настройки одной машины одного
   человека, а не организационная модель ресурсов. Понятий проекта-как-
   владельца, гранта и «от чьего имени» нет.
2. Сложность иерархии источников (managed/CLI/user/project/local + scope +
   исключения + расписание доставки) — реальная цена. Нам нужно **меньше
   уровней**, иначе §12.4 («режим определяется в ядре») станет
   недиагностируемым.

## 9. Cursor Cloud (background) Agents

Источники:
- https://cursor.com/docs/cloud-agent/security-network
- https://docs.cursor.com/en/account/agent-security

### Как устроено

Агент исполняется в изолированной VM в инфраструктуре Cursor (AWS), код
хранится на диске VM, пока агент доступен. GitHub App с правами
read-write на выбранные репозитории. Интернет по умолчанию есть, но есть
egress-контроль по доменам для пользователей, команд и сохранённых окружений.

Самое интересное — **три класса секретов, различаемых по видимости для
агента**:

| Тип | Кому виден | Назначение |
|---|---|---|
| Environment Variable | виден агенту | неконфиденциальная конфигурация: флаги, публичные URL |
| Runtime Secret | загружается как env, но **вырезается из результатов tool call, транскрипта, коммитов и сообщений коммитов**, заменяется на `[REDACTED]` | чувствительные credentials |
| Build Secret | доступен только процессу docker build, **не попадает в окружение работающего агента** | приватные реестры пакетов |

Документация честно указывает границу: Runtime Secret остаётся обычной
переменной окружения внутри процесса, поэтому **пользователь, зашедший в
терминал окружения агента, его увидит** — скрыт он только от модели.

Вместо долгоживущих ключей рекомендуются **OIDC-токены**: агент запрашивает
подписанный Cursor JWT через локальный сокет и предъявляет его AWS, GCP,
Azure, Vault или любому OIDC-верификатору. Коммиты подписываются HSM-
хранимым Ed25519-ключом и получают бейдж Verified на GitHub/GitLab —
происхождение коммита проверяемо. Админы команды могут «запереть» git-
организацию за своей организацией Cursor (Protected Git Scopes), так что
запускать агентов на её репозиториях могут только их команды. Есть
политика удержания данных (Indefinite / 90 дней) на уровне команды.
Приватный доступ — не через размещение у себя, а через Tailscale или
Cloudflare Tunnel внутри окружения агента, то есть исходящим соединением.

### Что забрать / чего избежать

**Забрать.**
1. **Классификация секретов по видимости для модели, а не только по
   чувствительности** (§15.3, §8.2). У нас в §15.3 сказано «секреты
   монтируются в compute, а не глобальны»; Cursor добавляет вторую ось:
   даже смонтированный секрет может быть скрыт от LLM. Runtime Secret —
   это фактически наш исходящий фильтр (§8.2), но применённый к
   транскрипту, коммитам и результатам инструментов. Стоит взять список
   мест, где надо редактировать: tool results, транскрипт, коммиты,
   сообщения коммитов.
2. **Build-секреты, недоступные работающему агенту.** То же, что двухфазная
   модель Codex: у секрета есть фаза жизни, а не только место.
3. **Короткоживущие OIDC-токены вместо долгих ключей.** Для §11.3
   (grant с фильтром и сроком) это реализуемая техника: платформа выдаёт
   подписанный JWT на конкретное действие, а ресурс проверяет его сам.
   Снимает проблему «отзыв не возвращает уже прочитанное» хотя бы для
   будущих вызовов: токен и так протухает.
4. **Подписанные коммиты с проверяемым происхождением** (§12.2). Событие
   «кто сделал» получает криптографическое, а не журнальное подтверждение.
   Для нашей ответственности человека (§12.3) это правильное направление.
5. **Protected Git Scopes.** Ресурс (git-организация) заявляет, кто вправе
   запускать над ним агентов, — то есть право приходит со стороны владельца
   ресурса, а не со стороны платформы (§11.4).
6. **Приватный доступ исходящим соединением (Tailscale/Cloudflare Tunnel),
   а не входящим.** Полезно для §15.6: личный compute может участвовать, не
   принимая входящий трафик; «ноутбук выключен ночью» остаётся нормой.

**Избежать.**
1. **Иллюзия «секрет скрыт»**: Runtime Secret не виден модели, но виден в
   терминале. Если у агента есть `bash` (§0.6), редактирование в
   транскрипте — косметика. Вывод для §12: `bash`/`eval` и «скрытые от
   модели секреты» на одном compute несовместимы; это должны быть разные
   compute.
2. **Интернет по умолчанию включён.** Наш дефолт обязан быть обратным
   (ср. Codex: агентная фаза офлайн), иначе §8.2 не имеет смысла.
3. Модель владения — команда и пользователь, но нет понятия действия от
   имени другого человека и нет approval-механизма для чужих ресурсов.

## 10. Zapier Agents / Central — анти-пример шаринга подключений

Источники:
- https://help.zapier.com/hc/en-us/articles/8496326497037-Share-app-connections-with-members-of-your-Team-or-Enterprise-account
- https://help.zapier.com/hc/en-us/articles/39268320740749-Give-other-Zapier-users-access-to-your-agent

### Как устроено

App connection (подключённый аккаунт стороннего сервиса) по умолчанию
приватен. На планах Team/Enterprise его можно расшарить конкретным людям,
командам или «всем» в аккаунте. Получив доступ, человек может: **смотреть
данные, использованные при тестировании Zap**, использовать подключение в
своих собственных Zap (в том числе приватных), и редактировать шаги чужих
Zap, где оно используется. Владение подключением можно передать другому
участнику.

Документация сама формулирует предупреждение и обходной путь: делитесь
подключением только с теми, кому вы готовы дать доступ; **вместо того чтобы
шарить свой почтовый аккаунт, заведите отдельный общий аккаунт вроде
`zapier@yourcompany.com`** и шарьте его.

У агентов — роли Owner / Editor / Viewer. Важная деталь: **Viewer может
тестировать, запускать и общаться с агентом**, а также видеть всю статистику
использования; он лишь не может менять инструкции и инструменты. То есть
«только чтение» для агента означает право его исполнять.

### Что забрать / чего избежать

**Забрать.**
1. **Признание проблемы самой документацией**: рекомендация завести
   отдельный сервисный аккаунт — это косвенное подтверждение §11.3. Если
   единственный безопасный способ поделиться доступом — создать другой
   аккаунт, значит модель «шарить подключение» неверна, и надо шарить
   *действие*, а не *носитель доступа*.
2. **Передача владения подключением** как явная операция — полезный
   примитив для §14.5 (уход носителя из организации): грант не должен
   молча умирать, у него может быть процедура передачи.

**Избежать (главный урок раздела).**
1. **Шаринг подключения = отдача личного доступа.** Получатель использует
   мой аккаунт в своих приватных сценариях и видит данные тестов. Это ровно
   то, что §11.6 запрещает: членство в команде превращается в доступ к
   личному ресурсу. Наш ответ — grant на узкое действие с фильтром и сроком
   (§11.3), а не передача носителя.
2. **«Поделиться со всеми» одним чекбоксом.** Операция, необратимая по сути
   (§6, правило 3: отзыв не возвращает прочитанное), не должна быть
   одним кликом без адресата и срока.
3. **Viewer, который может запускать агента.** Опасная семантика: право
   «смотреть» даёт право вызывать побочные эффекты чужими руками. У нас
   (ср. n8n, где Viewer явно не может запускать) право исполнения — всегда
   отдельное от права чтения, и оно попадает в §12 как минимум в `account`.

## 11. OpenHands (All Hands AI)

Источники:
- https://github.com/OpenHands/OpenHands (README)
- https://github.com/OpenHands/OpenHands-Cloud
- https://docs.openhands.dev/

### Как устроено

Опенсорсная платформа для агентов, пишущих код. Архитектурно ценно то, что
**backend, на котором исполняется агент, — переключаемая сущность**:
локально, в Docker, на VM, на сервере в облаке. Из одного фронтенда
(Agent Canvas) можно переключаться между локальным, удалённым и облачным
backend «не теряя фокуса», и можно **разделить Agent Server с командой** для
агентов, которым нужно работать постоянно. Мотивация в README прямая:
агенты продолжают работать, когда ноутбук закрыт, и их проще триггерить из
Slack, GitHub, Datadog.

Поддерживается ACP (Agent-Client Protocol), то есть один и тот же
пользовательский слой работает с OpenHands, Claude Code, Codex, Gemini —
агент-исполнитель не привязан к платформе. Есть автоматизации по расписанию
и по webhook, интеграции со Slack, GitHub, Linear, Notion. LLM настраивается
профилями (`LLM profiles`), то есть источник модели — именованная сущность.
Self-hosting описан отдельным документом с оговоркой про hardening.

Про организационную модель (org/team/роли, владение credentials между
пользователями, approval чужих ресурсов) в публичной документации и README
**деталей найти не удалось** — self-hosted вариант описан как «поднимите
свой сервер», а enterprise-модель доступа в открытых источниках не
детализирована. Отмечаю как не найденное, а не как отсутствующее.

### Что забрать / чего избежать

**Забрать.**
1. **Backend как переключаемая сущность при неизменном интерфейсе** — это
   наш §15.2 compute, подтверждённый работающим продуктом. Особенно совпадает
   §15.6: агенты на личной машине и на общем сервере сосуществуют, и
   выключенный ноутбук — мотивация, а не ошибка.
2. **Общий Agent Server для команды рядом с личным** — ровно наша пара
   `kind: server` / `kind: personal` (§15.2).
3. **ACP: агент-исполнитель отделён от платформы.** Полезно для §0.4:
   раз у нас несколько провайдеров и подписок, интерфейс задачи не должен
   зависеть от того, чей агент её исполняет.
4. **LLM profiles как именованная сущность** — шаг к §0.5 («откуда берётся
   доступ и кто платит»), хотя привязки профиля к человеку и учёта топлива
   в документации не описано.

**Избежать / открытый вопрос.**
1. Явной модели «чей credential» между пользователями в открытых источниках
   не нашёл. Пример того, что шаринг backend между людьми без модели
   владения секретами — это §15.6 «соседство на одной машине — это риск».
   Если несколько человек делят Agent Server, вопрос «чьи секреты там
   смонтированы» обязан иметь ответ; у нас он есть, здесь — не найден.

## 12. Lindy

Источник: https://docs.lindy.ai/account-billing/teams-collaboration

### Как устроено

Workspace с ролями Member / Admin. Два пути вступления: приглашение
админом из настроек команды и **самостоятельное присоединение через
@mention Lindy в Slack** — человек упоминает бота, получает кнопку
«Connect Slack to Lindy», привязывает Slack-идентичность к аккаунту Lindy
(аккаунт создаётся под этим workspace, если его не было), после чего его
исходное сообщение автоматически переигрывается. Место в биллинге
занимается сразу при приглашении и после бесплатной первой недели — при
самоприсоединении.

Экономика: у каждого участника план (Plus/Pro/Max), и план **добавляет
кредиты в общий пул workspace**. Все участники черпают из общего пула.

Технических деталей модели доступа (владение коннекторами, разграничение
секретов между участниками, approval) в публичной документации найти не
удалось.

### Что забрать / чего избежать

**Забрать.**
1. **Привязка внешней идентичности (Slack) к внутреннему аккаунту как явный
   акт человека** с кнопкой подтверждения — корректный паттерн для §5
   (личность и вход) и §8 (внешние участники): идентичность связывает сам
   человек, а не администратор за него.
2. **Переигрывание исходного сообщения после привязки** — приятная деталь
   UX: запрос не теряется, пока разрешение оформляется. Применимо к §11.4:
   задача ждёт решения владельца, а не падает.

**Избежать (главный урок).**
1. **Общий пул кредитов** — прямое противоречие §0.5. Человек покупает план,
   кредиты уходят в общий котёл, и «на чьём топливе выполнен вызов»
   перестаёт иметь ответ. Именно этот дизайн наш §0.5 запрещает: у вызова
   должен быть не только автор, но и владелец топлива.
2. **Самоприсоединение через упоминание бота** создаёт участника (и списание)
   без решения администратора. Для организационной платформы вход в
   организацию — административный акт (§13.2).

## 13. Letta / MemGPT

Источники:
- https://github.com/letta-ai/letta (README, main)
- https://docs.letta.com/guides/agents/multi-user

### Как устроено

Важный факт о состоянии репозитория: **`letta-ai/letta` больше не содержит
основного кода**. README указывает, что актуальный исходник живёт в
`letta-ai/letta-code` (агентный harness, терминальный UI, App Server,
каналы, рантайм для desktop и web), а ветка `archive` содержит вышедший из
употребления сервер Letta V1 API. Клонирование main даёт только документы —
проверено (`git clone --depth 1`, в дереве лишь markdown-файлы).

Модель многопользовательности в Letta построена на **identities**: сущность,
представляющая конечного пользователя приложения, к которой привязываются
агенты и блоки памяти. Типичный сценарий из документации — приложение с
множеством своих пользователей (multi-user chatbot с Supabase), где
identity разделяет состояние и память агентов между конечными
пользователями.

То есть это **мультиарендность приложения, а не организации**: identity —
это про то, чью память видит агент, а не про то, чьи полномочия он
использует. Модели ролей, владения credentials между сотрудниками и
approval-механизма в этой модели не предусмотрено — это другой класс задачи.

### Что забрать / чего избежать

**Забрать.**
1. **Identity как срез состояния** — полезное различение для §6: «чья
   память» и «чьи права» — независимые измерения. У нас комната и грант
   отвечают за права, но вопрос «какой контекст видит агент, работая с
   разными людьми» тоже нуждается в носителе.
2. Косвенное подтверждение §11.5: разделять надо не только доступ, но и
   накопленное агентом состояние. Наше правило «сырые письма не попадают в
   общий контекст проекта» — это та же проблема с другой стороны.

**Избежать.**
1. **Не переносить identity-модель как модель доступа.** Она отвечает на
   вопрос «за кого агент помнит», а не «что агенту позволено». Для §11
   (кортеж из пяти носителей прав) identity покрывает только одно измерение.
2. Отсутствие организационных сущностей подтверждает: библиотека агентов ≠
   платформа организации, и §0.2 (мы строим второе) означает, что готовую
   модель здесь взять неоткуда.

## 14. AutoGen Studio (Microsoft)

Источники:
- https://github.com/microsoft/autogen/blob/main/python/packages/autogen-studio/autogenstudio/datamodel/db.py
- https://microsoft.github.io/autogen/stable/user-guide/autogenstudio-user-guide/faq.html

### Как устроено

Схема (SQLModel) читается за минуту и показательна. Базовый класс
`BaseDBModel` даёт всем таблицам `id`, `created_at`, `updated_at`, `version`
и **`user_id: Optional[str] = None`** — просто необязательную строку.
Таблицы: `Team`, `Session`, `Run`, `Message`, `Gallery`, `Settings`, плюс
eval-таблицы. Связи — обычные FK с `ondelete="CASCADE"`; конфигурация
агентов и команд лежит в JSON-колонках (`component`) как декларативные
спецификации компонентов.

Хранилище по умолчанию — **SQLite-файл** в каталоге, задаваемом
`--appdir`. Модели задаются `model_client`-конфигурацией, в которой
`api_key` присутствует **прямо в JSON-спецификации компонента** (примеры в
FAQ содержат `"api_key": "sk-..."`).

То есть: понятий организации, workspace, ролей, проверки прав, разграничения
секретов между пользователями — нет. `user_id` — это дискриминатор строк в
однопользовательском по сути инструменте, а не модель доступа.

### Что забрать / чего избежать

**Забрать.**
1. **Декларативные спецификации компонентов в JSON** (`dump_component()`),
   которые можно перенести между средами, — удобный формат для §14.3
   (плагин объявляет свои требования декларативно) и §15.6 (деплоймент как
   данные, а не как код).
2. Пример минимальной схемы прогона: `Session → Run → Message` со статусом
   у Run — близко к нашей inline-очереди в `agents`.

**Избежать (это основной вклад раздела).**
1. **`user_id` как необязательная строка без FK и без политик** — ровно
   вариант A из §3 («один процесс, owner_id везде»), который DESIGN.md
   отверг. AutoGen Studio показывает, чем он заканчивается: поле есть,
   модели доступа нет, и ничто не мешает его не проставить.
2. **API-ключ внутри конфигурации компонента.** Секрет становится частью
   данных, которые копируются, экспортируются в Gallery и попадают в
   контекст. Противоречит §15.3 («секреты монтируются в compute») и §8.2
   (исходящий фильтр). Наш вывод: конфигурация ссылается на секрет по имени,
   но никогда не содержит его значения.
3. **SQLite-файл как хранилище.** Несовместимо с §0.1 и §15.7: нет ни общей
   ленты событий, ни общего аудита, ни RLS. Инструмент для одного человека.

## 15. Devin / Cognition (enterprise)

Источник: https://docs.devin.ai/enterprise/security-access/security/enterprise-security

### Как устроено

Публичная enterprise-документация посвящена **security posture, а не модели
доступа**: шифрование в транзите и покое, мониторинг продакшена, MFA и
ежегодное обучение сотрудников, SOC 2 Type II с сентября 2024, программа
раскрытия уязвимостей, политика хранения данных.

Содержательные для нас пункты всего два:

- **Обработка данных зависит от способа взаимодействия.** В веб-приложении
  обрабатываются только данные, которые активно предоставил авторизованный
  пользователь. Для интеграций — **администратор, устанавливающий интеграцию,
  может просмотреть и управлять всеми правами, выданными Devin**.
- Для enterprise-клиентов с выделенным развёртыванием **все данные клиента
  хранятся в тенанте клиента**.

Технических деталей организационной модели (сущности org/team, владение
credentials между пользователями, механизм approval на действие, «от чьего
имени») в публичной документации **найти не удалось**. Фиксирую как не
найденное.

### Что забрать / чего избежать

**Забрать.**
1. **Права интеграции обозримы и управляемы устанавливающим админом.**
   Слабая, но верная форма §14.5: полномочие, выданное автоматизации,
   должно быть видимым списком, а не набором молчаливых scope'ов.
   Наше требование сильнее: «виден всем участникам проекта», а не только
   установившему.
2. **Выделенный тенант для данных клиента** — то же соображение, что §15.8
   («когда общая БД не годится»): есть класс данных, для которого
   изоляция хранилища — требование, а не оптимизация.

**Избежать.**
1. **Разница между «мы защищены» и «вот модель доступа».** SOC 2 и
   шифрование не отвечают на вопрос §11.2 (кто × от чьего имени × в каком
   проекте × над чьим ресурсом × на чьём топливе × на каком compute).
   Для нас это напоминание: аудиты не заменяют модель, и §12
   (ответственность) — это продуктовое требование, а не комплаенс.
2. Единственный субъект прав — администратор, установивший интеграцию.
   Владелец затронутого ресурса в этой картине не участвует (§11.4).

## 16. Синтез: что это меняет в DESIGN.md

### 16.1 Подтверждённые положения (не трогать)

| Положение | Кем подтверждено |
|---|---|
| §0.1 граница — GRANT/RLS в Postgres, а не проверки в коде | Windmill: RLS на 8+ таблицах, `current_setting('session.user')` |
| §11.3 credential принадлежит человеку, а не платформе | n8n end-user credentials (лучшая реализация) |
| §11.6 членство в проекте ≠ доступ к личным ресурсам | n8n (админ не видит содержимое), Codex (не обходит права SCM) |
| §15.2 compute как отдельная сущность | Temporal namespaces, OpenHands switchable backends |
| §15.3 права = пересечение | Codex: sandbox × approval — ортогональные оси |
| §15.7 compute и storage — разные абстракции | LangGraph: control plane / data plane / общая observability |
| §0.5 топливо привязано к человеку | Lindy — от противного: общий пул кредитов теряет владельца |
| §12 нужен режим между deny и allow | n8n и CrewAI: без него автономность упирается в общий credential |

### 16.2 Конкретные изменения, которые стоит внести

1. **§11.7 — добавить `permissioned_as` в очередь.** У Windmill это колонка
   в `queue`/`completed_job`, по которой работает RLS. У нас очередь живёт
   inline в `agents`; добавить туда «от чьего имени» и фильтровать по нему.
   Без этого §12.3 («у каждой фоновой работы есть владелец») не имеет
   технического носителя.

2. **§12 — сформулировать правило комбинирования режимов как минимум, а не
   как приоритет.** Из Claude Code: для security-ключей побеждает строгое
   значение из любого источника, а не значение самого приоритетного.
   Формулировка для нас: итоговый режим = самый строгий среди (роль,
   grant, политика проекта, capabilities compute). И асимметрия:
   `deny`/`ask` принимаются от любого источника немедленно, `allow` —
   только от доверенного (не из кода проекта).

3. **§15.3 — уточнить «секреты монтируются в compute» до «на фазу».**
   Из Codex (секреты только в setup-фазе, удаляются до агентной) и Cursor
   (build secrets). Секрет имеет не только место, но и окно жизни. Это
   самая дешёвая защита от §9 (инъекции через контент): в момент чтения
   недоверенного текста секрета в процессе уже нет.

4. **§8.2 — взять у Cursor конкретный список мест редактирования.**
   Исходящий фильтр должен применяться к: результатам вызова инструментов,
   транскрипту, коммитам и сообщениям коммитов. И честно записать границу:
   если на том же compute есть `bash`/`eval`, редактирование в транскрипте —
   косметика (Cursor это признаёт про Runtime Secrets). Значит `bash` и
   «скрытые от модели секреты» — разные compute.

5. **§11.4 — approval как приостановка в БД, а не блокирующий вызов.**
   Из Windmill (suspend + resume-события + обязательный таймаут + ветка
   «отказано/истекло» + форма с JSON Schema). Ложится на наш `wakeUpWhen`.
   Но, в отличие от Windmill, возобновление обязано проверять личность
   одобряющего, а не только знание секретного URL.

6. **§14.5 — грант роли проекту держать в git.** Из Windmill: `extra_perms`
   трекается в исходниках и деплоится через git sync. «Этот проект пишет в
   CRM от имени Ани» становится ревьюабельным диффом, а не кликом в UI, и
   автоматически удовлетворяет требование «виден всем участникам проекта».

7. **§13 — добавить правило «для секретов нет read-only».** Из CrewAI:
   у environment_variables и llm_connections есть только Manage/No access.
   Шкала Viewer/Writer неприменима к носителям доступа; право «увидеть
   секрет» эквивалентно праву им воспользоваться.

8. **§15.6 — критерий, когда заводить новый compute.** Из Temporal:
   отдельный namespace берут тогда, когда граница арендатора обязана быть
   границей credential. Переводится в правило: **новый compute нужен ровно
   там, где нужен отдельный набор смонтированных секретов**; во всех
   остальных случаях достаточно тега/очереди. Плюс их цифра «namespace на
   арендатора практичен примерно до 50» — аргумент против инстанса на
   человека (вариант C из §3) в наивной форме.

9. **§11.3 — дефолт видимости `only_me`.** Из Dify (где дефолт `ALL_TEAM` —
   ошибка) и CrewAI (где Private — верно). Плюс взять у Dify саму шкалу
   `only_me / all_team / partial_members` как минимальный словарь и колонки
   `credential_type` (`api-key` | `oauth2`) и `expires_at` на подключении.

10. **§12.4 — показывать, почему действие получило этот режим.** Из Claude
    Code `/status`, называющего выигравший источник настройки. Если режим
    вычисляется в ядре из четырёх источников, человеку нужен ответ
    «почему `ask`, а не `allow`», иначе модель недиагностируема.

11. **§11.3 — рассмотреть короткоживущие OIDC-токены.** Из Cursor: агент
    минтит подписанный JWT через локальный сокет, ресурс верифицирует сам.
    Частично снимает боль «отзыв не возвращает уже прочитанное»: полномочие
    протухает само, и узость гранта подкрепляется сроком жизни токена.

12. **§14.3 — плагин, скиллы, коннектор и авторизация — отдельные решения.**
    Из Codex: отключение возможности на базе коннектора не деинсталлирует
    плагин и его скиллы. У нас §14.3 должен явно различать «плагин
    установлен», «возможность включена», «полномочие выдано».

### 16.3 Чего ни у кого нет (наша собственная работа)

Ни в одной из 15 изученных систем не найдено:

- **Режима `account`** («делай, но за событие отвечаешь») — везде только
  можно/нельзя плюс, иногда, approval. Это делает §12 нашим оригинальным
  вкладом и одновременно самым рискованным: образца для подражания нет.
- **Учёта «на чьём топливе»** (§0.5). Ближайшее — Lindy с общим пулом
  кредитов, то есть ровно противоположное решение. Cursor и Codex считают
  расход на команду/workspace, не на человека.
- **Спрашивания разрешения у владельца ресурса, а не у инициатора задачи**
  (§11.4). Везде approve даёт тот, кто запустил, либо администратор.
- **Запрета на запрос разрешения, инициированный недоверенным текстом**
  (§11.4) — нигде не встречено как явное правило.
- **Трёхуровневой лестницы «роль → грант роли проекту → одолженное
  полномочие в комнате»** (§14.5). Есть отдельные куски: роли (все),
  шаблон подключения (n8n), entity-level права (CrewAI), — но не связка.

### 16.4 Открытые вопросы после research

- **Не найдено** деталей организационной модели OpenHands (владение
  credentials при общем Agent Server) и Devin (модель доступа за пределами
  security posture). Если это важно — нужен доступ к enterprise-докам или
  прямой запрос вендору.
- **Не проверено на практике**: как RLS-подход Windmill ведёт себя при
  hot-reload и пользовательском коде в одном процессе (§0.6). Windmill
  исполняет скрипты в воркерах, а не в процессе API, — у нас это аргумент
  за то, что `eval` обязан уехать на отдельный compute.
- Актуальный код Letta переехал в `letta-ai/letta-code`; если identity-модель
  понадобится подробнее, смотреть надо там, а не в `letta-ai/letta`.

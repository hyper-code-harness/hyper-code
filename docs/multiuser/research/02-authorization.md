## 1. ReBAC и policy-движки

### 1.1 Google Zanzibar

**Как устроено.** Вся авторизация — это множество *relation tuples* вида
`⟨object⟩#⟨relation⟩@⟨user⟩`, где `object = namespace:object_id`, а `user` — либо
id пользователя, либо *userset* `object#relation`. То есть группа — это просто ACL
с семантикой членства, а не отдельная сущность. Отношения между отношениями
(«все editor являются viewer») не хранятся тапплами, а задаются *userset rewrite
rules* в namespace configuration: правило — функция от object_id, возвращающая
дерево userset-выражений (`this`, `computed_userset`, `tuple_to_userset`).
`tuple_to_userset` даёт наследование по иерархии («viewer родительской папки —
viewer документа»). Отдельно решена проблема причинности: клиент при изменении
контента получает *zookie* — закодированную глобальную метку времени, и передаёт
её в последующих check-запросах; это даёт «не старее чем» семантику и закрывает
«new enemy problem» (Alice убрала Bob из ACL папки, Charlie положил туда новые
документы — Bob не должен их увидеть). Масштаб по статье: >2 триллионов ACL,
95-й перцентиль <10 мс, доступность >99.999%.

- Источник: Pang et al., «Zanzibar: Google's Consistent, Global Authorization System», USENIX ATC '19 — https://www.usenix.org/system/files/atc19-pang.pdf

**Что забрать.** Две вещи. Первая — *userset как значение*: субъектом права может
быть не только человек, но и «все, кто состоит в таком-то отношении». Это ровно
наша §14: «комната обладает возможностью X, если ей обладает хотя бы один
участник» выражается как отношение, а не как копия прав. Вторая — *zookie* как
признание того, что проверка и данные живут во времени. У нас есть более жёсткий
аналог проблемы: §6 правило 3 («у LLM нет отзыва знания»). Zanzibar решает
причинность для чтения; нам нужно фиксировать не «когда проверили», а «что уже
утекло», — но идея «решение привязано к точке во времени, и это записывается»
переносится в аудит §12.2.

**Чего избежать.** Не строить у себя Zanzibar. Он глобально распределён, потому
что у Google миллиард пользователей; вся его сложность (Leopard-индекс, quantized
timestamps, шардирование) — цена этого масштаба. У нас одна организация и один
Postgres (§0.1). Брать модель данных — да, брать архитектуру — нет.
Раздел DESIGN.md: **§13, §14, §6**.

### 1.2 OpenFGA

**Как устроено.** Открытая реализация Zanzibar (CNCF, ex-Auth0). Модель пишется
на DSL: `type document / relations / define viewer: [user] or editor`. Схема
хранения в Postgres проверяемо простая — из миграции `001_initialize_schema.sql`:

```sql
CREATE TABLE tuple (
  store TEXT, object_type TEXT, object_id TEXT, relation TEXT,
  _user TEXT, user_type TEXT, ulid TEXT, inserted_at TIMESTAMPTZ,
  PRIMARY KEY (store, object_type, object_id, relation, _user)
);
CREATE INDEX idx_tuple_partial_user   ON tuple (...) WHERE user_type = 'user';
CREATE INDEX idx_tuple_partial_userset ON tuple (...) WHERE user_type = 'userset';
```
Плюс `authorization_model` (версионированная схема, BYTEA-протобуф), `store`,
`changelog` (журнал операций), и отдельной миграцией `003` — обратный индекс
`(store, object_type, relation, _user)` для ListObjects. Миграция `005` добавила
условия: `ALTER TABLE tuple ADD COLUMN condition_name TEXT, condition_context BYTEA`.
Условия (Conditions) — CEL-выражения, привязанные к типу субъекта:

```
type document
  relations
    define viewer: [user with non_expired_grant]

condition non_expired_grant(current_time: timestamp, grant_time: timestamp, grant_duration: duration) {
  current_time < grant_time + grant_duration
}
```

- Источники: https://github.com/openfga/openfga (assets/migrations/postgres/), https://openfga.dev/docs/modeling/conditions

**Что забрать.** Ровно две конструкции. Первая — таблица отношений на пять
колонок с составным PK и *частичными* индексами по типу субъекта; это прямой
шаблон для нашей таблицы grants (§11.7), у которой субъект тоже двух родов
(`agent` или `project`). Вторая, более важная — **Conditions**. Наш grant по
§11.3 — это «агенту проекта landing, чтение почты, фильтр: метка landing, до
1 марта». Это буквально caveated tuple: отношение существует, только если
контекст запроса удовлетворяет условию. То есть срок и фильтр гранта не нужно
проверять в коде плагина — они часть самой записи о праве.

**Чего избежать.** Известная больная точка — `ListObjects`: «перечисли всё, к чему
у пользователя есть доступ» разворачивается в обход графа и деградирует.
Открытые issue на момент чтения: #2828 (нет пагинации и continuation-token в
ListObjects), #3076 (нельзя перечислить объекты нескольких типов), #1961 (при
упирании в deadline пользователь не узнаёт об этом), #1561 (просят слой кэша
подзапросов); закрытый #942 — «terrible performance» на исключениях `but not`.
Вывод для нас: проектировать API как **точечный check** (можно ли этому агенту
это действие над этим ресурсом), а «покажи все ресурсы, доступные Ане» — считать
обычным SQL-запросом по нашей таблице, не через движок обхода графа.
Раздел DESIGN.md: **§11.3, §11.7**.

### 1.3 SpiceDB (AuthZed)

**Как устроено.** Второй Zanzibar-клон, но интереснее устроен на уровне Postgres.
Из миграции `0001`: `relation_tuple` с MVCC прямо в таблице —

```sql
CREATE TABLE relation_tuple (
  id BIGSERIAL, namespace VARCHAR, object_id VARCHAR, relation VARCHAR,
  userset_namespace VARCHAR, userset_object_id VARCHAR, userset_relation VARCHAR,
  created_transaction BIGINT NOT NULL,
  deleted_transaction BIGINT NOT NULL DEFAULT '9223372036854775807',
  CONSTRAINT uq_relation_tuple_living UNIQUE (namespace, object_id, relation,
    userset_namespace, userset_object_id, userset_relation, deleted_transaction)
);
```
Строки не удаляются: запись «умирает» установкой `deleted_transaction`, а
уникальность живой записи держится включением `deleted_transaction` в constraint.
Есть `relation_tuple_transaction` — собственная лента транзакций, на которой
работает Watch API и GC. Миграция `0009` добавила caveats: таблица `caveat(name,
definition BYTEA, ...)` плюс `relation_tuple.caveat_name VARCHAR, caveat_context
JSONB`. Миграция `0021` добавила `expiration TIMESTAMPTZ DEFAULT NULL` прямо в
relation_tuple, `0022` — индекс по нему. Более поздние миграции (`0010`–`0014`)
— переезд с bigserial на `xid8`.

- Источник: https://github.com/authzed/spicedb (internal/datastore/postgres/migrations/), https://authzed.com/docs/spicedb/concepts/caveats

**Что забрать.** Три конкретных инженерных решения, которые ложатся на наш
Postgres напрямую:
1. **Грант никогда не удаляется, а «умирает»** — `deleted_transaction` / `revoked_at`
   в PK. Для §11.3 это критично: отзыв гранта не возвращает прочитанное, значит
   история грантов сама по себе — аудит-материал, и физический DELETE её уничтожает.
2. **`expiration TIMESTAMPTZ` отдельной колонкой и индексом**, а не внутри
   выражения условия. Срок гранта (§11.3, «до 1 марта») — самый частый фильтр;
   он должен быть колонкой.
3. **`caveat_context JSONB` рядом с записью** — наш «фильтр гранта» (метка,
   30 дней) хранится как JSONB при самом гранте.

**Чего избежать.** Собственная MVCC-лента транзакций поверх Postgres-MVCC —
это дорого и породило у них цепочку миграций (xid8, GC-индексы, tuned GC).
Нам не нужна распределённая консистентность: у нас один кластер, хватает
обычной транзакции.
Раздел DESIGN.md: **§11.3, §11.7, §12.2**.

### 1.4 AWS Cedar / Amazon Verified Permissions

**Как устроено.** Cedar — язык политик (Rust, открыт) плюс верифицированный
движок. Политика — `permit`/`forbid` с тройным scope и условиями:

```cedar
permit (principal == User::"alice", action == Action::"view",
        resource in Album::"jane_vacation");
```
Сущности типизированы (`User::"alice"`), имеют атрибуты и родителей (`parents`),
что даёт иерархию через оператор `in`. Условия — `when { ... }` / `unless { ... }`.
`forbid` всегда побеждает `permit`. Отдельная фича — **policy templates**:
политика с плейсхолдерами `?principal` / `?resource`, которая затем
«линкуется» в template-linked policy с конкретными значениями. В репозитории есть
`cedar-policy-symcc` — символический компилятор для верификации свойств политик
с контрпримерами.

- Источники: https://github.com/cedar-policy/cedar, https://docs.cedarpolicy.com/policies/syntax-policy.html, https://docs.cedarpolicy.com/policies/templates.html

**Что забрать.** Две вещи. Первая — **`forbid` сильнее `permit`**, безусловно.
У нас это §12: `deny` (необратимое, чужое, `bash`/`eval` для гостя) должен быть
не «самым приоритетным правилом», а отдельным слоем, который невозможно
перекрыть ни ролью, ни грантом. Вторая — **templates как модель гранта**: «Коля
выдал право на свой ящик агенту landing» — это инстанцирование шаблона «владелец
даёт чтение своего ресурса субъекту X до срока Y», а не свободно написанная
политика. Это делает грант структурой данных, а не текстом.

**Чего избежать.** Их же документация честно предупреждает: templates жёстко
связывают policy store с жизненным циклом пользователей — при смене роли надо
найти, заархивировать и пересоздать все связанные политики, а если удалить
вместо архивации, теряется историческая запись «кому что было можно», нужная
для разбора инцидентов. Прямое подтверждение нашего решения из §13: роль как
отдельная сущность, а не как набор сгенерированных персональных правил.
Раздел DESIGN.md: **§12, §13.5**.

### 1.5 Casbin

**Как устроено.** Движок на конфиге в INI: модель отдельно, политика отдельно.

```ini
[request_definition] r = sub, obj, act
[policy_definition]  p = sub, obj, act
[role_definition]    g = _, _
[policy_effect]      e = some(where (p.eft == allow))
[matchers]           m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
```
Политики — строки `p, alice, data1, read` и `g, alice, data2_admin`. Несколько
независимых RBAC-систем одновременно (`g`, `g2` — роли пользователей и роли
ресурсов). Есть RBAC with Domains (роль в пределах tenant'а).

- Источники: https://github.com/casbin/casbin, https://casbin.org/docs/rbac

**Что забрать.** Идею **RBAC with Domains** — роль осмысленна не глобально, а в
пределах области. У нас область — проект: `lead` в landing ≠ `lead` везде. Это
прямо §13.2 (уровни ролей). И разделение «модель» / «политика»: набор возможных
режимов задаётся один раз, конкретные записи — данные.

**Чего избежать.** Matcher как строка выражения, интерпретируемая в рантайме, —
авторизация становится нетипизированной и непроверяемой; ошибка в matcher'е
молча открывает доступ. Для нас это особенно опасно из-за §0.6 (код пишется
внутри системы): выражение в конфиге — тот же недоверенный код. Наша граница —
`GRANT` в Postgres (§15.7), а не строка-матчер.
Раздел DESIGN.md: **§13.2, §15.7**.

### 1.6 Oso

**Как устроено.** Библиотека авторизации с языком политик Polar (Prolog-подобный,
ядро на Rust), встраиваемая в приложение; умеет не только yes/no, но и *data
filtering* — превращать политику в условие выборки («покажи только записи,
которые Juno может видеть»). **Важный факт: open-source библиотека помечена
авторами как deprecated** — в README первым разделом стоит «# Deprecated», развитие
ушло в коммерческий Oso Cloud.

- Источник: https://github.com/osohq/oso/blob/main/README.md

**Что забрать.** Понятие *authorization-aware data filtering*: правило должно уметь
компилироваться в предикат выборки, а не только отвечать на вопрос про один объект.
В Postgres это ровно RLS (§2.1) — то есть Oso подтверждает выбор, а не добавляет.

**Чего избежать.** Собственно, сам сюжет: универсальный встраиваемый
authz-фреймворк с своим языком оказался нежизнеспособен как OSS. Ещё один
аргумент против «сделаем свой движок политик» (§13.5).
Раздел DESIGN.md: **§13.5**.

### 1.7 ReBAC vs RBAC: как ложится на наш дизайн

Наблюдение по итогам 1.1–1.6. Все ReBAC-системы выражают и роль, и грант одной
конструкцией — отношением. Но семантически это разные вещи, и наш §13.1
разделяет их правильно:

| | Роль (§13) | Grant (§11) |
|---|---|---|
| ReBAC-выражение | `project:landing#lead@user:anya` | `mailbox:kolya#reader@agent:landing` + caveat |
| Кто вносит | организация/владелец проекта | владелец ресурса, лично |
| Ресурс | общий (репозиторий, CRM) | личный |
| Срок | бессрочно, пока в проекте | обязателен (§11.3) |
| Фильтр | нет | обязателен (метка, период) |

То есть: одна таблица отношений технически возможна, но **грант обязан нести
caveat (условие) и expiration, а роль — нет**. Если сделать их одной сущностью
без этого различения, грант деградирует до роли и потеряет узость, которая
по §11.3 важнее отзываемости.

## 2. Postgres-native: RLS, роли, GRANT, пулы

Это самый важный раздел для нас, потому что §15.7 постулирует: граница —
`GRANT`, а не проверка в коде.

### 2.1 Row Level Security

**Как устроено.** `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` — и весь доступ к
таблице должен быть разрешён какой-нибудь политикой; если политик нет,
действует **default-deny** (ничего не видно). Политики создаются `CREATE POLICY`,
привязываются к командам (ALL/SELECT/INSERT/UPDATE/DELETE) и к ролям. Ключевые
детали из документации PostgreSQL 17:

- Несколько политик комбинируются через **OR для permissive** (по умолчанию) и
  **AND для restrictive**. То есть добавить ограничение можно только
  restrictive-политикой; ещё одна permissive-политика доступ только расширяет.
- **Суперпользователи и роли с `BYPASSRLS` всегда обходят RLS.** Владелец таблицы
  тоже обходит — если только не `ALTER TABLE ... FORCE ROW LEVEL SECURITY`.
- Выражение политики выполняется **с правами вызывающего**, до условий запроса.
  Исключение — `leakproof`-функции: оптимизатор вправе применить их *раньше*
  проверки строки. Это канал утечки: не-leakproof функция в предикате не будет
  поднята, но leakproof-функция может выполниться над строками, которых
  пользователь видеть не должен.
- `TRUNCATE` и `REFERENCES` под RLS не попадают вообще.
- Включать RLS и создавать политики может только владелец таблицы.

- Источники: https://www.postgresql.org/docs/17/ddl-rowsecurity.html, https://www.postgresql.org/docs/17/sql-createpolicy.html

**Грабли производительности** (задокументированы, с цифрами):
1. **Индекс на колонки, участвующие в RLS**, если они не PK/unique — «improvement
   seen over 100x on large tables».
2. **Оборачивать функции в `select`**: `(select auth.uid()) = user_id` вместо
   `auth.uid() = user_id`. Обёртка заставляет планировщик сделать initPlan и
   вычислить значение один раз, а не на каждую строку.
3. **JOIN внутри RLS-предиката тянет за собой RLS присоединяемой таблицы** —
   вложенная проверка на каждую строку. Обходится `SECURITY DEFINER`-функцией,
   которая обходит RLS целевой таблицы.
4. `SECURITY DEFINER`-функцию, принимающую поле строки параметром, обернуть в
   `select` нельзя — кэширования не будет.

- Источник: https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices-Z5Jjwv

**Что забрать.** RLS — единственный механизм, который делает §15.7 («проверка в
коде — обещание, `GRANT` — граница») правдой при общей базе. Конкретно: таблицы
платформы (agents, messages, events, grants) получают RLS, и агент, написанный
пользователем по §0.6, физически не увидит чужие строки, даже если забудет
проверку. Восемь строк политики заменяют дисциплину, которой не будет.
Практические выводы: предикаты строить на **колонке-владельце с индексом**, а
не на джойнах; всё, что можно, — через `(select ...)`; ограничения добавлять
**restrictive**-политиками, иначе они не ограничивают.

**Чего избежать.** Трёх вещей. Первая — **владелец таблицы обходит RLS молча**:
если рантайм подключается ролью-владельцем схемы (а это типично), RLS не работает
вообще и об этом никто не узнает; нужен `FORCE ROW LEVEL SECURITY` и отдельная
роль приложения, не владеющая таблицами. Вторая — **BYPASSRLS у миграционной
роли** не должна быть у рабочей. Третья — не пытаться выразить в RLS всю модель
§12: RLS отвечает на «какие строки видны», а не на «в каком режиме выполняется
действие»; режим (deny/ask/account/allow) — это решение до вызова, в ядре (§12.4).
Раздел DESIGN.md: **§15.7, §0.6, §12.4**.

### 2.2 SET ROLE и request-scoped identity

**Как устроено.** `SET ROLE role_name` меняет текущий идентификатор пользователя
сессии: «permissions checking ... is carried out as though the named role were
the one that had logged in originally». `RESET ROLE` / `SET ROLE NONE`
возвращают к `session_user`. Важные детали из документации 17:

- Проверки для самих `SET ROLE` и `SET SESSION AUTHORIZATION` — исключение: они
  идут по `session_user` и по изначально аутентифицированному пользователю.
  Поэтому **`RESET ROLE` может выполнить кто угодно**: `SET ROLE` не понижает
  права необратимо.
- Если членство выдано `WITH INHERIT TRUE`, роль автоматически имеет все права
  вышестоящих; `SET ROLE` тогда эффективно *сбрасывает* всё лишнее. При
  `WITH INHERIT FALSE, SET TRUE` права доступны только через явный `SET ROLE`.
- **`SET ROLE` не применяет per-role настройки из `ALTER ROLE ... SET`** — они
  срабатывают только при логине. То есть `search_path`, привязанный к роли, после
  `SET ROLE` не подхватится.

- Источник: https://www.postgresql.org/docs/17/sql-set-role.html

**Что забрать.** `SET ROLE` + `SET LOCAL` внутри транзакции — честный способ
сделать request-scoped identity: соединение открыто служебной ролью, но на время
обработки одного вызова агента переключается в роль деплоймента. В паре с RLS
это даёт §15.7 в точности: деплоймент не видит чужого, потому что у его роли нет
GRANT. Для идентичности внутри запроса (кто агент, от чьего имени, какой проект)
— `set_config('hyper.actor', ..., true)` с `true` = local, читается в RLS-предикате
через `current_setting('hyper.actor', true)`.

**Чего избежать.** Главная ловушка: **`SET ROLE` не является границей
безопасности сам по себе, потому что обратим**. Любой код, исполняемый в сессии
(а по §0.6 это код пользователя), может сделать `RESET ROLE` и вернуть себе
права служебной роли. Отсюда жёсткое правило для нас: если пользовательский код
исполняется в том же процессе, соединение должно быть открыто **сразу под
нужной ролью** (отдельный пул / отдельный DSN на деплоймент), а не переключено
через `SET ROLE`. `SET ROLE` годится для нашего доверенного ядра, а не для
изоляции недоверенного кода — что ещё раз подтверждает §0.6 («либо только
админы, либо за границей процесса») и §15.8 (ephemeral-compute вообще без
соединения с БД).
Раздел DESIGN.md: **§15.7, §0.6, §15.8**.

### 2.3 PgBouncer и пулы с разными ролями

**Как устроено.** `pool_mode`: `session` (сервер возвращается в пул после
дисконнекта клиента — по умолчанию), `transaction`, `statement`. PgBouncer
по умолчанию отслеживает и восстанавливает при переключении клиента лишь
небольшой набор параметров — `client_encoding`, `datestyle`, `timezone`,
`standard_conforming_strings`, `application_name`; остальные нужно явно
перечислять в `track_extra_parameters`. Есть `auth_user` + `auth_query` для
запроса пароля из `pg_authid` (документация рекомендует не суперпользователя, а
`SECURITY DEFINER`-функцию).

Прямое подтверждение проблемы — **issue #75 «Set role and schema on connection»,
закрыт как won't-fix**. Мейнтейнер (markokr): «SET SCHEMA will not work as well as
you hope... It seems much simpler and robust setup if you give each tenant
separate db user». Репортёр формулирует ровно нашу дилемму: отдельный db-user на
tenant означает, что пул почти не переиспользуется между tenant'ами
(«connections cannot be shared across authenticated users, hence the SET ROLE»),
и приходится держать много соединений. Issue закрыт без реализации.

- Источники: https://www.pgbouncer.org/config.html, https://github.com/pgbouncer/pgbouncer/issues/75

**Что забрать.** Честную формулировку компромисса: **пул общий ИЛИ роль на
деплоймент — но не оба сразу, бесплатно**. Правильный путь для нас — то, что и
советует мейнтейнер: отдельная роль = отдельный пул (отдельный DSN), с малым
`server_lifetime`/`server_idle_timeout`, вместо переключения ролей внутри одного
соединения. Деплойментов у нас десятки, а не тысячи tenant'ов (§15.6), так что
цена приемлема.

**Чего избежать.** Схемы «один пул + `SET ROLE` на каждый запрос» в transaction
pooling. Она ломается тихо и двумя способами: (а) `SET ROLE` без `LOCAL`
переживает возврат соединения в пул, и следующий клиент получает чужую роль —
PgBouncer не сбрасывает то, чего не знает (`track_extra_parameters` по умолчанию
не покрывает роль); (б) `RESET ROLE` доступен кому угодно (§2.2). Это прямая
утечка прав между деплойментами. Правило для §15.7: **роль приходит из строки
подключения, а не из SQL-команды.**
Раздел DESIGN.md: **§15.7, §15.6**.

## 3. Делегированные полномочия

Центральный вопрос раздела: как выразить «полномочие, суженное по scope и
времени, выданное агенту» — то есть наш grant из §11.3.

### 3.1 OAuth 2.0 Token Exchange (RFC 8693)

**Как устроено.** Расширение grant type для обмена одного токена на другой.
Параметры запроса: `subject_token` + `subject_token_type` (обязательны — «от чьего
имени»), `actor_token` + `actor_token_type` (опционально — «кто действует»),
`requested_token_type`, `resource`, `audience`, `scope`. RFC явно разделяет два
режима:

- **Impersonation**: «A is B within the context of the rights authorized by the
  token» — получатель не может отличить, что действует не B.
- **Delegation**: «principal A still has its own identity separate from B, and it
  is explicitly understood that while B may have delegated some of its rights to
  A, any actions taken are being taken by A representing B. In a sense, A is an
  agent for B.»

Делегирование выражается claim'ом **`act`**:
```json
{ "iss":"https://issuer.example.com", "sub":"user@example.com",
  "exp":1443904177, "act": { "sub":"admin@example.com" } }
```
Токен *про* `user@example.com`, но текущий актор — `admin@example.com`. Цепочка
делегирования — вложенные `act`; самый внешний = текущий актор, вложенные =
история. Жёсткое правило RFC: «For the purpose of applying access control policy,
the consumer of a token **MUST only consider the token's top-level claims and the
party identified as the current actor** by the `act` claim. Prior actors ...
are informational only and are not to be considered in access control decisions.»
Отдельный claim **`may_act`** — утверждение, что некая сторона *вправе стать*
актором за другую; используется сервером авторизации при решении, можно ли
выдать запрошенное делегирование.

- Источник: https://www.rfc-editor.org/rfc/rfc8693.txt (§1.1, §2.1, §4.1, §4.4)

**Что забрать.** Это готовая, стандартизованная форма нашего кортежа из §11.2
(`агент × от чьего имени × ...`). Три вещи берём дословно:
1. **Разделение impersonation / delegation — и выбор delegation.** Наш агент
   НЕ становится Аней. Он действует как отдельная сущность, представляющая Аню.
   Это прямо обосновывает §12.3: «отвечает человек, от имени которого действовал
   агент» — потому что в токене оба видны.
2. **`act` как цепочка с историей, но решение — только по текущему актору.**
   У нас §8 (федерация) и делегирование родитель→подагент дают именно цепочки.
   Правило RFC — то, что нам нужно: цепочка пишется в аудит (§12.2), но права
   считаются по текущему актору; иначе подагент унаследует права по всей цепи.
3. **`may_act`** — отдельное утверждение «X вправе стать актором за Y». Это наш
   §14.2: «полномочие вносит человек, а не комната». `may_act` — это и есть
   формальная запись того, что человек внёс полномочие.

**Чего избежать.** Impersonation-режима как такового. Он удобен и он же делает
§12 невыполнимым: если агент неотличим от человека, аудит-событие §12.2 не может
указать, кто на самом деле действовал, и «ответить» некому. Также: RFC
сознательно оставляет за скобками модель доверия и формат токена — то есть он
даёт форму, но не безопасность; узость scope придётся обеспечивать нам.
Раздел DESIGN.md: **§11.2, §11.3, §12.3, §14.2**.

### 3.2 On-Behalf-Of (Microsoft Entra)

**Как устроено.** Реализация RFC 8693 для цепочки сервисов: middle-tier API
получает токен A от пользователя и обменивает его на токен для downstream API B.
Существенные ограничения из документации:

- OBO **использует только delegated scopes, не application roles**: «Roles remain
  attached to the principal (the user) and never to the application operating on
  the user's behalf. This occurs to prevent the user gaining permission to
  resources they shouldn't have access to.»
- **OBO работает только для user principals.** Сервис, получивший app-only токен,
  не может обменять его «за себя» — для этого client credentials.
- Middle-tier с собственным ключом подписи не может участвовать в OBO: downstream
  не сможет проверить подпись токена, подписанного ключом клиента.
- Согласие на downstream-доступ собирается **заранее**, на этапе аутентификации,
  потому что у middle-tier нет взаимодействия с пользователем.

- Источник: https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-on-behalf-of-flow

**Что забрать.** Правило «роли принадлежат человеку и НЕ переходят приложению,
действующему от его имени» — это независимое подтверждение нашего §13.3 и §13.6:
«роль даётся человеку, а его агент получает её только явным сужением». Microsoft
пришёл к этому же из-за конкретного риска — иначе пользователь через приложение
получает права, которых у него нет. И второе: «нет взаимодействия с
пользователем → согласие собирается заранее» — ровно наша §11.4 («нельзя
запрашивать подтверждение из фонового цикла молча»): если спросить нельзя,
полномочие должно быть выдано заранее и узко, а не додумано на месте.

**Чего избежать.** Сбор всех возможных согласий авансом «на всякий случай» — это
как раз и превращает delegated scope в широкий постоянный доступ. Наш §11.3
требует обратного: узкий фильтр и срок. Значит, согласие заранее — да, но на
конкретный фильтр, а не на весь ящик.
Раздел DESIGN.md: **§13.3, §11.4**.

### 3.3 Google Workspace domain-wide delegation

**Как устроено.** Администратор Workspace-домена авторизует service account
(по его OAuth client ID) на набор scope'ов; после этого service account может
получать токены, **имперсонируя любого пользователя домена** (поле `sub` в JWT —
email жертвы... то есть пользователя). Документация формулирует прямо:
приложение, использующее Calendar API, может добавлять события в календари
*всех* пользователей домена. Выдаёт только super administrator, через Admin
console.

- Источник: https://developers.google.com/identity/protocols/oauth2/service-account

**Что забрать.** Практически нечего — кроме отрицательного примера, и он очень
полезный. Это **ровно та модель, которую §11.1 описывает как текущее
(недопустимое) состояние Hyper**: `google.token` берёт «единственный
авторизованный» аккаунт, «there is no account allowlist» — то есть любой агент
читает любой подключённый ящик. DWD — это индустриальный стандарт с той же
дырой: согласие даёт админ, а не владелец данных.

**Чего избежать.** Всей конструкции целиком. Наш §11.4 говорит: «спрашивают
владельца ресурса, а не того, кто инициировал задачу». DWD нарушает это по
устройству: доступ к ящику Коли выдаёт администратор, Коля не участвует и не
уведомляется. Конкретное требование к нашей реализации (§11.7 п.1): обязательный
явный `account`, запрет неявного выбора, и — добавляю по итогам — **никакого
организационного механизма, дающего доступ к личным ресурсам всех сразу**.
Если такой механизм нужен операционно (например, увольнение), он обязан быть
режимом `account` (§12) с уведомлением владельца, а не тихим `allow`.
Раздел DESIGN.md: **§11.1, §11.4, §11.7, §12**.

### 3.4 GitHub App: installation tokens vs user-to-server

**Как устроено.** Три разных способа аутентификации одного приложения:
1. **Как само приложение** — JWT, подписанный приватным ключом; нужен только
   чтобы выпустить installation token и управлять самим приложением.
2. **Как installation** — installation access token, выпускается по JWT.
   «Authenticating as an app installation lets your app access resources that are
   owned by the user or organization that installed the app... ideal for
   automation workflows that don't involve user input.» Токен **истекает через
   1 час**. При выпуске можно передать `repositories` или `repository_ids` и
   **сузить токен до конкретных репозиториев**; без них токен получает доступ ко
   всему, что было выдано установке.
3. **От имени пользователя** — user access token: действия атрибутируются
   пользователю, и доступ ограничен пересечением прав приложения и прав
   пользователя.

- Источники: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/about-authentication-with-a-github-app, https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app

**Что забрать.** Это **лучшая найденная практическая модель для нашего гранта
агенту**, и забрать стоит целиком:
- **Долгоживущее право (installation) ≠ короткоживущий токен (1 час).** У нас
  grant (§11.3) живёт в таблице со сроком, а исполняющий его «ключ» выдаётся на
  время задачи. Отзыв гранта тогда реально работает в пределах часа, а не
  «никогда».
- **Сужение при выпуске**: `repository_ids` — это и есть «фильтр гранта» из
  §11.3, применённый в момент выдачи, а не в момент проверки. Агент, которому
  нужен один репозиторий, получает токен на один репозиторий.
- **Три разных субъекта — приложение / установка / пользователь** — почти точно
  наши §11.2 «кто действует / где действие имеет смысл / от чьего имени».
- Атрибуция: действия installation видны как действия приложения, а не человека
  — что делает аудит §12.2 осмысленным.

**Чего избежать.** Дефолта «если не перечислил репозитории — доступ ко всему».
Это ровно наоборот нашему §6 правилу 1 (наследование = пересечение) и §6 правилу 4
(гость получает пустой набор). У нас умолчание обязано быть пустым: не указан
фильтр — грант не выдаётся.
Раздел DESIGN.md: **§11.3, §11.2, §6, §12.2**.

### 3.5 Slack: bot tokens vs user tokens

**Как устроено.** Явно разные классы токенов:
- **Bot token** (`xoxb-`) — представляет бота, привязан к приложению, **не к
  личности пользователя**; приложение остаётся установленным, даже если
  установивший сотрудник деактивирован. Гранулярные scope'ы.
- **User token** (`xoxp-`) — «represent the same access a user has to a workspace».
  Записи выполняются «as if by the user themselves». Scope'ы ресурсные: запросил
  `channels:history` — получил историю *любого* публичного канала.
- **App-level** (`xapp-`) — приложение across organizations.
- **Workflow token** — «just in time» токены, подмножество bot-токенов, не могут
  делать то, что требует user scope.
- Legacy bot tokens — «umbrella» scope; платформа от этой модели ушла, и
  документация прямо говорит: такие токены «take on the full operational scope of
  the user that created them».

- Источник: https://api.slack.com/concepts/token-types

**Что забрать.** Разделение «агент действует как агент» / «агент действует как
человек» — это наш §12.3 и §13.3. И очень практичное наблюдение: bot-токен
переживает увольнение установившего, а user-токен — нет. Для нас это вопрос
из §0.5 (подписки принадлежат людям): фоновая работа, привязанная к личному
токену, умирает вместе с человеком; работа на ресурсах организации — не должна.
Плюс «workflow token = just-in-time подмножество» — ещё одно подтверждение
паттерна «узкий короткоживущий токен под конкретную задачу».

**Чего избежать.** Двух вещей, которые Slack сам признал ошибкой. Первая —
umbrella scope (legacy bot): одно право, включающее всё. Вторая, не признанная
и до сих пор актуальная — **ресурсная широта user-scope**: `channels:history`
даёт историю всех публичных каналов, без возможности сузить до одного. Это
антипример для нашего §11.3: scope без фильтра по конкретному ресурсу — это не
грант, а роль. Наш grant обязан называть ресурс.
Раздел DESIGN.md: **§11.3, §13.3, §0.5**.

### 3.6 SPIFFE / SVID

**Как устроено.** Стандарт идентичности для workload'ов. **SPIFFE ID** — строка
`spiffe://trust-domain/path`, «structured string used to identify a resource or
caller». **SVID** (SPIFFE Verifiable Identity Document) — документ, которым
workload криптографически предъявляет свой SPIFFE ID; форматы — X.509-SVID и
JWT-SVID. Ключевая идея: workload получает идентичность **от платформы, по факту
своего запуска и окружения**, а не из вшитого секрета.

- Источники: https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE-ID.md, https://github.com/spiffe/spiffe/blob/main/standards/X509-SVID.md

**Что забрать.** Идентичность деплоймента (§15) должна выдаваться платформой при
запуске, а не лежать в конфиге. У нас деплоймент = project × compute (§15), и
именно он — носитель прав в базе (роль Postgres, §15.7). SPIFFE-подобный ID
(`hyper://org/project/landing/compute/mac-1`) даёт единое имя для: роли в
Postgres, субъекта гранта и поля в аудит-событии. Это дёшево и снимает вопрос
«как деплоймент доказывает, кто он».

**Чего избежать.** Разворачивать SPIFFE/SPIRE как инфраструктуру — несоразмерно
(§15.7, «не делаем свой оркестратор»). Берём схему именования и принцип выдачи
при запуске, не берём сервер аттестации.
Раздел DESIGN.md: **§15, §15.7, §12.2**.

### 3.7 Macaroons и Biscuit: attenuation как операция

**Как устроено.** *Macaroons* (Birgisson et al., Google, NDSS 2014) — bearer-токены
на цепочке вложенных HMAC. Токен несёт **caveats** — предикаты, которые
*сужают* его полномочия и контекстно ограничивают, «when, where, by who, and for
what purpose» сервис должен авторизовать запрос. Ключевое свойство: **любой
держатель может добавить caveat и получить более слабый токен, без обращения к
эмитенту** — цепочка HMAC одновременно и распределяет ключ, и защищает
целостность. Есть third-party caveats: требование предъявить discharge-макарун
от другой стороны (например, от сервиса детекции злоупотреблений).

*Biscuit* — современный потомок: «bearer token that supports offline attenuation
... and decentralized verification». Политики на Datalog: `check if` / `check all`
/ `reject if`. Примеры прямо из спецификации:
```
check if resource($0), right($0, $1)
check if time($0), $0 < 2019-02-05T23:00:00Z          // срок
check if source_ip($0), ["1.2.3.4","5.6.7.8"].contains($0)
check if resource($0), $0.starts_with("/folder/")      // префикс
```
Attenuation использует эфемерные ключевые пары; есть **sealed**-версия токена,
запрещающая дальнейшее сужение; есть third-party blocks, подписанные внешней
стороной и привязанные к конкретному токену через `previousSignature`.

- Источники: https://research.google.com/pubs/archive/41892.pdf, https://github.com/biscuit-auth/biscuit/blob/main/SPECIFICATIONS.md

**Что забрать.** Это концептуально **самая точная модель для «одолженного
полномочия в комнате» (§0, §14)**. Три идеи:
1. **Attenuation монотонна: сужать может кто угодно, расширять — никто.** Когда
   агент делегирует подагенту (§8, delegate), подагент обязан получать строго
   более узкое полномочие. Это свойство надо сделать инвариантом ядра, а не
   соглашением. Прямо закрывает §8.1 (лестница доверия): уровень пира
   ограничивает сверху, а не выдаёт.
2. **Caveat как выражение срока и фильтра одновременно** — `check if time(...) <
   ...` и `resource.starts_with("/folder/")` — это буквально «письма с меткой
   landing за последние 30 дней, до 1 марта» из §11.3.
3. **Sealed-токен** — «дальше делегировать нельзя». У нас это нужно для §14.2:
   полномочие, внесённое человеком в комнату, не должно уходить из комнаты
   дальше по цепочке.

**Чего избежать.** Bearer-семантики. Macaroon — предъявительский: кто получил,
тот и пользуется; отзыв возможен только через caveat со сроком или внешнюю
проверку. У нас же §11.3 и §12 требуют, чтобы каждое использование гранта было
записано с обоснованием и адресатом. Поэтому: **модель attenuation забираем,
формат bearer-токена — нет.** Наш грант — строка в Postgres, проверяемая ядром
в одной точке (§11.7 п.3), а сужение — операция над этой строкой. Тогда каждое
использование видно, что для §12.2 обязательно.
Раздел DESIGN.md: **§8.1, §11.3, §14.2, §12.2**.

## 4. Accountability: как устроено «разрешено, но ты ответишь»

Это раздел про наш режим `account` (§12) — самый нестандартный элемент дизайна.
Вывод вперёд: **чистого аналога `account` в найденных системах нет**; индустрия
разделена на «запретить и выдавать по запросу» (JIT) и «разрешить и логировать»
(sudo/break-glass). Наш `account` — это их середина, и она собирается из частей.

### 4.1 sudo: логирование как условие доступа

**Как устроено.** В `sudoers` режим задаётся тегами на правиле, а не глобально:
`LOG_INPUT` / `NOLOG_INPUT`, `LOG_OUTPUT` / `NOLOG_OUTPUT` (запись ввода-вывода
сессии в I/O-логи), `MAIL` / `NOMAIL` (уведомление), `PASSWD` / `NOPASSWD`
(требовать ли пароль), `INTERCEPT` / `NOINTERCEPT`, `SETENV`, `NOEXEC`. Есть
`mail_always`. Плюс «лекция» (lecture) при первом использовании — напоминание об
ответственности.

- Источник: https://www.sudo.ws/docs/man/sudoers.man/

**Что забрать.** Структуру: **режим — это набор тегов на паре (кто, что можно), а
не свойство команды**. Это ровно наше требование §12.4 («режим — свойство пары
(действие, ресурс)»). Конкретно полезны три тега как модель: `NOPASSWD` ≈ наш
`allow`, `PASSWD` ≈ `ask`, `MAIL`+`LOG_OUTPUT` ≈ `account` (делай, но событие
уйдёт адресату и запись останется). То, что sudo различает «уведомить» и
«записать» отдельными тегами, полезно: у нас §12.2 требует и адресата, и запись
— это два разных свойства, и стоит их разделить.

**Чего избежать.** Sudo пишет логи «в никуда»: syslog, который читают постфактум
и обычно не читают. §12.1 у нас прямо говорит, что аудит-событие бессмысленно,
если его никто не читает, а §12.2 требует адресата и жизненного цикла. То есть
берём теги, не берём «лог как место, где всё умирает».
Раздел DESIGN.md: **§12.4, §12.2, §12.1**.

### 4.2 Google BeyondCorp

**Как устроено.** Отказ от периметра: доступ к приложению определяется не сетью,
а состоянием пользователя и устройства на момент запроса. Компоненты по статье:
**Device Inventory Database** (мета-инвентарь, отслеживающий изменения устройства
за его жизненный цикл), **устройство идентифицируется сертификатом**, хранимым в
TPM или квалифицированном хранилище, и сертификат выдаётся только устройству,
которое «present and correct» в инвентаре. **Access Control Engine** внутри
access proxy даёт «service-level authorization to enterprise applications on a
per-request basis», делая утверждения о пользователе, его группах и устройстве.
Движок «constantly fed by a running pipeline that dynamically extracts information
useful for access decisions» — включая trust-уровни устройств и пользователей.

- Источник: Ward & Beyer, «BeyondCorp: A New Approach to Enterprise Security», ;login: 2014 — https://storage.googleapis.com/gweb-research2023-media/pubtools/pdf/43231.pdf

**Что забрать.** Две вещи. Первая — **решение принимается per-request и на
основании динамически вычисляемого уровня доверия**, а не статической записи.
У нас есть прямой аналог: §8.1 (лестница доверия пиров) и §13.4 (роль влияет на
режим, а не только на «можно/нельзя»). BeyondCorp подтверждает, что «уровень
доверия → режим» — рабочая индустриальная конструкция, а не изобретение.
Вторая — **инвентарь как обязательное условие идентичности**: устройства нет в
инвентаре → нет сертификата → нет доступа. У нас это §15: compute должен быть
зарегистрирован, иначе деплоймент на нём не получает роли в Postgres.

**Чего избежать.** Масштаба реализации: мета-инвентарь, пайплайн, access proxy
перед каждым сервисом — это годы работы отдела. Нам нужно взять принцип
(доверие динамично и влияет на режим) без инфраструктуры.
Раздел DESIGN.md: **§8.1, §13.4, §15**.

### 4.3 Netflix ConsoleMe

**Как устроено.** Веб-сервис централизованного управления AWS IAM: несколько
способов входа в консоль под ролью, **IAM Self-Service Wizard** — запрос прав
«plain English», автогенерация cross-account resource policy с применением в один
клик, управление ролями/политиками/S3/SQS/SNS; CLI `weep` раздаёт креды локально
пятью способами.

**Важный факт о состоянии проекта: репозиторий архивируется и переводится в
read-only 1 марта 2026**. Причина по README: внутренние версии в Netflix
значительно разошлись с OSS после крупного рефакторинга, поддерживать две
версии команда не может. 3200+ звёзд, но развитие остановлено.

- Источник: https://github.com/Netflix/consoleme/blob/master/README.md

**Что забрать.** Идею **self-service запроса прав на понятном языке** с
автогенерацией конкретной политики. Для нас это §11.4: агент формулирует запрос
(кто просит, зачем, что именно, на какой срок), а система превращает его в
узкий грант. ConsoleMe подтверждает, что «человек описывает намерение → система
генерирует минимальную политику» работает на практике.

**Чего избежать.** Централизованного портала-посредника ко всем правам как
отдельного продукта — его судьба показательна: он дублирует то, что должно быть
в самой платформе. У нас проверка гранта — «в одной точке ядра» (§11.7 п.3), а
не в отдельном сервисе сбоку.
Раздел DESIGN.md: **§11.4, §11.7**.

### 4.4 Just-in-time access: Teleport

**Как устроено.** Access Requests («Just-in-Time Access Requests»): пользователь
запрашивает доступ к роли или к конкретному ресурсу, запрос одобряется или
отклоняется **настраиваемым числом одобряющих**. Два вида: **Role Access
Requests** (временные креды с повышенной ролью для системных задач) и **Resource
Access Requests** (доступ только к нужному ресурсу). Заявленные свойства: **dual
authorization** — два ревьюера должны одобрить (это удовлетворяет FedRAMP AC-3),
**принцип наименьших привилегий** — «attacker no permanent admin roles», привилегии
выдаются на ограниченный период. Пользователь не может одобрить собственный
запрос; есть автоматические ревью по правилам и маршрутизация уведомлений.
Функциональность — только в Teleport Enterprise.

- Источник: https://goteleport.com/docs/identity-governance/access-requests/

**Что забрать.** Три конкретные вещи для §11.4 и §12:
1. **Разделение «запрос роли» и «запрос ресурса»** — точно наше разделение
   роль (§13) / grant (§11). Подтверждение, что это не два способа сказать
   одно и то же, а разные операции с разными UX.
2. **Нельзя одобрить свой запрос.** Простое правило, которого у нас в §11.4 явно
   не записано, а надо: агент Ани не может уговорить Аню — это есть, но «Аня не
   одобряет запрос к своему же ресурсу от своего же агента автоматически» —
   стоит уточнить.
3. **Постоянных админ-ролей не существует** — повышение всегда временное.
   Для нас: роль `admin` организации (§13.4) не должна давать `allow` на чужое
   постоянно; §13.4 уже говорит «чтение чужого ресурса → всегда `account`».
   Teleport делает шаг дальше: право вообще не существует, пока не запрошено.

**Чего избежать.** Чистого JIT как единственного режима: он требует человека в
цикле на каждое повышение, а §12.1 прямо говорит, что `ask` на каждый шаг
убивает автономность агента. JIT — форма нашего `ask`, а не замена `account`.
Раздел DESIGN.md: **§11.4, §12.1, §13.4**.

### 4.5 Break-glass

**Как устроено.** Чего не нашёл: искомая страница Google Cloud Architecture
Framework про break-glass по прямому URL вернула 404, и я не подобрал
надёжной замены из первоисточника — поэтому детальную схему GCP тут не привожу,
чтобы не пересказывать по памяти. Общая конструкция, подтверждаемая
рассмотренными системами (Teleport dual authorization, sudo `MAIL`+`LOG_OUTPUT`,
BeyondCorp per-request решение): break-glass = заранее созданное, обычно
неактивное полномочие, активация которого (а) требует явного действия и
обоснования, (б) немедленно уведомляет, (в) ограничена по времени, (г)
обязательно разбирается постфактум.

**Что забрать.** Именно жизненный цикл: *активация → уведомление → срок →
обязательный разбор*. Это и есть недостающая часть нашего `account`: §12.2 уже
описывает событие, адресата и ответ, но не говорит, что **разбор обязателен**,
а не опционален. Break-glass-практика: если событие не разобрано, это само по
себе инцидент.

**Чего избежать.** Break-glass, который не разбирают, вырождается в обычный
доступ — самая частая претензия к нему. Наш §12.2 «накопление» (40 раз читал
чужие календари → поднять вопрос) — правильное лекарство; его надо сделать
автоматическим порогом, а не ручным наблюдением.
Раздел DESIGN.md: **§12.2**.

### 4.6 Вывод по `account`

Сопоставление режимов §12 с найденным:

| Наш режим | Ближайший индустриальный аналог | Что взять |
|---|---|---|
| `deny` | Cedar `forbid` (побеждает всегда) | неперекрываемый слой, не «правило с приоритетом» |
| `ask` | Teleport Access Request; sudo `PASSWD` | нельзя одобрять свой запрос; спрашивают владельца |
| `account` | **прямого аналога нет**; ближе всего sudo `MAIL`+`LOG_OUTPUT` и break-glass | обоснование ДО действия; адресат; обязательный разбор; порог накопления |
| `allow` | sudo `NOPASSWD` | обычный лог |

`account` действительно является оригинальной частью дизайна. Ближайшие
родственники — break-glass (но он исключительный, а наш `account` рутинный) и
sudo с `MAIL` (но там нет обоснования и жизненного цикла). Это аргумент за §12,
а не против: пробел в индустрии реальный — системы умеют блокировать и умеют
логировать, но не умеют «разрешить под ответственность» как штатный режим.
Риск, о котором стоит знать: без обязательного разбора (§4.5) `account`
выродится в `allow` с логами, и тогда весь §12 обесценится.

### Три самых сильных вывода

1. **Grant = caveated tuple с обязательным expiration.** OpenFGA Conditions и
   SpiceDB `caveat_context`/`expiration` дают готовую, проверенную в проде схему
   для §11.3. Срок — колонка с индексом, фильтр — JSONB, отзыв — не DELETE.
2. **Граница — соединение, а не команда.** RLS работает, но `SET ROLE` обратим
   (`RESET ROLE` доступен любому), а PgBouncer не умеет безопасно переключать
   роли в пуле (issue #75, won't-fix). Значит §15.7 реализуется как «роль в DSN
   деплоймента + `FORCE ROW LEVEL SECURITY`», а не «одна сессия с переключением».
3. **Attenuation должна быть инвариантом ядра.** Из macaroons/biscuit: сужать
   может кто угодно, расширять — никто. Применительно к §8.1 и делегированию
   подагентам это превращает лестницу доверия из соглашения в проверяемое
   свойство. Но формат — строка в Postgres, а не bearer-токен, иначе §12.2
   (каждое использование записано) невыполним.

### Чего не нашёл

- Детальной первоисточниковой схемы break-glass в Google Cloud (страница
  Architecture Framework вернула 404) — раздел 4.5 написан как обобщение
  рассмотренных систем и это в нём отмечено.
- Прямого индустриального аналога режима `account` (§12): системы либо блокируют
  и выдают по запросу (JIT), либо разрешают и пишут лог. Комбинации
  «разрешено + обоснование до действия + адресат + обязательный разбор» как
  штатного режима я не нашёл ни в одной из рассмотренных систем.

# Архитектура плагинов: runtime в procs, доставка отдельно

Статус: архитектурное решение с реализованным первым этапом — opt-in реестр путей для source runtime и read-only preview миграции. Остальные этапы ниже остаются планом. Рабочая конфигурация не переключена, файлы плагинов не перемещены.

Руководство по написанию плагинов: [канонический SKILL.md](../src/plugins/SKILL.md).

## Реализовано: первый безопасный этап

- `procs.modules.readPluginRegistry({})` читает `workspace.json.pluginRegistry: { version: 1, entries: [{ path, enabled }] }`. Отсутствие ключа сохраняет legacy; пустой массив исключает управляемые плагины, но не core и обычные неплагинные модули. Относительные пути разрешаются относительно WORKDIR; поддерживается `~`, realpath устраняет повторные пути.
- `discover` выбирает явные корни без импорта отключённого кода. Смена режима, записей или разрешённых realpath в работающем процессе требует перезапуска. Это не полноценный hot-unload.
- В explicit-режиме `modules.fetch` не клонирует репозитории и не устанавливает зависимости: подготовка выполняется отдельно.
- `plugins.previewMigration({})` ничего не записывает: возвращает предложение реестра, диагностику корней, `ready`, `blockers` и `restartRequired`. Alias/prefix, неоднозначный порядок, неразрешённые объявления и конфигурация, требующая проверки, блокируют автоматический переход. Значения настроек и секретов не возвращаются. API применения миграции пока нет.
- Поддерживается только запуск из исходников. `procs.dev.build` отклоняет explicit-режим до записи сборки; уже собранные executable не умеют применять этот реестр. Preview в baked-runtime блокируется.
- При проверке текущей установки preview нашёл 63 включённых корня и блокер `unresolved-declaration` для `liteparse`; переход не выполнялся. Это результат проверки, не постоянное свойство схемы.


## 1. Решение в двух словах

**procs отвечает за исполнение локальных, уже подготовленных исходников.** Он определяет корни, сканирует файлы и управляет общей жизнью деклараций. Приложение `plugins` отвечает за каталог, интерфейс, поиск и согласие пользователя на запуск доверенного кода. Провайдер доставки, например HyperHub, отвечает за Git: найти, получить и обновить checkout.

Целевая простая модель: Git-репозиторий с несколькими каталогами `plugins/<name>`, локальный checkout и реестр включения `path + enabled`. Разработчик редактирует тот же checkout, из которого загружается код. Отдельный неизменяемый snapshot-cache, копии каждого плагина для каждого commit и собственный пакетный менеджер для этой модели не нужны.

## 2. Что работает сейчас

### 2.1. Источники и конфигурация

Основные точки реализации:

- `src/procs/modules/paths.ts`: search roots из manifest и окружения; realpath-дедупликация.
- `src/procs/modules/readDeclared.ts`: объединение declarations хоста и workspace.
- `src/procs/modules/discover.ts`: эффективный набор runtime roots.
- `src/procs/project/scan.ts`, `src/procs/boot/load.ts`: сканирование, импорт и применение деклараций.
- `src/plugins/{load,reload,remove}.ts`: прикладные обёртки над `procs.modules`.

Хост задаёт `package.json.procs.modules` (есть совместимость с `proc`); машина добавляет `workspace.json.modules`. Старый ключ `workspace.json.plugins` используется как fallback через `modules ?? plugins`, **не как второй автоматически объединяемый список**. Workspace переопределяет записи хоста поверхностно. Значение `false` действительно исключает модуль до сканирования.

Discovery не сводится к workspace paths: есть собственные корни приложения и framework, `.hyper`, search roots, npm/path/git declarations, установленные проекты с prefix и дополнительные app roots. Official-плагины берутся из `procs.plugins`/`PROCS_PLUGINS`; валидные непосредственные дети `USER_PLUGINS` обнаруживаются автоматически. Optional-кандидаты не означают автоматического включения: нужно сохранить существующие правила запроса и исключения.

Семантика переменных окружения различается:

| Переменная | Не задана | Пустая строка |
|---|---|---|
| `PROCS_PATH` | manifest/default roots | также fallback, потому что проверяется truthiness |
| `PROCS_PLUGINS` | manifest/default plugin roots | явный пустой список official roots |
| `USER_PLUGINS` | слой user plugins отсутствует | слой user plugins отсутствует; пробелы обрезаются |

Пути `./` и `../` в search roots разрешаются от host project root, другие относительные пути — от workdir. Это не универсальное правило для всех API: миграция должна использовать существующий resolver каждой декларации, а не повторно толковать все строки одинаково. Имена контейнеров, порядок roots, prefix и порядок overrides влияют на результат; каталог пакета не задаёт автоматически namespace функций внутри `src`.

### 2.2. Load и remove пока не образуют полный lifecycle

`plugins.load` проверяет локальный manifest и вызывает `procs.modules.add`. `plugins.reload` вызывает общий reload: параметр `name` сейчас не означает изолированную перезагрузку одного плагина.

`procs.modules.reload` **сначала вызывает `fetch`**, затем boot load, lint, генерацию типов и перестройку routes. Индексы документации обновляются отдельно. Значит нынешний reload нельзя считать чистой операцией чтения локальных исходников. Legacy `procs.modules.fetch` умеет clone и `bun install`; это отличается от ограничений managed-copy пути ниже.

`procs.modules.remove` удаляет declaration из workspace и вызывает reload; файлы не удаляются. Старые функции остаются в registry до restart. Кроме того, удаление override может снова открыть автоматически обнаруживаемый или заданный по умолчанию модуль. Поэтому «remove» сейчас не гарантирует «отключён».

Повторный boot load не является атомарной заменой всего runtime: старые функции, settings/config, hooks и custom loaders могут оставаться. Loader для исчезнувшего kind может вообще не получить пустой набор. Reload не выполняет полный stop/start lifecycle плагина. **Этот документ не утверждает, что эти ограничения исправлены.**

В production boot объединяет baked entries и найденные файлы. Новый реестр нельзя реализовать только фильтром filesystem scan: нужно отдельно проверить исключение baked plugin entries, а также возможность выполнить их импорт до фильтра.

### 2.3. Существующая managed-copy доставка

`src/plugins/lifecycle.ts` и `validateTree.ts` реализуют отдельный путь: проверка подготовленных кандидатов, review, digest/provenance, установка копии и отчёт о частичном load failure. `validateTree` запрещает зависимости и package scripts в managed copies, embedded `.git`/`node_modules`, symlinks и ряд небезопасных файлов. Это ограничения **этого пути**, а не всех локально подключённых плагинов и не legacy fetch.

Эти проверки не создают sandbox: импортируемый плагин исполняет доверенный серверный код с правами процесса. Текущее snapshot/provenance поведение не следует выдавать за целевую Git-bundle модель или удалять без отдельной совместимой миграции.

## 3. Согласованные границы ответственности

| Слой | Владеет | Не должен делать |
|---|---|---|
| `procs` | Resolver roots, scan, import/load, общая регистрация и lifecycle деклараций, диагностика владельца и конфликта | Знать HyperHub, клонировать репозиторий при discovery, принимать пользовательское решение о доверии |
| Прикладной `plugins` | Каталог, поиск, UI, workflow review/approval, orchestration явных действий | Дублировать scanner, напрямую менять внутренние runtime registries, считать каталог источником истины о live-коде |
| Провайдер, например HyperHub | Git URL/ref/commit, получение checkout, diff и repo-wide update | Определять смысл `$route`, `$setting` или `$hook`, автоматически запускать полученный код |
| Владелец плагина | Исходники, manifest, декларации и явно описанные подготовительные действия | Предполагать, что reload откатывает любые побочные эффекты |

`procs` владеет общим протоколом деклараций и их удаления; конкретные loaders по-прежнему могут принадлежать HTTP, settings, hooks и другим модулям. «Перенести под procs» не означает перенести туда прикладной UI или знания о каждой интеграции.

## 4. Целевая модель локального реестра и Git bundle

### 4.1. Checkout как источник кода

Пример структуры, не новый обязательный формат конфигурации:

```text
<local-checkout>/
  plugins/
    alpha/package.json
    alpha/src/...
    beta/package.json
    beta/src/...
```

Согласованный формат — `workspace.json.pluginRegistry`, только версия и записи `path + enabled`:

```json
{
  "pluginRegistry": {
    "version": 1,
    "entries": [
      { "path": "/path/to/checkout/plugins/alpha", "enabled": true },
      { "path": "/path/to/checkout/plugins/beta", "enabled": false }
    ]
  }
}
```

Поля `name`, `source` и `prefix` не добавляются: идентичность папки выводится существующим `describe`. Для сравнения resolver получает canonical realpath; относительный путь допустим только с однозначной базой разрешения. Если прежний alias/prefix нельзя выразить этой схемой без изменения поведения, dry-run сообщает блокирующий конфликт, а не теряет его молча. Метаданные доставки — repository/ref/commit — не нужны scanner и принадлежат provider. Settings и секреты не переносятся в реестр.

Один checkout — одна единица Git update. Перед обновлением проверяется весь worktree, включая изменения соседних плагинов и untracked-файлы. При грязном дереве — отказ с понятной причиной; никаких автоматических reset, clean или stash. Пользователь видит diff всех затронутых плагинов, включая выключенные. Dev-редактирование идёт в том же checkout, без публикации и копирования перед каждым reload.

Получить новую ревизию на диске, подготовить её и активировать runtime — разные состояния. В первой версии после смены состава/версии нужен restart; старый процесс не должен изображать, что уже исполняет новое состояние реестра. Для code rollback можно явно вернуть Git revision, но это не откатывает БД или внешние действия.

### 4.2. Совместимость важнее автоматического перехода

- По умолчанию сохраняется **legacy discovery**. Отсутствие нового реестра не меняет установку пользователя.
- Новый режим включается явно и переживает restart: startup читает сохранённый desired registry до сканирования плагинов и до запуска их кода.
- В новом режиме реестр авторитетен для управляемых plugin roots. `enabled: false` — исключение, а не удаление записи, которое позволяет autodiscovery включить плагин снова.
- Отсутствующий реестр, явный пустой реестр и некорректный реестр различаются. Пустой — намеренно нет включённых управляемых плагинов; некорректный — явная ошибка, не молчаливый возврат к legacy.
- Framework, host/application roots и другие необходимые runtime roots не должны исчезнуть из-за пустого списка плагинов. Граница plugin roots и общих modules фиксируется тестами.
- Смена списка включения в V1 возвращает `restartRequired`, а UI различает desired и active состояние. Полный hot unload не обещается.
- Discovery/load нового режима не вызывает clone, `bun install`, hooks подготовки или legacy fetch для исключённых плагинов. Нужно проверить весь startup, а не только `discover`.

## 5. Безопасная миграция — только конфигурация

Первый шаг — **read-only dry-run**, который не импортирует плагины и не меняет диски, БД, settings или окружение. Он собирает текущую effective discovery, а не только записи `workspace.json`: иначе автоматически найденные official/user плагины будут потеряны.

Preview показывает разрешённые пути, порядок и имена, источник включения/исключения, optional/disabled кандидатов, конфликты и ожидаемый набор после restart. Он не печатает содержимое приватных конфигураций, secret values или credential-bearing URL. Optional отсутствующие плагины не превращаются во включённые; явно выключенные сохраняются как выключенные. Overrides и существующая precedence должны сохранять результат разрешения функций, а не только число каталогов.

Предлагаемый apply — отдельное явное подтверждение показанного preview. Проверка drift привязана к исходным manifest/config hashes, relevant env и базам путей, realpaths/inventory и целевой конфигурации; при изменении входных данных нужен новый preview. Запись конфигурации атомарная, с возможностью вернуться к прежнему режиму. Точный формат digest и backup — часть реализации, не существующий API.

Миграция **не перемещает каталоги**, не клонирует и не обновляет Git, не ставит зависимости, не запускает install scripts или миграции БД, не меняет settings, не удаляет legacy manifests и не делает скрытый reload. Применение пишет desired registry; следующий startup активирует его. Возврат конфигурации к legacy не является откатом уже выполненных миграций или внешних эффектов.

## 6. Подготовка отдельно от load

Будущая поддержка dependencies, migrations и install hooks — отдельное направление, а не незаметное расширение scanner:

1. **Delivery:** получить выбранный checkout и показать diff.
2. **Review:** согласовать доверие к коду и перечень подготовительных действий.
3. **Prepare:** явно выполнить разрешённую установку зависимостей, миграции и необходимые hooks с журналом результата.
4. **Activate:** включить подготовленные пути и выполнить restart/допустимый reload.

Это предложенный протокол, не готовая API. В managed-copy сейчас dependencies/scripts запрещены; нельзя написать, будто их уже можно включить флагом. Для локальных mounts окружение может быть подготовлено вручную. Нужны отдельные решения о lockfiles, package manager, разрешении зависимостей Bun и области действия hooks. Общий репозиторий может иметь общие dependencies — единица подготовки должна это учитывать.

Миграции БД должны выполняться явным контролируемым этапом, с записью результата. `down` может отсутствовать или терять данные. Возврат старого кода не гарантирует совместимости с новой схемой: нужны backward-compatible migrations либо отдельный план восстановления/backup. Автоматический rollback схемы при ошибке импорта недопустим как обещание.

## 7. Будущий полный lifecycle: что ещё потребуется

Полноценный hot unload — отдельный рефакторинг после безопасного startup-only режима.

- Каждая регистрация должна иметь owner: plugin/root/revision или generation. Это относится к функциям, routes, settings declarations, hooks, custom loaders и прикладным индексам. Settings values нельзя удалять вместе с declaration автоматически.
- Generic lifecycle должен вызывать dispose/unload callbacks и передавать пустой набор loaders, когда исчез последний файл соответствующего kind.
- Нужен учёт подписок, timers, workers, фоновых задач и in-flight запросов. Отключение расписания и удаление исторических данных — разные действия.
- Durable jobs/triggers должны иметь владельца и проверяться против active registry до claim/start. Startup reconciliation выполняется до запуска worker; простой restart сам по себе не очищает задания в БД.
- Нужны порядок stop зависимых компонентов, draining/cancellation, поведение при timeout и ошибках cleanup. Частичный stop нельзя объявлять успешной выгрузкой.
- Кандидатную таблицу деклараций можно подготовить до переключения, но **импорт модуля не транзакционен**: top-level код способен открыть соединение, запустить таймер, изменить внешний сервис или записать данные. Swap registry не откатывает эти эффекты. Strict import и lint не являются sandbox или транзакцией.

До реализации этого контракта remove/reload должны честно сообщать ограничения и необходимость restart, а не гарантировать отсутствие старого кода в процессе.

## 8. Этапы рефакторинга

1. **Зафиксировать baseline:** тесты effective roots, env semantics, optional/disabled, precedence, production baked entries и существующих побочных эффектов reload. Только наблюдение, без изменения установки.
2. **Ввести registry resolver в procs:** legacy по умолчанию, явный новый режим, read-only dry-run и диагностика. Сначала parity текущего discovery.
3. **Добавить подтверждаемую миграцию конфигурации:** drift check, атомарная запись, startup-only activation и desired/active UI. Убрать delivery из нового пути load, сохранив совместимость legacy.
4. **Упростить provider delivery:** Git bundle, чистый repo-wide update, один checkout для dev/runtime. Переход от managed copies — отдельный review, без удаления прежних установок по умолчанию.
5. **Спроектировать prepare:** dependencies/migrations/hooks с отдельными разрешениями и журналом. Не смешивать с load.
6. **При необходимости реализовать owner-aware unload:** cleanup, draining, jobs, reconciliation всех loaders, затем ограниченно разрешить горячую смену состава.

Каждый этап проверяем отдельно. Этот документ не запускает ни один из них.

## 9. Тесты и критерии приёмки

Базовые существующие тесты для расширения: `src/procs/modules.test.ts`, `src/procs/modules/{userPlugins,add,link}.test.ts`, `src/procs/repl/unload.test.ts`, `src/procs/{boot,lifecycle}.test.ts`, `src/plugins/{lifecycle,providers,configuration}.test.ts`. Тесты с замоканным reload не доказывают реальный unload; нужен интеграционный процесс со свежим startup.

| Проверка | Ожидаемый результат |
|---|---|
| Новый registry отсутствует | Тот же ordered effective набор roots и winners, что в legacy |
| `PROCS_PATH`/`PROCS_PLUGINS`/`USER_PLUGINS` отсутствуют или пусты | Сохранена индивидуальная семантика каждой переменной |
| package/workspace override, старый ключ `plugins`, `false`, optional | Нет потери precedence и неожиданного включения |
| Автоматические user children, official roots, npm/path и symlink aliases | Dry-run учитывает все применимые roots, dedupe и контейнерные имена |
| Explicit registry пуст/invalid | Пустой не включает плагины; invalid явно отклонён без fallback |
| Отключённый plugin после restart | Нет его runtime declarations и побочных импортов; core/host продолжают работать |
| Production baked plugin отключён | Не возвращается через baked merge; отдельно проверено исполнение static imports |
| Dry-run и config migration | Ни moves, clone/install/scripts, settings writes, code import, ни hot reload |
| Drift между preview и apply | Отказ без частичной записи и без исполнения |
| Restart после применения | Desired становится active; disabled jobs не запускаются до reconciliation |
| Git checkout dirty либо общий bundle изменён | Нет reset/clean; показан полный repo diff, update не притворяется обновлением одного каталога |
| Ошибка prepare/import/migration | Отдельные фактические статусы, без ложного обещания rollback БД/внешних эффектов |
| Legacy remove/reload | Регрессионный тест фиксирует текущие ограничения; новый UI их не скрывает |
| Будущий hot unload последнего файла kind | Удалены owned registrations, вызван cleanup, остановлены owned jobs/subscriptions |

Приёмка V1: opt-in режим переживает restart, default legacy не изменился, migration preview воспроизводит текущую композицию без секретов и побочных эффектов, а новый startup не доставляет и не подготавливает код автоматически. Полный hot unload не является критерием V1.

## 10. Открытые решения

- Точные имена CLI/API и правила разрешения относительных paths. Место и схема уже согласованы: `workspace.json.pluginRegistry: { version: 1, entries: [{ path, enabled }] }`; отсутствие означает legacy, пустой entries — явный пустой набор управляемых плагинов.
- Формальная граница управляемых plugin roots против общих modules, prefixed projects и `.hyper`; обязательные host roots не должны отключаться случайно.
- Идентичность, порядок и правила конфликтов для новых записей; миграция обязана сохранить legacy winners, даже если для новых installs потребуется более строгий отказ при конфликте.
- Build/runtime контракт для baked entries и static imports: startup-only режим нельзя объявить полноценным до проверки production.
- Политика review при repo-wide update, общих dependencies и подготовительных hooks; переход установленных managed copies без потери пользовательских правок.
- Допустимость и контракт hot unload, drain timeout, ownership durable jobs и восстановление после частично выполненного prepare.

Эти пункты требуют решения или явного ограничения поддержки до соответствующего этапа реализации. Они не повод усложнять первую версию immutable caches, отдельными копиями каждого commit или скрытой автоматизацией установки.
